# 2.2 本体论（Ontology）—— 知识图谱的骨架

> 定位：这一节是整章的理论核心。**没有本体，图只是一堆连起来的节点。** 我们要讲清本体由什么构成、它能表达什么、以及"有本体"和"没本体"在工程上差在哪。

本节目标：

1. 说清本体的定义与它解决的问题；
2. 掌握本体的五个核心构件（类 / 个体 / 属性 / 关系 / 公理）与两种层级关系（is-a 与 part-of）；
3. 分清 **TBox 与 ABox**（模式与实例），并理解描述语言的三个层次（RDFS / OWL / SHACL）；
4. 理解"推理"是怎么从本体里**推出新知识**的，以及开放世界假设（OWA）带来的反直觉后果；
5. 认识本体的**代价**，以及为什么很多工程系统（包括本项目）只用"弱本体"。

---

## 1. 什么是本体

哲学里"本体论"研究"存在什么"；在计算机里，本体的定义是：

> **对某个领域"存在哪些东西、怎么分类、彼此有什么关系"的一套显式、形式化的规范。**

拆开三个关键词：

| 关键词 | 含义 | 反例 |
|---|---|---|
| **显式** | 写下来了，不是"大家心里都懂" | 靠命名约定隐含的"章号相同的条文归一类" |
| **形式化** | 能被机器处理（有确定的语法与语义） | 一段自然语言的说明文档 |
| **规范** | 是**约束**，不是描述——它规定"应该怎样" | 一份"我们大概是这么用的"的备忘录 |

举个最贴近本项目的例子。"法条有章有节"这件事，如果只是"我们知道"，那**不是本体**；把它写成规则——"每个知识点必须属于某个章，章属于某个编（若有），条是章的下位结构"——并且由代码**强制执行**（切分时的状态机、建边时的分组键），这才算本体在起作用。

## 2. 本体的五个核心构件

### 2.1 类（Class）/ 概念（Concept）

**类**是对一组具有共同特征的事物的抽象。它回答"这个领域里有哪些**种类**的东西"。

```
类：法条（Article）
类：编（Part）
类：章（Chapter）
类：法律概念（LegalConcept）
```

类是**抽象**的——"法条"这个类本身不是某一条法条。

### 2.2 个体（Individual）/ 实例（Instance）

**个体**是类的具体成员。它回答"具体有哪些"。

```
个体：中华人民共和国劳动合同法·第四十六条   （属于"法条"类）
个体：试用期                                （属于"法律概念"类）
```

> 注意：**个体和它的名字不是一回事**。"劳动合同法第四十六条"是一个个体，而"第四十六条"只是它的标签——两部法律都有"第四十六条"。这个区分在多法库里至关重要（3.1 的"上下文标题必须带法律名"就是它的工程后果）。

### 2.3 属性（Property）/ 数据属性

**属性**描述个体的**内在特征**，取值是字面量（字符串、数字、日期）：

```
法条.名称     = "第四章·第四十六条"
法条.正文     = "用人单位应当向劳动者支付经济补偿…"
法条.来源行号 = "中华人民共和国劳动合同法.md L..."
```

### 2.4 关系（Relation）/ 对象属性

**关系**连接**两个个体**：

```
法条 --引用-->        法条        （crossref）
法条 --属于章-->      章          （结构）
法条 --同章相关-->    法条        （sibling）
概念 --对应条文-->    法条        （concept_map）
```

> **属性 vs 关系**的区分标准很简单：**另一端是"值"还是"实体"**。是值 → 属性；是另一个可以独立指称、还可能继续往外连的东西 → 关系。本项目把 `content`（正文）当属性、把"引用"当关系，正是因为这个区分——正文不会再往外连，而"被引用的那条法条"还要继续参与多跳。

### 2.5 公理（Axiom）/ 约束（Constraint）

**公理**是本体里"永远为真"的断言，用来**约束**类和关系。常见的几类：

| 公理 | 含义 | 例子 |
|---|---|---|
| **定义域**（domain） | 这个关系的主体必须属于哪个类 | "引用"的主体必须是法条 |
| **值域**（range） | 客体的类别 | "引用"的客体也必须是法条 → **这就是"跨法不建边"的另一种说法** |
| **基数约束**（cardinality） | 至少/至多几个 | "每一条法条**恰好**属于一个章" |
| **不相交**（disjointWith） | 两类不能重叠 | "编"与"章"不相交 |
| **传递性**（transitive） | 关系可传递 | "包含"是传递的：编包含章、章包含节 ⟹ 编包含节 |
| **互逆**（inverseOf） | 两个关系互为反向 | "引用"的逆是"被引用" |
| **等价**（equivalentClass） | 两个类外延相同 | "劳动合同"≡"劳动契约"（术语归一） |

**公理的价值在于"能把领域约束写下来、并被机器检查"**。项目里的例子：

```python
# 一条隐式公理：sibling 边只在同一个 (编, 章) 内建立
key = (point.part, point.chapter)
```

这条 `(编, 章)` 就是"同章"这个概念的**定义**（等价于"同一个章 ⟺ 编与章都相同"）。它在 3.2 会以"1.97 万条假边"的形式狠狠提醒我们：**公理写错，图就错**。

## 3. 两种层级关系：is-a 与 part-of

层级是本体最常用的结构，但**两种层级不能混**——这是本体设计里最经典的错误来源。

### 3.1 is-a（子类关系，subClassOf）：分类学（taxonomy）

表达"**是一种**"：

```
章 is-a 结构单元          （章是一种结构单元）
侵权责任编 is-a 编
```

特点：子类**继承**父类的属性与约束。"章有章号"这条规则，对"侵权责任编里的章"同样成立。

### 3.2 part-of（部分-整体，mereology）：组成关系

表达"**是……的一部分**"：

```
第一条 part-of 第一章
第一章 part-of 第一编
```

特点：**传递**（第一条 part-of 第一编），但**不继承属性**——"第一章有章号"并不意味着"第一条有章号"。

### 3.3 混用会出什么错

| 错误 | 后果 |
|---|---|
| 把 part-of 当 is-a | "第一条 is-a 第一章" → 推断出"第一条有章号"，逻辑与数据都乱 |
| 把 is-a 当 part-of | 概念层级丢失，无法按类做批量约束 |
| **层级少了一层** | 3.2 的"同号章并团"：民法典 7 编各自从"第一章"起算，少了"编"这一层，两个不同的"第一章"就被当成同一个 |

> 第三条是本项目**真实踩过的坑**：1.97 万条假 sibling 边、全库边数从 21252 虚高到 40992。根因就是**本体层级设计漏了一层**，而不是代码写错了行。**这类 bug 的特征是"看起来更连通、更像好事"，极难自查**——所以本体设计要单独拿出来评审。

## 4. TBox 与 ABox：模式与实例

这是本体论里最重要的一个区分，也是理解"本体 vs 数据"的钥匙。

| | **TBox**（Terminological Box） | **ABox**（Assertional Box） |
|---|---|---|
| 内容 | **类、关系、公理**——"这个领域的规则" | **个体、断言**——"具体有哪些事实" |
| 回答 | "**能**存在什么" | "**实际**有什么" |
| 类比 | 数据库的 **schema** | 数据库的**数据行** |
| 本项目对应 | 编→章→节→条的层级、四类边的定义与权重、53 个概念的映射规则 | 1465 个知识点、21252 条边、97 处引用 |

为什么不只是"换个说法"？因为两者的**变更成本**完全不同：

| 变更 | 影响 |
|---|---|
| 改 ABox（加一条法条） | 重跑 pipeline，重建图谱（小时级、幂等） |
| 改 TBox（改"同章"的定义、加一类边） | **所有下游都受影响**——建图、扩展、检索排序、评估基线全部要重新验证 |

**面试时这个区分很有用**：被问"你的图谱怎么扩展到新法律"，答"ABox 层面是数据驱动、零改代码；但如果新法律带来了**新的结构层级**（比如"分编"），那就是 TBox 变更，要动切分规则并重跑全量验证"——这句话能立刻体现出你分得清"数据"和"模式"。

## 5. 描述语言的三个层次

### 5.1 RDFS：最轻的表达

只提供最基础的词汇：`rdfs:Class`、`rdf:type`、`rdfs:subClassOf`、`rdfs:domain`、`rdfs:range`、`rdfs:label`。

**能表达**：分类层级、类型、关系的定义域/值域。
**不能表达**：基数、不相交、传递性、等价。

### 5.2 OWL：完整的描述逻辑

在 RDFS 之上补足表达能力：`owl:Class`、`owl:ObjectProperty`、`owl:Restriction`（`someValuesFrom` / `allValuesFrom` / 基数）、`owl:disjointWith`、`owl:TransitiveProperty`、`owl:inverseOf`、`owl:equivalentClass`、`owl:sameAs`。

**代价**：OWL 的不同子集对应不同的**计算复杂度**（从多项式到不可判定）。表达力越强，推理越贵、越难预测——这是本体的经典权衡。

### 5.3 SHACL：只管约束，不做推理

**SHACL** 是"形状"语言，用于**校验**数据是否符合约束（"每条法条必须有恰好一个章"），不做推理。工程上常和 RDFS/OWL 配合：**OWL 定义含义，SHACL 校验数据**。

### 5.4 开放世界假设（OWA）——一个反直觉的后果

RDF/OWL 采用**开放世界假设**：

> **没写下来的，不代表是假的，只代表"不知道"。**

举例：本体规定"每条法条恰好属于一个章"。某条法条在数据里没写章号——

| 假设 | 结论 |
|---|---|
| **OWA**（RDF/OWL） | "不知道它属于哪个章" → 可能**推出矛盾**（如果还断言了它属于两个不同的章） |
| **CWA**（关系库、属性图、本项目的代码） | "没有章" → 直接当成**错误**，校验失败 |

本项目实际用的是 **CWA**：切分代码要求"条必须能落在某个章上下文里"，缺了就是数据错误。**这不是缺陷，是取舍**——我们要的是"确定性地校验数据"，不是"逻辑推理"。理解 OWA 的价值在于：**当有人问"为什么不用 OWL 做推理"时，你要能说出"因为我要的是闭合校验，OWA 会让我无法判断数据缺失算不算错"。**

## 6. 推理：本体怎么"推出"新知识

本体不只是"记录"，它能**推导**出没直接写下来的事实。几条典型机制：

| 机制 | 规则 | 例子 |
|---|---|---|
| **子类继承** | `A subClassOf B`，`x type A` ⟹ `x type B` | "侵权责任编是一种编" → 对"编"的约束自动适用于它 |
| **层级传递** | `subClassOf` / `part-of` 可传递 | 第一条 part-of 第一编（经由第一章） |
| **关系传递** | `T` 是传递属性 ⟹ `a T b, b T c` ⟹ `a T c` | 引用链的两跳可达 |
| **逆关系** | `R inverseOf S` ⟹ `a R b` ⟺ `b S a` | "引用"与"被引用" |
| **等价类** | `A equivalentClass B` ⟹ 两者外延相同 | "劳动合同" ≡ "劳动契约"（术语归一） |
| **不相交检测** | `A disjointWith B`，`x` 同时属于两者 ⟹ **本体不一致** | 数据录入错误的自动发现 |
| **sameAs 合并** | 两个标识指同一实体 | 跨库合并时的实体消歧 |

### 6.1 推理的代价

推理很诱人，但工程上要付三笔账：

| 代价 | 说明 |
|---|---|
| **可解释性** | "这条关系是推理出来的"——用户问依据，你很难给出可读的路径 |
| **计算复杂度** | 表达力越强，推理越贵；全量推理在数据量大时不可接受 |
| **调试困难** | 推出错误结论时，根因往往在几条公理的交互里，而不是某一行代码 |

### 6.2 本项目的选择：用显式遍历代替推理

我们把"推理"换成了**可控的显式遍历**（BFS 扩展，4.3）：

```
不想做："用传递性公理推出所有两跳可达，再统一排序"
而是做："从种子出发，一跳一跳地走，每跳按边权与衰减算分并剪枝"
```

为什么？因为法律场景要求**每条进上下文的条文都能说清"它是怎么来的"**。BFS 的路径可以完整打进日志（`hop=2`、经由哪条边、分数多少），而推理机的推导过程对用户来说是个黑盒。

> 一句话总结这节的取舍：**本体用来"定义清楚关系"，不用来"自动发现关系"。** 前者是工程上极高的收益（规则明确、可校验、可解释），后者在这个场景里收益与代价不成比例。

## 7. 本体的价值与代价

| 有价值的地方 | 代价 |
|---|---|
| **规则显式化**：术语、层级、关系定义写在代码里可被 review | 设计成本高，且**设计错了代价很大**（1.97 万假边） |
| **可校验**：数据不符合约束时能立刻发现 | 约束越严，摄入管线的适配工作越多 |
| **可解释**：每个关系都有名字与含义，便于沟通 | 过细的本体会让简单需求变复杂 |
| **可演进**：加一层结构（如"分编"）时知道该改哪里 | 变更影响面大（TBox 变更要重跑全量验证） |
| **可复用于下游**：检索、解释、评估都建立在同一套语义上 | 团队需要理解本体才能改代码 |

### 7.1 本项目的"弱本体"

我们**没有**用 OWL、没有推理机、没有 schema 文件——但本体该做的事都做了：

| 本体构件 | 本项目对应物 | 在哪 |
|---|---|---|
| 类 | `KnowledgePoint`（唯一节点类） | `graph_store.py` |
| 层级 | 编 → 章 → 节 → 条 | `knowledge_extract.py` 的状态机 |
| 关系类型 | 4 类边 + 权重 + 方向 | `graph_build.py` |
| 概念层 | 53 个概念映射 | `concept_map.py` |
| 公理/约束 | `(编,章)` 分组键、条头正则、`CN_NUM_CHARS`、空列表不能作属性值 | 各模块 |
| 实例 | 1465 知识点 / 21252 边 | `knowledge_graph.json` |

**"弱"指的是不用推理机，不是不用本体。** 这种"代码即本体"的做法在工程上很常见：**规则的表达形式是代码，而不是 schema 文件**。代价是没有形式化语义（不能自动推理），收益是**透明、可调试、零依赖**。

## 8. 代码走读：本项目的"代码即本体"

本节讲了不少抽象概念。最后用**代码**把它们一一对上——这是本项目本体论的真正存在形式：**没有 OWL 文件，规则写在代码里**。

### 8.1 类与个体

```python
# 类：唯一的节点类型
@dataclass
class KnowledgePoint:
    id: str                  # 个体标识（KP_046）
    title: str
    part: str = ""           # 属性（编，可缺）
    part_title: str = ""
    chapter: str = ""
    chapter_title: str = ""
    clause: str = ""
    content: str = ""        # 属性（正文）
    keywords: list = field(default_factory=list)
    source: str = ""         # 属性（原文位置，供溯源）
```

**这就是 TBox 里的"类"与"属性"**——一个 dataclass 定义了一种节点能有哪些字段。注意 `part` 有默认值 `""`：这是**"编可缺"这条公理**在类型层面的表达（劳动合同法/劳动法没有编）。

### 8.2 层级公理与它的执行

```python
# 层级：编 → 章 → 节 → 条（part-of，不是 is-a）
_PART_RE    = re.compile(rf"^第([{CN_NUM_CHARS}]+)编[　\s]+(.+)$")
_CHAPTER_RE = re.compile(rf"^第([{CN_NUM_CHARS}]+)章[　\s]+(.+)$")
_ARTICLE_RE = re.compile(rf"^第([{CN_NUM_CHARS}]+)条[　\s]+(.*)$")

def handle_header(stripped, this_line) -> bool:
    stripped = stripped.translate(_KANGXI_TABLE)      # 归一化必须在校验前
    pm = _PART_RE.match(stripped)                     # ^ 锚定 = "只认行首"
    if pm:
        flush()
        part = f"第{pm.group(1)}编"
        chapter = chapter_title = section = clause = ""   # 编内章号重新起算
```

三行正则 + 一次上下文清空，就是**四条公理**的代码形式：

| 公理 | 代码 |
|---|---|
| "条头必须后跟空白" | `[　\s]+` |
| "结构标记只认行首" | `^` 锚定 |
| "编内章号重新起算" | 遇编清空 `chapter` 等 |
| "字符集要含千与零" | `CN_NUM_CHARS = "一二三四五六七八九十百千零"` |

### 8.3 关系定义

```python
_JSON_TYPE_TO_REL = {"sibling": "SIBLING", "keyword": "KEYWORD",
                     "semantic": "SEMANTIC", "crossref": "CROSSREF"}
```

**一张映射表定义了"这个领域有哪四种关系"**——这就是关系层的 TBox。配套的还有各关系的阈值与权重（`keyword_threshold=0.3`、`semantic_threshold=0.75`、`_CROSSREF_WEIGHT=1.5`），它们定义了"什么样的两条法条算有这层关系"。

### 8.4 公理与约束散落在需要它的地方

```python

by_chapter.setdefault((p.part, p.chapter), []).append(p)

# graph_store.py：Neo4j 不接受空列表作属性值 → 空关键词存 None，读回还原 []
keywords = node.get("keywords") or []

# knowledge_extract.py：章/节标题不产生知识点
if buf and chapter and clause and body:
```

注意它们**不在一个文件里**。这正是"代码即本体"的代价：**约束分散在需要它的地方**。

### 8.5 怎么防止规则漂移

规则分散会带来一个问题：**同一条规则被两处使用时，两份实现会漂移**。本项目的对策是**抽成共用函数**：

```python
# 引用解析：建边与反思候选用的是同一份实现
def crossref_map(nodes) -> dict[str, list[str]]: ...

# 调用点 1：graph_build.py 建 crossref 边
for source_id, targets in crossref_map(nodes).items(): ...
# 调用点 2：reflective_retriever.py 生成反思候选
candidate_ids = self._candidate_ids(collected, seen)   # 内部复用 crossref_map
```

**"同一份规则被两处使用 → 必须抽成一个函数"**，这是"代码即本体"能否长期成立的关键。否则迟早出现"建边认这个条号、反思认另一个"的分歧，而这种分歧**在下游表现为"偶尔少带一条法条"**，极难定位。

## 9. 本节小结

- 本体是**对领域"存在什么、怎么分类、有什么关系"的显式、形式化规范**——没有它，图只是一堆连起来的节点。
- 五个核心构件：**类、个体、属性、关系、公理**；区分属性与关系的标准是"另一端是值还是实体"。
- 两种层级**不能混**：**is-a**（子类，继承属性）与 **part-of**（部分-整体，传递但不继承）。**层级少一层就会出大错**——本项目 1.97 万条假边就是漏了"编"这一层。
- **TBox（模式：类/关系/公理）vs ABox（实例：个体/事实）**，对应数据库的 schema vs 数据行；两者的**变更成本差一个数量级**。
- 描述语言三层：**RDFS**（分类与类型）→ **OWL**（基数/不相交/传递等，表达力换取计算复杂度）→ **SHACL**（只校验不推理）。
- **开放世界假设（OWA）**是 RDF/OWL 的默认语义：没写下来 ≠ 假，只是"不知道"。本项目用**闭合世界（CWA）**做校验——这是取舍，不是缺陷。
- 推理能推出隐含知识，但代价是**可解释性、计算复杂度、调试困难**；本项目**用显式 BFS 遍历代替推理**（路径可打进日志）。
- 本项目的做法是**"弱本体"：不用推理机，但类/层级/关系/概念/约束一样不少**——只是表达形式是代码而非 schema 文件。

## 企业常见面试问答

**Q1：什么是本体？和知识图谱是什么关系？**

> 本体是对一个领域"**存在哪些东西、怎么分类、彼此有什么关系**"的显式形式化规范；知识图谱是**按这套规范构建出来的具体知识网络**。类比数据库：本体 ≈ 表结构 + 约束（schema），知识图谱 ≈ 表里的数据。所以"有没有本体"不是看有没有写 OWL 文件，而是看**节点与关系的语义有没有被明确定义**。本项目的本体是以代码形式存在的：编→章→节→条的层级在 `knowledge_extract.py` 的切分状态机里，四类关系及其权重在 `graph_build.py` 里，53 个概念在 `concept_map.py` 里，`(编,章)` 分组键这类约束散在需要它的地方。**这些规则显式、可 review、可测试——那就是本体在起作用。**

**Q2：TBox 和 ABox 有什么区别？为什么要分？**

> TBox 是"术语层"——类、关系、公理，回答"**能**存在什么"；ABox 是"断言层"——个体与事实，回答"**实际**有什么"。数据库里就是 schema 与数据行的区别。分开的意义在**变更成本**：加一条法条（ABox）只是重跑 pipeline，幂等、可回滚；而改"同章"的定义或加一类关系（TBox）会**影响全部下游**——建图、扩展、排序、评估基线都要重新验证。所以面对"怎么扩展到新法律"这类问题，正确的回答要先分清是哪种变更：如果是新增数据，零改代码；如果新法律带来了**新的结构层级**（比如民法典的"编"和"分编"），那就是 TBox 变更，必须重跑全量并重新看基线。这个区分能直接决定你对工作量的判断准不准。

**Q3：既然有 OWL，为什么不用它做推理？**

> 三个原因，按重要性排序：① **可解释性**——法律场景里每一条进上下文的条文都要能说清"它是怎么来的"。BFS 遍历能给出完整路径（从哪个种子、走哪条边、第几跳、分数多少，全都进日志）；而推理机给出的结论是"根据若干公理推导得出"，对用户和排障的人来说是黑盒。② **确定性与可控性**——OWL 表达力越强计算复杂度越高（部分子集甚至不可判定），而我们的扩展需要**可控的预算**（每跳剪枝、跳数上限、超时即停），这些在图遍历里都是一行参数，在推理机里就没那么好控。③ **成本与收益不匹配**——我们真正需要的"推理"其实就是多跳可达，而这件事用 30 行 BFS 就做完了，还完全透明。**所以不是 OWL 不好，是这个场景里"显式遍历"的性价比明显更高。**

**Q4：开放世界假设对工程有什么影响？**

> 影响很实际。OWA 的语义是"没写下来的不等于假的，只是不知道"——这在**数据校验**场景里会变得别扭：本体说"每条法条恰好属于一个章"，某条法条没写章号时，OWA 下你不能断定它错，只能说"信息缺失"，甚至可能在别处推出矛盾。而工程上我们想要的是"缺了就报错"。本项目用的是**闭合世界假设**（CWA）：切分代码要求每条法条必须落在某个章上下文里，缺了就是 bug；Neo4j 的属性也不接受空列表（3.5）——这些"缺了就是错"的判断，都是 CWA 的体现。所以我的结论是：**如果你要的是"逻辑推理与知识融合"，OWA 是必要的；如果你要的是"数据质量校验"，CWA 更实用。** 选之前先想清楚自己是要"推理"还是要"校验"。
