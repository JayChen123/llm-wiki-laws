# 2.1 知识图谱是什么 —— 从"关系"说起

> 定位：在进入本项目之前，先把"知识图谱"这个词讲清楚——它到底存什么、和数据库/向量库有什么本质区别。

本节目标：

1. 用"三元组"这个最小单元理解知识图谱存的是什么；
2. 分清图的两个基本要素（节点、边）以及边的四个修饰（方向、类型、权重、属性）；
3. 讲清知识图谱与**关系数据库**、**向量库**的定位差异；
4. 认识两种主流形态（RDF 三元组 vs 属性图）以及本项目为什么选属性图。

---

## 1. 一句话：知识图谱是把"关系"变成一等公民

传统做法里，数据是**表格**：

| id | 法条 | 内容 |
|---|---|---|
| KP_046 | 劳动合同法第四十六条 | 用人单位应当向劳动者支付经济补偿的情形… |
| KP_038 | 劳动合同法第三十八条 | 劳动者可以解除劳动合同的情形… |

"46 条引用了 38 条"这个**关系**，在表格里要么塞进一个字段（`引用的条号 = 38`），要么单开一张关联表（`(46, 38)`）。无论哪种，**关系都是"存完数据之后再想办法表达的东西"**。

知识图谱换了个角度：**关系本身就是数据**。

```
(KP_046) ──[CROSSREF 权重 1.5]──► (KP_038)
   实体            关系               实体
```

这个三元组 `(主体, 关系, 客体)` 就是知识图谱的最小单元。

---

## 2. 图的两个要素：节点与边

### 2.1 节点（Node / 顶点）

节点代表**实体**——一个可以独立指称的东西。在本项目里，节点就是**一个知识点（一条法条）**：

```
节点 { id: "KP_046", title: "第四章·第四十六条",
       clause: "第四十六条", content: "...", source: "..." }
```

节点可以带：
- **标签（Label）**：节点属于哪个类别（本项目只有一种：`KnowledgePoint`）——类别是**本体**的内容，2.2 讲；
- **属性（Property）**：键值对（`title` / `content` / `seq`…）。

### 2.2 边（Edge / 关系 / 弧）

边代表**两个实体之间的关联**。它比节点多几个修饰维度，这四个维度都要想清楚：

| 修饰 | 问题 | 本项目的取值 |
|---|---|---|
| **方向** | 关系是对称的还是有向的？ | `:CROSSREF` **有向**（引用方→被引方）；其余三类无向 |
| **类型** | 是哪一种关系？ | 四种：`:SIBLING` / `:KEYWORD` / `:SEMANTIC` / `:CROSSREF` |
| **权重** | 这条关系有多强？ | `sibling` 1.0、`crossref` **1.5**、`keyword`/`semantic` 用相似度值 |
| **属性** | 关系本身还要携带信息吗？ | 目前只存权重；如需可加"引用出现的次数""引用的原句"等 |

> **方向这一维最容易被忽略。** 本项目的 `:CROSSREF` 如果不区分方向，"沿引用链往下找"就没法做——这一个小决定直接影响了能不能做有向遍历（3.5 会讲它在技术上怎么实现）。

### 2.3 一个更小的例子

```
                 ┌──────────────┐
                 │  KP_046      │  经济补偿情形
                 └──────┬───────┘
        CROSSREF(1.5)   │   SIBLING(1.0)
          ┌─────────────┴─────────────┐
          ▼                           ▼
   ┌──────────────┐           ┌──────────────┐
   │  KP_038      │           │  KP_047      │
   │  劳动者解除权  │           │  同章条文      │
   └──────────────┘           └──────────────┘
```

读法：46 条在**引用**38 条（有向、权重最高），同时它在**结构上**与 47 条属于同一章（无向、权重 1.0）。

## 3. 知识图谱 vs 关系库 vs 向量库

这三者常被混为一谈，因为都能"存数据、都能查"。差别在**查询的形态**：

| | 关系数据库 | 向量库 | 知识图谱 |
|---|---|---|---|
| 存什么 | 行与列 | 高维向量 | 节点与边 |
| 擅长的问题 | "满足条件的行"（精确过滤、聚合） | "和它相似的东西"（近邻） | "和它**相连**的东西"（关系遍历） |
| 典型查询 | `WHERE salary > 10000` | `top-5 最相似的向量` | "从 A 出发，沿引用走 3 跳能到哪" |
| 多跳代价 | 每多一跳多一次 JOIN，跳到 3 跳以上很别扭 | 不支持 | **天然支持**（`*1..3`） |
| 可解释性 | 高（就是筛选条件） | 低（相似度是个数字） | 高（路径可打印出来） |

**关键区别在多跳。** 用关系库表达"沿引用走 3 跳"，就是三张自连接（或递归 CTE），SQL 会迅速变得难以阅读和维护；而图查询里就是一句 `-[:CROSSREF*1..3]->`。

> 但也要说清**图谱不擅长什么**：聚合统计（"平均条文字数"）、高并发精确更新、模糊匹配。**没有一个存储是万能的**，选型看"你最常问哪种问题"（1.2 的技术选型表就是这个思路）。

## 4. 两种主流形态：RDF 三元组 vs 属性图

### 4.1 RDF：一切皆三元组

**RDF（Resource Description Framework）** 是 W3C 标准，把一切都写成三元组：

```
<劳动合同法第四十六条> <引用> <劳动合同法第三十八条> .
<劳动合同法第四十六条> <所属章> "第四章" .
```

特点：

| 优点 | 代价 |
|---|---|
| 全球统一标识（IRI）→ **跨库可合并** | 每个属性都是一条三元组 → 节点属性多时"边"会爆炸 |
| 标准化的本体描述（RDFS/OWL，2.2 讲） | 查询要写 SPARQL，学习曲线陡 |
| 图灵完备的推理生态 | 属性的**类型**要靠 schema 约定，不像属性图那样原生 |

### 4.2 属性图：节点和边都能挂属性

**属性图（Property Graph）** 是工程界更常见的选择（Neo4j 就是它）：

```
(KP_046:KnowledgePoint {title: "...", seq: 46})
   -[:CROSSREF {weight: 1.5}]->
(KP_038:KnowledgePoint {title: "..."})
```

特点：

| 优点 | 代价 |
|---|---|
| **属性直接挂在节点/边上**，写起来直观 | 没有跨库合并的标准标识体系 |
| 查询语言（Cypher）**可读性好**，接近画图 | 本体/推理能力弱于 RDF 生态 |
| 工程生态成熟（驱动、可视化、运维） | — |

### 4.3 本项目选属性图

理由很直接：

| 理由 | 说明 |
|---|---|
| 我们的图谱**就是一个库内部的**，不需要跨库合并 | 放弃 IRI 统一标识的收益为零 |
| 节点属性多（title/clause/content/keywords/source…） | 属性图能直接挂；RDF 要炸成一堆三元组 |
| 需要**人可读**的查询与调试 | Cypher 比 SPARQL 更好读，排障时能直接贴给同事看 |
| 需要**有向遍历** | 属性图的关系原生带方向 |
| 权威源是 JSON，图库只是副本（1.2） | 不追求"图库即唯一真相"，要的是**查询能力** |

> 一句话：**RDF 适合"知识要在组织之间共享与推理"，属性图适合"工程上要快速构建与查询一张图"。** 本项目属于后者。

## 5. 知识图谱的"知识"体现在哪

最后回到一个容易被忽略的问题：**同样的节点和边，凭什么叫"知识"图谱？**

差别在于**节点和边的语义是被明确定义的**：

| 层面 | 内容 | 谁定义 |
|---|---|---|
| **类**（有哪些种类的东西） | `KnowledgePoint` | 本体（2.2） |
| **关系类型**（有哪几种关系） | 4 类边，各自什么含义、权重多少 | 本体 + 建图规则（3.2） |
| **层级**（怎么分类） | 编 → 章 → 节 → 条 | 本体（2.3） |
| **实例**（具体有哪些） | 1465 个知识点、21252 条边 | 摄入管线（第三章） |

**没有前三层，就只是一堆连起来的节点，不是知识图谱。** 这也是为什么本课程要在讲实现之前，先专门讲一节本体论（2.2）——它是知识图谱真正的"骨架"。

## 6. 本节小结

- 知识图谱的最小单元是**三元组** `(主体, 关系, 客体)`：**关系本身就是数据**，而不是"存完数据之后再想办法表达的东西"。
- 图的两个要素：**节点**（实体，带标签与属性）与**边**；边有四个要交代清楚的维度——**方向、类型、权重、属性**，其中方向最容易被忽略。
- 与关系库/向量库的分水岭在**多跳**：图查询 `-[:CROSSREF*1..3]->` 天然支持关系遍历，关系库要多次 JOIN，向量库则不支持。但图谱不擅长聚合统计与模糊匹配——**没有万能的存储**。
- 两种形态：**RDF**（统一标识、标准化本体与推理，但属性多了会"边爆炸"）与**属性图**（属性直接挂节点/边、查询语言好读）。本项目选**属性图**，因为我们不需要跨库合并，需要的是人可读的查询与有向遍历。
- "知识"体现在**类、关系类型、层级、实例**四层语义被明确定义——没有前三层，就只是一堆连起来的节点（这件事 2.2 专门讲）。

## 企业常见面试问答

**Q1：知识图谱和普通图数据库有什么区别？**

> 图数据库是**存储与查询技术**，知识图谱是**一种知识表示方式**。你可以用图数据库存一个社交网络（谁是誰的好友）——那是图，但不一定是"知识图谱"；区别在于知识图谱的节点与边**有明确定义的语义**：类是什么、关系有哪几种、层级的分类依据是什么（这套东西叫**本体**，见 2.2）。本项目的例子很典型：同样是"46 条和 38 条连了一条边"，我们还必须说清楚这四种边各自的含义与权重（结构/关键词/语义/引用），才能让这条边在检索时**可用、可解释**。所以我的回答是：**图数据库提供了"存关系"的能力，本体提供了"关系是什么意思"的规范，两者合起来才是知识图谱。**

**Q2：为什么不直接用关系数据库存这些边？**

> 短链路上可以，长了就不行。用关系库存边很自然（一张 `edges(source, target, type, weight)` 表就够），但**查询形态会立刻变得别扭**：问"沿引用走 3 跳能到哪些条文"，在 SQL 里是三张自连接或递归 CTE，写出来长、读起来费力、加个"排除已访问节点""按路径权重剪枝"就更复杂。而图库里就是 `MATCH (a)-[:CROSSREF*1..3]->(b)`。更关键的是**维护性**：多跳查询在业务里会不断加条件（只走某类边、限权重、带跳数返回），图查询语言天然表达这些，SQL 每次都要重写。反过来，如果我的需求只是"按条件筛行 + 统计"，那关系库是更好的选择——**选型看查询形态，不看数据像什么。**

**Q3：RDF 和属性图怎么选？**

> 三个判据：① **要不要跨组织/跨库合并知识**？要 → RDF（IRI 统一标识是它的核心价值）；② **属性多不多、要不要快速落地**？属性多 → 属性图（RDF 里每个属性都是一条三元组，会"边爆炸"，且取值类型要靠 schema 约定）；③ **要不要自动推理**（比如"本体里声明 A 是 B 的子类，那么查 B 就自动包含 A"）？要 → RDF + OWL 生态更成熟。本项目三条都落在属性图这边：图谱只在自家库内、节点属性有六七个、推理需求其实就是"多跳遍历"（用 BFS 自己实现，透明可控）。所以选 Neo4j 的属性图 + Cypher。

**Q4：你这算"真"的知识图谱吗？**

> 算，但属于**轻量/弱本体**的那一类——这需要坦诚说明。完整的知识图谱通常包含：实体、关系、**本体（类与关系的规范）**、以及基于本体的推理。我们有前三者：实体是 1465 个知识点，关系是四类带权重与方向的边，本体是"编→章→节→条"的层级 + 四类关系的定义 + 53 个概念的术语映射（2.3）。**没有做的是"自动推理"**——我们不用 OWL 推理机去推导隐含关系，而是用 BFS 扩展显式地"走"图谱。这不是能力不足，而是取舍：法律场景要求每条结论可回溯，**"推理出的隐含关系"不如"走出来的路径"好解释**。所以准确的说法是：**这是一张有明确本体定义、但推理靠显式遍历的工程化知识图谱。**
