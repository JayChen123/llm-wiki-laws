# 2.3 法律本体设计与本项目实践

> 定位：把 2.2 的本体构件落到**法律领域**，然后逐条交代本项目的本体是怎么设计的、为什么这么设计、以及设计错了会怎样。

本节目标：

1. 认识法律领域天然的知识结构，以及它为什么比一般领域更适合做知识图谱；
2. 掌握本项目的**本体全貌**（类 / 层级 / 关系 / 概念 / 公理）；
3. 讲清三个关键设计决定的理由：为什么"条"是最小实体、为什么是这四类边、为什么概念不进图谱当节点；
4. 复盘本体的一次**真实演进**（v1.0 没有"编"→ v2.0 加上），并给出本体自查清单。

---

## 1. 法律领域天然的知识结构

法律文本的特殊性在于：**它的结构是显式写在文本里的，而且层级是权威的**。

```
中华人民共和国民法典                    ← 法律（Statute）
├── 第一编 总则                        ← 编（Part）
│   ├── 第一章 基本规定                 ← 章（Chapter）
│   │   ├── 第一节 …                   ← 节（Section）
│   │   │   └── 第一条 …               ← 条（Article）
│   └── 第二章 自然人
└── 第二编 物权
```

这个层级不是我们的发明，而是法律文本**自带**的——这一点非常关键：**它意味着"本体"可以从文档里确定性地抽出来，而不是靠人去归纳。** 1.1 讲的"llm-wiki 只适用于结构化强的领域文档"，法律就是最好的例子。

法律领域还有两类同样重要的知识：

| 类型 | 形态 | 本项目如何处理 |
|---|---|---|
| **引用关系** | 条文正文里写"依照本法第 X 条" | 抽成 `crossref` 边（3.2） |
| **概念与术语** | "试用期""竞业限制""离婚冷静期" | 抽成概念映射表（3.2） |
| （进阶）修正/废止关系 | "本法自 X 日起施行，原《Y 法》同时废止" | **本项目未做**（如实说明） |

> 最后一行的"未做"也值得讲：**并不是所有法律知识都要进图谱**。修正/废止关系需要跨法律的版本管理，收益（对问答帮助有限）与成本（要引入时间维度）不成比例。**知道该不做什么，也是本体设计的一部分。**

## 2. 本项目的本体全貌

### 2.1 类（只有一个）

```
类：KnowledgePoint（知识点）
```

**只用一个类**是刻意的——本项目的图谱是"同构图"（所有节点同一类型），这让遍历与评分逻辑简单得多（不用为每种节点类型写分支）。代价是**丢了"节点类型"这层语义**：编/章/节不是节点，而是节点上的**属性**。

> 这是一个真实的取舍点：**"编/章/节"该做成节点还是属性？**
> - 做成**节点**（异构图）：可以表达"多个条文共享同一个章"这种结构，也能给章挂属性（如章的标题）；
> - 做成**属性**（本项目）：遍历简单、无需为不同节点类型分别处理。
>
> 我们选属性，是因为**"同章"这个关系已经被 `sibling` 边显式表达了**——多条边代替了"共享父节点"的作用。这是一个可以拿去讨论的设计题。

### 2.2 层级（分类学：is-a）

```
条（Article）──part-of──► 节（Section）──part-of──► 章（Chapter）──part-of──► 编（Part）
```

注意这里用的是 **part-of（组成）** 而不是 is-a（分类）：第一条**是**第一章的一部分，而**不是**一种章（2.2 的 3.1/3.2 讲了这两者不能混）。它的三个性质直接决定了工程实现：

| 性质 | 工程后果 |
|---|---|
| **传递** | "条属于编"可以由"条属于章、章属于编"推出——但我们**不推出**，而是在切分时直接记录 `part` |
| **不继承属性** | "第一章有章号"**不意味着**"第一条有章号"——所以知识点自己的 `clause` 与 `chapter` 是两回事 |
| **层级可能缺失** | 劳动合同法/劳动法**没有"编"**（`part` 为空），只有民法典有 → 分组键必须容忍空值 |

### 2.3 关系（四类，各自表达一种"相关性"）

| 关系 | 语义 | 对应本体的什么 |
|---|---|---|
| `:SIBLING` | 同 (编, 章) 的结构相关 | **结构公理**：同章 ⟺ 编与章都相同 |
| `:KEYWORD` | 词面相近（Jaccard ≥ 0.3） | 主题相关性 |
| `:SEMANTIC` | 语义相近（余弦 ≥ 0.75） | 语义相关性 |
| `:CROSSREF` | 法条互相引用（**有向**、权重 1.5） | **领域关系**：引用（cites） |

前两类是"统计相关性"，第三类是"文本语义相关性"，第四类是**领域定义的确定性关系**。把它们**放在同一张图里但保留类型**，是为了下游能区别对待（比如扩展时 `crossref` 权重更高、反思时只沿 `crossref` 走）。

### 2.4 概念层（术语表）

```
概念"试用期" ──对应──► [劳动合同法 第十九条, ...]
概念"加班费" ──对应──► [劳动法 第四十四条]
```

**53 个概念，存在 `concept_map.py` 里，不进图谱当节点。** 为什么？（见第 3.3 节的讨论）

### 2.5 公理与约束（散落在代码里）

| 公理/约束 | 表达形式 | 位置 |
|---|---|---|
| 条头必须"第X条"+空白 | 正则 `^第([…]+)条[　\s]+(.*)$` | `knowledge_extract.py` |
| 条号字符集必须含"千""零" | 常量 `CN_NUM_CHARS` | 同上 |
| "分编"只作边界、不成点 | `_SUBPART_RE` 单独处理 | 同上 |
| 同章 ⟺ (编, 章) 相同 | 分组键 `(part, chapter)` | `graph_build.py` / `wiki_writer.py` |
| 引用只在同法内 | `crossref_map()` 按文档隔离 | `graph_build.py` |
| 关键词为空要存 `None` | 写入前转换 | `graph_store.py` |
| 每条法条恰好属于一个章 | 状态机保证 + `flush()` 要求 `clause` 非空 | `knowledge_extract.py` |

**这张表就是本项目的 TBox**——它不是 schema 文件，而是**代码里的规则集合**。

## 3. 三个关键设计决定

### 3.1 为什么"条"是最小实体？

法律文本从大到小有：法律 → 编 → 章 → 节 → 条 → 款 → 项 → 目。我们停在**条**。

| 候选粒度 | 优点 | 缺点 |
|---|---|---|
| 章/节 | 上下文完整 | **太粗**——一章几十条，检索命中了也定位不到具体依据 |
| **条** | **语义完整、可检索、可引用** | 长条文中的具体款项无法单独被命中 |
| 款/项 | 最细 | **失去自足性**——"（一）项"脱离条文无法理解，引用也没法说"依据第 X 条第（一）项" |

决定性判据是**"这一单元能不能被独立引用"**：法律实践里引用依据的粒度就是"《X 法》第 Y 条"，所以**条是天然的自足单元**。这款粒度还有一个附带好处：**一条法条一个知识点，编号与条号一一对应**，引用溯源与评估标注都变得可直接核验。

### 3.2 为什么是这四类边？

因为"两条法条相关"这件事，在法律问答里有**四种不同的成因**，各自要用不同手段去发现：

| 相关性成因 | 发现手段 | 边类型 |
|---|---|---|
| 它们在同一章（结构上就该一起看） | 读结构 | `:SIBLING` |
| 它们用词相近（讨论同一主题） | 关键词 Jaccard | `:KEYWORD` |
| 它们（换了说法也）语义相近 | bge-m3 余弦 | `:SEMANTIC` |
| 一条明文引用了另一条 | 解析正文 | `:CROSSREF` |

**这四类不能合并成一类**，因为它们的可靠性、可解释性与用途都不同：

| | 可靠性 | 可解释性 | 权重 |
|---|---|---|---|
| 结构 | 确定 | "同一章" | 1.0 |
| 引用 | 确定 | "46 条写明引用 38 条" | **1.5**（最高） |
| 关键词/语义 | 统计（有阈值） | "词面重合 0.35" | 按相似度 |

**把确定的与统计的分开**，是这个设计最重要的一条：确定关系可以当作"事实"用（甚至能做有向遍历），统计关系只能当作"线索"用（靠阈值与权重控制噪音）。

### 3.3 为什么概念不进图谱当节点？

概念（试用期、加班费…）看起来很像节点："概念 ——对应——► 条文"。我们**没这么做**，理由三条：

| 理由 | 说明 |
|---|---|
| **会让图变成异构图** | 遍历与评分就要为"概念节点"写分支；扩展时概念节点会互相连接形成噪音路径 |
| **概念的作用是"改检索词"，不是"被遍历"** | 概念的价值在**摄入期**把查询词注入知识点关键词（影响 BM25 与语义编码），这个过程不需要图 |
| **图谱要干净** | 图里只有一种节点、语义统一，`sibling`/`crossref` 这些公理才成立（概念没有"编/章"，也没有"引用"） |

**如果概念进了图会怎样？** 最直接的问题：`sibling` 的定义是"同 (编, 章)"——概念节点没有编章，这条公理对它无意义；`crossref` 的定义是"条文正文里的引用"——概念没有正文。**引入一个不符合既有公理的节点类型，会让所有公理都要加"除非是概念"的例外**。这就是本体设计的典型症状：**新类型不该硬塞进旧公理体系。**

> 对比一下另一种做法：如果把概念做成节点，通常要**同时**引入 `:MENTIONS`（条文提到概念）这类新关系，并为概念节点设计另一套遍历规则。那是"更大的本体"，我们判断收益不抵复杂度。

## 4. 法律领域的四个坑（本体视角）

| 坑 | 本体层面的原因 | 后果 |
|---|---|---|
| **多法同条号** | 条号只在"法律"这个层级内唯一，不是全局标识 | 检索/生成时张冠李戴（合同法的 85 条 vs 劳动法的 85 条） |
| **编/分编** | 民法典的章号**在编内**重新起算；"分编"是编与章之间的**额外一层** | 分组键漏 `part` → 1.97 万条假边；"分编"被当正文 → 污染 6 条条文 |
| **千位条号** | 中文数字字符集不全 → 条号不连续 | 民法典从第 1000 条起整段漏切（丢 261 条） |
| **跨法不引用** | 一部法律的条文不会引用另一部（文本上不存在） | 硬连会产生"看起来像结构知识"的假关系 |

**这四条有一个共同的本质**：它们都是**"我 assumed 的结构规律其实不成立"**。

- "条号唯一"假设不成立（要带法律名）；
- "章号在本法内唯一"假设不成立（要带编）；
- "中文数字就那十个字"假设不成立（要含千/零）；
- "引用可以跨法"假设不成立（要按文档隔离）。

> 做本体设计时，最该问的问题就是：**"我这条规则，在所有已知文档上都成立吗？换一部法律还成立吗？"** 这四个坑如果只拿劳动合同法开发，一个都不会暴露。

## 5. 本体的一次真实演进：v1.0 没有"编"

### 5.1 演进过程

| 版本 | 层级 | 当时的"章号唯一"假设 |
|---|---|---|
| v1.0 | 章 → 节 → 条 | 成立（劳动合同法、劳动法都没有编） |
| 加入民法典后 | **编 → 章 → 节 → 条** | **不成立**（7 编各自从第一章起算） |

加入民法典时，代码沿用了 v1.0 的假设（只按章号分组），于是：

```
第一编 总则   第一章  ┐
第二编 物权   第一章  ├─ 被当成"同一个第一章"，两两连边
第三编 合同   第一章  ┘
──────────────────────────────────────
结果：约 1.97 万条假 sibling 边
     全库边数 21252 → 虚高到 40992
```

### 5.2 修复与教训

```python
# 修法：分组键从"章号"升级为二元组 (编, 章)
key = (point.part, point.chapter)
```

三条教训：

| 教训 | 说明 |
|---|---|
| **本体变更会被"数据扩展"触发** | 不是"想改本体"，而是"新数据让旧假设失效"——所以要为新文档类型主动检查本体假设 |
| **"更连通"不一定是好事** | 假边让图谱看起来更丰富，实际是把扩展预算浪费在无关条文上 |
| **这类 bug 不报错** | 只有人会怀疑"边数怎么突然大了一倍"——所以**边的分类统计要能一眼看到**（`sibling 15306 / semantic 11720 / keyword 3446 / crossref 97`） |

## 6. 本体设计自查清单

给一个新领域做图谱时，按顺序问自己这 6 个问题：

1. **最小实体是什么？**（本项目：条）——判据是"能不能被独立引用"。
2. **领域自带的层级有哪些层？**（编→章→节→条）——**一层都不能少**，少一层就并团。
3. **哪些层级可能缺失？**（劳动法没有编）——分组键要容忍空值。
4. **有哪几类"相关性"？各自的可靠性如何？**——确定关系（结构/引用）与统计关系（关键词/语义）**必须分开**。
5. **标识是否全局唯一？**（条号不是）——不唯一就要加限定（法律名）。
6. **有哪些"只在一个文档上成立"的假设？**——换一部法律就失效的规则，必须显式检查。

> 这 6 问基本能提前挡掉前面讲的所有坑。**它们不需要 OWL、不需要推理机——只需要在动手写建图代码前，把领域结构想清楚一遍。**

## 7. 本节小结

- 法律文本**自带显式层级**（编→章→节→条），所以本体可以**确定性抽取**，不必靠人工归纳——这是它特别适合做知识图谱的原因。
- 本项目的本体：**1 个类**（`KnowledgePoint`）、**part-of 层级**（编→章→节→条，且可缺"编"）、**4 类关系**（结构/关键词/语义/引用）、**概念层**（53 个术语，不进图谱）、**公理散在代码里**（`(编,章)` 分组、条头正则、字符集、空列表约束…）。
- 三个关键决定：**最小实体选"条"**（判据是可被独立引用）；**四类边分开**（确定关系 vs 统计关系不能混）；**概念不做节点**（会让图异构、且概念没有编章与正文，硬塞会破坏既有公理）。
- 法律领域四个坑的本质都是**"以为是普遍规律，其实只在部分文档上成立"**：条号不全局唯一、章号在编内重算、中文数字要看千零、引用不跨法。
- 本体**会因数据扩展而失效**：v1.0 的"章号唯一"假设在民法典上崩了，代价是 1.97 万条假边。**新文档类型进来时，要主动重审本体假设。**
- 设计前问自己 6 个问题（最小实体/层级有哪几层/哪层可能缺/有哪几类相关性/标识是否唯一/哪些假设只在单文档成立）——**不需要 OWL 也能挡掉绝大多数坑。**

## 企业常见面试问答

**Q1：你的知识图谱里本体是怎么定义的？**

> 我们的本体**以代码形式存在**，没有单独的 OWL 文件。具体分五块：① **类**——只有 `KnowledgePoint` 一种节点；② **层级**——编→章→节→条，是 part-of 关系（不是 is-a），在切分状态机里强制；③ **关系**——四类边：`sibling`（同 (编,章)，权重 1.0）、`keyword`（Jaccard ≥ 0.3）、`semantic`（余弦 ≥ 0.75）、`crossref`（同法内引用，有向，权重 1.5）；④ **概念层**——53 个概念到条文的映射，用于检索词增强，**不进图谱当节点**；⑤ **公理与约束**——比如"同章 ⟺ 编与章都相同""条头后必须跟空白""条号字符集必须含千和零"。**为什么不做成 OWL**？因为我们需要的不是自动推理，而是"规则显式、可 review、可测试、可解释"——而代码形式恰好满足这四点，且零额外依赖。

**Q2：为什么最小单位是"条"，不是"章"或"款"？**

> 判据是**"能不能被独立引用"**。法律实践里引用依据的粒度就是"《X 法》第 Y 条"——章太粗（几十条一起给，定位不到具体依据），款/项太细（"（一）项"脱离条文无法理解，也没法规范地引用）。所以"条"是天然的**自足单元**。这个选择还带来两个工程收益：① 知识点编号与条号一一对应，**引用溯源可直接核验**（生成时标题带法律名与条号，回答末尾的引用能对回原文）；② 评估标注、recall@k 这类指标可以按"条"精确计算，不需要处理"命中半条法条"的模糊情况。反过来，代价是**长条文里的具体款项无法被单独命中**——这是已知的粒度取舍。

**Q3：新加一部法律，你的本体要动吗？**

> 要分两种情况，这也是 TBox / ABox 的区分（2.2）。**如果是纯新增实例**（比如再来一部结构相同的法规，也是章→节→条），那是 ABox 变更——零改代码，丢进 `data/src/` 重跑 pipeline 就并入了，知识点会追加在末尾编号，历史基线仍可比。**如果新法律带来了新的结构层级**（民法典就是这种：多了"编"，而且编内的章号重新起算），那是 TBox 变更——要改切分规则与分组键，并且**必须重跑全量 + 重新看基线**。所以我的判断流程是：先看新文档的结构层级与标识规则跟现有假设是否一致（对照 2.3 的 6 问清单），一致就零改代码，不一致就把它当本体变更来对待，而不是"改个 bug"。

**Q4：为什么不把"法律概念"也建成节点？**

> 三条理由。① **会让图变成异构图**：节点类型一多，遍历与评分就要为每种类型写分支，扩展时概念节点之间还会连成噪音路径。② **概念的价值不在"被遍历"**：概念的作用是**改检索词**——把"加班费"这类口语词注入法条的关键词字段，从而影响 BM25 与语义编码。这件事在**摄入期**就做完了，运行时不需要图查询。③ **最根本的：概念不符合既有公理**。`sibling` 的定义是"同 (编, 章)"，`crossref` 的定义是"正文里的引用"——概念节点既没有编章、也没有正文，硬塞进来会让这两条公理都要加"除非是概念节点"的例外。当一条公理需要不断加例外时，通常说明**这个东西不该放进这套公理体系**，而应该用另一个机制（这里是关键词增强）去承载。
