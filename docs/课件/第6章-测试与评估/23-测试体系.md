# 6.1 测试体系 —— 217 项全离线测试怎么守住这套系统

> 定位：这一节不讲"怎么写测试"，讲的是**这套系统的哪些地方最容易悄悄坏掉**，以及测试是怎么把那些"静默失败"变成"跑一次就报错"的。

本节目标：

1. 说清"测试必须全离线"的工程理由与实现手段；
2. 认识假实现清单（假编码器 / 假向量库 / 假 driver / mock LLM）；
3. 理解几类**只能靠测试挡住**的静默故障；
4. 掌握跑测试与排错的正确姿势。

---

## 1. 为什么测试必须全离线

这套系统的真实依赖相当"重"：

| 依赖 | 代价 |
|---|---|
| bge-m3 | 2.2GB 模型，首次加载慢 |
| Milvus / MySQL / Neo4j | 三个容器要起 |
| DashScope（qwen-max / qwen-turbo） | 要 API Key，要花钱，有网络抖动 |

如果测试依赖这些，结果必然是**开发者本地不想跑**——而"不想跑"的测试等于没有测试。所以本项目定了一条硬规则：

> **tests/ 下 217 项测试全部离线**：不加载 bge-m3、不连 Milvus/MySQL/Neo4j、不调 LLM。

跑法也有讲究：

```bash
uv run python -m pytest tests/ -v        # ✅ 用 python -m，把项目根加入 sys.path
pytest tests/ -v                         # ❌ 裸 pytest 可能因 app 包不在路径而失败
```

## 2. 假实现清单

离线的手段是**注入假实现**，而且每类依赖都有对应的"替身"：

| 替身 | 位置 | 替掉什么 |
|---|---|---|
| `StubEmbedder` | `test_retrieval.py` | bge-m3 编码器 |
| `FakeEmbedder` | `test_graph_build.py` | 同上（构建语义边用） |
| `StubVectorStore` | `test_retrieval.py` | Milvus 向量检索 |
| `FakeMilvusClient` | `test_milvus_store.py` | Milvus 客户端（含**可见性延迟**模拟） |
| 假 Neo4j driver | `test_graph_store.py` | 图数据库（验证 Cypher 与绑定参数） |
| mock LLM | `test_intent.py` / `test_reflector.py` / `test_generation.py` | qwen-max / qwen-turbo |
| `NullLogger` 夹具 | `tests/conftest.py` | 真实日志器（**防测试写生产日志**） |
| 假记忆后端 | `test_api_*.py` 的 `dependency_overrides` | MySQL / 长期记忆向量库 |

> 注入点的设计是前提：`MilvusVectorStore(client=None)`、`kb.load(store=None)`、`write_wiki(..., concepts_dir=...)` 都是**为了可注入而留的参数**。**可测试性要在设计时就留口子**，事后想注入往往要重构。

## 3. 只能靠测试挡住的三类静默故障

这是本节的核心。"静默故障"指的是**不报错、只让结果悄悄变差**的问题——它们靠人工使用几乎发现不了。

### 3.1 顺序类：Milvus 的 `flush` 与"清理陈旧主键"

回顾 3.4 的顺序要求：

```
① flush 并取出旧主键集合  →  ② upsert  →  ③ flush  →  ④ delete 陈旧主键
```

**写反了会怎样？** 第 ① 步取到空集，第 ④ 步"清理"无事可做——**静默失效**，集合里长期残留陈旧主键。

**测试怎么挡？** 假 Milvus client 必须**忠实模拟"未 flush 查不到"**（带可见性延迟）。如果假 client 让写入立即可见，这个顺序错误在单测里就会**蒙混过关**。

```python
# test_milvus_store.py：用带可见性延迟的假 client 卡住这个顺序
```

> 这条经验值得背下来：**假实现不能比真实实现"更好用"**。假 client 越顺手，越容易掩盖真实实现里的顺序约束。

### 3.2 隔离类：测试不能写生产产物

曾经出现过这样的事故：

> API 层用的是**模块级真实 logger**，`tests/conftest.py` 没替换它 → **跑一次 pytest 就往 `logs/qa.log` 写了几十条假问答事件**。
> 后果：污染 **297 条**、占日志 **69%**——既毁审计，也毁日志分析（`analyze_logs` 的统计全被带偏）。

修法：夹具注入 `NullLogger`，并加一条回归测试卡住它（`test_api_tests_do_not_write_production_log`）。

**同一个教训在别的模块上重复出现过**：

| 模块 | 症状 | 修法 |
|---|---|---|
| 日志 | 测试往 `logs/qa.log` 写假事件 | 注入 `NullLogger` + 回归测试 |
| Wiki | `write_wiki` 会写**真实 `wiki/`** | 目录参数可注入，测试传 `tmp_path` |

> 通用原则：**任何"会写磁盘"的函数都要能指定输出位置**，否则测试一定会污染生产产物。这是设计问题，不是"记得在测试里 mock"的问题。

### 3.3 用户隔离类：记忆绝不能跨用户

第 5.1 节讲过那条红线，测试是它唯一的守卫：

| 测试 | 断言什么 |
|---|---|
| `test_long_term.py` | 用户隔离（`test_alice / test_bob` 交叉验证）、画像+历史召回、注入段落标注"不得作为法律依据" |
| `test_mysql_store.py` | **生成的 SQL 与绑定参数**——`user_id` 过滤真的进了查询、排序 LIMIT 正确、画像去重、只吞唯一冲突 |
| `test_api_sessions.py` | 越权访问一律 **404**（读/删/提问都不放行）、删会话连带清长期记忆 |

**抓到过真实 bug**：SQLite 降级后端在 `facts()` 里漏了 `user_id` 过滤 → **画像跨用户泄漏**，正是 `test_alice/bob` 抓到的（这次事故直接导致我们删掉了降级路径）。

> 注意 `test_mysql_store.py` 的做法特别值得学：它**不连数据库**，而是**断言生成的 SQL 与绑定参数**。"过滤条件有没有真的进 SQL"这件事，不需要真库就能验证。

## 4. "配置项到底有没有传下去"

第 4.3 节讲过的坑，在测试这一节要给它一个位置：

```python
# kb.py 构造 HybridRetriever 时曾漏传 EXPAND_K / EXPAND_HOPS / EXPAND_DECAY
# → 长期沿用默认 expand_k=3，而 config 与文档都写着 5
```

| 特征 | 说明 |
|---|---|
| 会不会报错 | **不会** |
| 表现 | 只是扩展规模小了一截 |
| 怎么发现的 | 日志里 `graph_expanded` **恒为 3**（而不是 5） |
| 现在怎么防 | 回归测试 `test_expand_params_flow_from_config` 断言"config 里的参数真的传到了检索器" |

> 这类 bug 的共性是：**"配置"与"使用者"之间有一个手工中转站**（这里是构造函数调用）。只要是人手写的转接，就可能漏。**能断言就别靠自觉。**

## 6. 代码走读：假实现怎么写才算"忠实"

第 3 节讲了"假实现不能比真实实现更好用"。这一节用代码说明**具体怎么做**——以最典型的 Milvus 假 client 为例。

### 6.1 假 client 的核心：把"数据"和"可见数据"分开

```python
class FakeMilvusClient:
    """记录调用的假 MilvusClient，覆盖 store 用到的全部接口。

    忠实模拟真实 Milvus 的**写入可见性延迟**：`upsert` 写入的数据在 `flush` 之前
    查不到（`rows` 是实际数据，`visible` 是 query 能看到的）。漏掉这一步会让
    "写入后再读"这类顺序错误在单测里蒙混过关。
    """

    def __init__(self, existing_ids=(), dim=4):
        self.rows: dict[str, dict] = {i: {"kp_id": i} for i in existing_ids}  # 实际数据
        self.visible: set[str] = set(existing_ids)                            # query 能看到的
        self.dim = dim
        self.upserted = []      # 记录调用，供断言
        self.deleted = []
        self.flushed = 0
```

### 6.2 这个设计的关键在哪

| 设计 | 作用 |
|---|---|
| **`rows` 与 `visible` 分离** | 真实 Milvus 里"写进去了"≠"查得到"，必须 `flush` 才可见。假 client 用两个集合表达这个差异 |
| **`flushed` 计数器** | 测试可以直接断言"flush 调用了几次、在什么位置" |
| **`upserted` / `deleted` 记录调用** | 测试能断言**调用顺序**（这才是"清理陈旧主键顺序不能反"的可测形态） |
| **接口覆盖完整** | `has_collection` / `describe_collection` / `create_schema` / `prepare_index_params`… 真实现用到的全都要有，否则测试跑不起来 |

**如果省掉 `visible` 会怎样？** `upsert` 之后立刻 `query` 就能查到——于是"先 upsert 再取旧主键"这个**错误顺序在单测里完全通过**，而到了真实 Milvus 上，取到的是空集、清理静默失效。**这就是"假实现比真实现更好用"的代价：它把 bug 挡在了测试之外。**

### 6.3 三类回归测试的写法

本项目有三条"专门卡住某类 bug"的回归测试，写法值得借鉴：

```python
# ① 参数接线：断言 config 里的参数真的传到了检索器
def test_expand_params_flow_from_config():
    kb = KnowledgeBase.load(store=StubVectorStore())
    assert kb.retriever.expand_k == EXPAND_K          # ← 直接对值
    assert kb.retriever.expand_hops == EXPAND_HOPS
    assert kb.retriever.expand_decay == EXPAND_DECAY

# ② 测试不写生产日志：断言日志文件在跑测试前后没变化
def test_api_tests_do_not_write_production_log(...):
    before = <日志文件大小>
    ...  # 跑一遍接口
    assert <日志文件大小> == before

# ③ 不写真实 wiki/：断言真实目录没被动过
def test_write_wiki_does_not_touch_real_wiki_dir(tmp_path):
    before = {p.name for p in CONCEPTS_DIR.glob("*.md")}
    write_wiki(pts, {"edges": []}, wiki_dir=tmp_path/"wiki",
               concepts_dir=tmp_path/"concepts")
    after = {p.name for p in CONCEPTS_DIR.glob("*.md")}
    assert before == after
```

三条测试的**共同形状**：**用一个"可观测的副作用"来断言"某个隐含约束被遵守了"**。

| 测试 | 断言的副作用 |
|---|---|
| 参数接线 | 对象属性 **等于** config 值 |
| 不写生产日志 | 日志文件大小**不变** |
| 不写真实 wiki | 真实目录内容**不变** |

> 这类测试的写法有个共同点：**断言"没发生什么"比断言"发生了什么"更难写，但恰恰更有价值**。因为"没发生"的地方，正是静默 bug 藏身之处——日志被污染、生产目录被写、参数没传下去，全都不会有报错。

### 6.4 一个反面清单：假实现常见的"过度好用"

| 假实现 | 过度好用的地方 | 会漏掉什么 bug |
|---|---|---|
| 假向量库让写入立即可见 | 读得到刚写的数据 | **顺序类**（先写后取快照） |
| 假 LLM 永远返回合法 JSON | 不用写容错解析 | **解析容错**（围栏/噪音/大小写） |
| 假 DB 不区分用户 | 查询总能返回数据 | **隔离类**（漏 `user_id` 过滤） |
| 假编码器返回定长随机向量 | 语义边稳定可控 | **维度/归一化**相关（真实向量已 L2 归一） |
| 用 `tmp_path` 之外的目录 | 不写测试代码也"能跑" | **隔离类**（污染生产产物） |

**写假实现时的自检问题**：**"真实实现会不会在这里失败/延迟/拒绝？"** 如果会，假实现就必须也这样。

## 7. 本节小结

- **测试必须全离线**（不加载模型、不连服务、不调 LLM），否则开发者本地不会跑，等于没有测试。统一用 `uv run python -m pytest tests/`。
- 离线靠**注入假实现**（`StubEmbedder` / `FakeMilvusClient` / 假 Neo4j driver / mock LLM / `NullLogger`）；**可测试性要在设计时留注入口**。
- 三类只能靠测试挡住的**静默故障**：
  1. **顺序类**——Milvus 的 `flush` 顺序，靠"带可见性延迟的假 client"卡住；
  2. **隔离类**——测试写生产产物（曾污染 `logs/qa.log` 297 条），靠 `NullLogger` 与**可注入目录**挡住；
  3. **用户隔离类**——记忆跨用户泄漏，靠 `user_id` 过滤与"断言 SQL 与绑定参数"挡住。
- **"参数没接线"**（`EXPAND_K` 没传进构造函数）不报错、只变差，靠"断言配置真的传下去"的回归测试防。
- 一条贯穿的原则：**假实现不能比真实实现更好用**，否则它掩盖的正是真实世界的约束。

## 企业常见面试问答

**Q1：怎么保证测试不依赖外部服务？**

> 靠**依赖注入 + 假实现**：把"会连外部"的部分（编码器、向量库、图库、关系库、LLM）都做成**可注入的参数**，测试时传替身进去。这不是测试技巧，是**设计约束**——像 `MilvusVectorStore(client=None)`、`kb.load(store=None)`、`write_wiki(..., concepts_dir=...)` 这些参数都是为可注入留的口子。FastAPI 那边则用 `dependency_overrides` 替换整个依赖图，接口测试因此不需要 MySQL/Milvus/Neo4j/LLM，一个用例几毫秒。好处不只是"跑得快"：**离线让测试变成开发者愿意随手跑的东西**，这才是 217 项测试能一直保持绿色的实际原因。

**Q2：最值得写的测试是哪些？**

> 按"挡住静默故障的价值"排序，我最看重三类：① **隔离与安全类**——用户隔离、越权 404、账号枚举防护。这类 bug 一旦流出去是事故，而且平时完全看不出来；② **顺序与一致性类**——Milvus 的 `flush` 顺序、全量对齐的陈旧主键清理。这类问题的表现是"数据慢慢变脏"，等发现时已经无从追溯；③ **参数接线类**——断言配置真的传到了使用者（`EXPAND_K` 那次）。这类 bug 不报错、只让效果悄悄打折，除了断言没有别的办法发现。共同点是：**它们都对应的不是"代码写错了"，而是"代码看起来没写错，但行为偏离了预期"**——后者才是测试真正的价值所在。

**Q3：怎么发现静默失败？**

> 三条经验：① **假实现要忠实模拟真实约束**——最有代表性的是 Milvus 的可见性延迟：如果假 client 让写入立即可见，那么"先 upsert 再取旧主键"这个错误顺序在单测里会顺利通过，到了真实 Milvus 上才会静默失效。**假 client 越顺手，越容易掩盖真问题**；② **可观测性与测试配合**——`EXPAND_K` 那个 bug 是靠日志里 `graph_expanded` 恒为 3 才发现的，后来才补了回归测试。所以日志字段要**分类记来源**（种子/图谱扩展/反思补取分开），这样"某一环没生效"才有迹可循；③ **任何写磁盘的函数都要能指定输出位置**——否则测试污染生产产物这种"静默污染"就会发生（我们被 `logs/qa.log` 污染过 297 条）。

**Q4：测试覆盖率重要吗？**

> 在这个项目里我**没把覆盖率当目标**，217 项测试是"按风险挑出来的"，不是"按覆盖率凑出来的"。因为覆盖率衡量的是"代码被执行过"，而我们真正关心的是"**行为被断言过**"——比如 `test_mysql_store.py` 不连数据库，只断言"生成的 SQL 里有没有 `user_id` 条件"，覆盖率上看只是一行字符串比较，但它守的是一条安全红线。反过来，覆盖率高的地方也可能是"执行了但没断言"。所以我们的取舍是：**优先覆盖"错了会静默、且代价大"的地方**（隔离、顺序、接线、边界切分），而对"错了会立刻报错"的地方（比如参数类型）不额外花力气——因为报错本身就是最好的测试。
