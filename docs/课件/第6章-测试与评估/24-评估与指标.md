## 1. 评估数据：`eval/qa_test_cases.jsonl`

**规模：55 条**（JSONL，每行一个对象）。

| 切分维度 | 分布 |
|---|---|
| 按 `type` | `single_hop` **18** / `multi_hop` **25** / `complex` **12**（多跳+复杂合计 37 条，占 **67%**） |
| 按 `source`（来源法律） | 劳动合同法 **26** / 劳动法 **10** / 民法典 **20** |

字段：

| 字段 | 含义 |
|---|---|
| `id` / `type` | 用例编号 / 类型 |
| `source` | **来源法律**（跨法用例为多项）——用于**按法律分组**看检索质量 |
| `question` | 用户问题 |
| `answer` | 标准答案（作为 ragas 的 `ground_truth`） |
| `expected_knowledge` | 期望命中的知识点 id（recall@k 比对用） |
| `source_sections` / `sub_questions` | 答案来源章节 / 复杂题的子问题拆分 |

### 1.1 引用关系型用例：多跳能力怎么被量化

这是数据集设计里最见功力的一处。

一个多跳用例的 `expected_knowledge` **同时列出"引用方"与"被引方"**。例如「买卖合同价款约定不明」期望：

```
第六百二十六条（引用方）+ 第五百一十条 + 第五百一十一条（被引方）
```

这样 `recall@k` 就**直接量化了"引用链有没有被带进上下文"**——如果图谱扩展没把被引条文带出来，这个用例的 recall 就会掉，指标立刻反映出来。

两条保证数据可信的做法：

| 做法 | 说明 |
|---|---|
| `source` 字段**由脚本按 `expected_knowledge` 反推并校验**，不是手填 | 避免"人工标注与期望知识点对不上"的经典问题 |
| 全部引用关系用 `crossref_map()` **校验过**（被引条号确实出现在引用方正文里，共 17 处） | 保证"期望的引用链"**在真实图谱里存在**，而不是出题人想象的 |

> 这两条的意义：**评估集本身的正确性也需要被验证**。一个标注错误的数据集，会让所有指标失去意义——而且这种错误往往"看起来很正常"。

## 2. 检索质量指标：自定义 `recall@k`

```python
# eval/metrics.py
recall_at_k = |期望知识点 ∩ 检索 Top-k| / |期望知识点|
```

看 k = 1 / 3 / 5 / 8（`@8` 是沿用历史基线的汇报口径）。

```bash
uv run python -m eval.evaluate --skip-ragas          # 只算 recall@k（不调 LLM）
uv run python -m eval.evaluate --skip-ragas --source 民法典   # 只跑某部法律
```

### 2.1 一个必须讲清的口径：@8 不是生成上下文上限

| | 数值 |
|---|---|
| eval 检索口径 | `--top-k 5`（**5 个种子**）+ 前 3 个扩展 = 前 8 位 |
| 生产生成上下文 | 10 种子 + ≤5 扩展 + 反思补取 ≈ **15 块起**（实测见过 17） |

所以 **`@8` 只是"汇报口径"，不是生成器实际拿到的上下文规模**。这一点混淆的后果很实际：有人会以为"生成只用了 8 块"而去优化一个不存在的问题。4.3 那个 `EXPAND_K` 的 A/B 也是同一个道理——**指标只覆盖它定义的那部分**。

## 3. 回答质量指标：ragas

基于 **Ragas 0.3.0**，五个指标：

| 指标 | 看什么 |
|---|---|
| `ContextRelevance`（`nv_context_relevance`） | 上下文与问题的相关性 |
| `context_precision` | 上下文里的有效信息占比 |
| `context_recall` | 上下文是否覆盖了标准答案所需信息 |
| `answer_relevancy` | 回答与问题的相关度 |
| `faithfulness` | **忠实度**——回答是否只依据给定上下文（幻觉的直接指标） |

### 3.1 两个必踩的坑

**坑一：版本组合**

> `ragas==0.3.0` + `langchain-community==0.4.0` + langchain 1.x 是**唯一已验证兼容**的组合。
> ragas 0.4.x 与 langchain-community ≥0.4.2 不兼容（`vertexai` 模块被移除）；langchain 0.3 栈与 ragas 0.2.x 的 `agenerate_prompt` API 也不兼容。

**坑二：embedding 必须用 DashScope 自己的**

```python
# ✅ 必须用这个
from langchain_community.embeddings import DashScopeEmbeddings   # text-embedding-v3
LangchainEmbeddingsWrapper(DashScopeEmbeddings(...))

# ❌ 用 langchain_openai.OpenAIEmbeddings 配 DashScope 会报：
#    input.contents is neither str nor list of str
```

> 这两个坑的共同点：**报错信息都不指向真正的原因**（一个说模块找不到，一个说输入格式不对）。所以遇到 ragas 的怪报错，第一反应应该是"版本组合对不对""embedding 用的是不是 DashScope 家自己的"，而不是去 debug 自己的数据。

## 4. 实测基线解读（55 条，`--skip-ragas`）

**总体：**

| 指标 | recall@1 | recall@3 | recall@5 | recall@8 |
|---|---|---|---|---|
| 55 条 | **0.489** | **0.729** | **0.859** | **0.947** |

**按来源法律分组：**

| 来源 | 条数 | recall@1 | recall@3 | recall@5 | recall@8 |
|---|---|---|---|---|---|
| 民法典 | 20 | **0.592** | 0.758 | 0.892 | **0.983** |
| 劳动合同法 | 26 | 0.414 | 0.692 | 0.846 | 0.949 |
| 劳动法 | 10 | 0.433 | 0.692 | 0.742 | **0.775** |

### 4.1 怎么读这组数

**① 民法典 @8 = 0.983 说明"引用链基本都进上下文了"。**
民法典 20 条里的多跳用例，期望同时含引用方与被引方——@8 能到 0.983，说明 **crossref 图谱扩展（权重 1.5，4.3）确实在起作用**。这是"多跳能力"最直接的证据。

**② 两部劳动法 35 条的基线未变，可与历史对比。**

| 口径 | recall@1 | @3 | @5 | @8 |
|---|---|---|---|---|
| 两部劳动法 35 条 | 0.431 | 0.712 | 0.841 | 0.926 |

为什么能直接对比？因为 **`KP_001`–`KP_205` 的编号映射在新增民法典后保持不变**（民法典追加在 `KP_206` 之后，3.1 讲过）。这是刻意设计的——**评估基线可比性应该在数据设计阶段就保住**，而不是事后靠"换算"。

**③ 劳动法 @8 = 0.775 明显偏低，是下一步要攻的点。**
不是"整体不好"，而是**特定分组不好**——这正是按 `source` 分组的意义：**没有分组，你只会看到一个平均分，不知道该改哪里。**

## 5. 已知薄弱项与改进方向

### 5.1 薄弱项：宽泛的"措施/责任"类问题

| 用例 | 问题 | 现象 |
|---|---|---|
| eval_026 | 拖欠工资怎么维权 | 期望条文未必全部落入 top-8 |
| eval_030 | 维权途径有哪些 | 同上 |
| eval_025 | 孕期被违法解除怎么办 | 同上 |

**成因**（4.3 已分析）：这类问题**同时涉及多法多条文**，检索与扩展的分数被"泛主题"稀释，真正该进的几条反而不突出。

**但要说清现状**：生成器在缺失部分条文时，仍能基于**已召回的相关条文**给出**合法合理**的答案（冒烟测试验证）。也就是"检索不全"≠"答案乱来"。

### 5.2 改进方向（诚实标注状态）

| 方向 | 状态 |
|---|---|
| 按预期条文补 **crossref** 或**概念映射** | 可直接做（摄入期工作） |
| 放宽生成上下文 | 可调参数（`TOP_K` / `EXPAND_K`） |
| **查询分解**（LLM 拆子问题分别检索再合并） | **已讨论、未实现** |
| **实体链接 + 图传播**（query 抽实体 → 图节点 → 影响力传播召回） | 未实现 |
| 评估完善（抽样、随机 `--limit`、历史版本对比） | 部分有 |

> 讲这一节最该有的态度：**知道自己哪里不行，比宣称自己哪里强更有说服力。** 面试时如果被问"你的项目有什么不足"，能说出"劳动法分组 @8 只有 0.775，成因是泛主题稀释，我试过 A/B 但没解决"——这比背一串漂亮指标更可信。

## 7. 代码走读：`recall_at_k` 与评估数据的组装

评估这一块代码不多，但有两处**设计上的小心思**值得单独看。

### 7.1 `recall_at_k`：15 行实现，两个关键决定

```python
def recall_at_k(retrieved_ids: list[str], expected_ids: list[str], k: int) -> float | None:
    """计算 Top-k 检索召回率。若 expected_ids 为空返回 None（无法评估）。"""
    if not expected_ids:
        return None
    hit = sum(1 for eid in expected_ids if eid in set(retrieved_ids[:k]))
    return hit / len(expected_ids)

def recall_report(retrieved_ids, expected_ids, ks=(1, 3, 5)) -> dict[str, float | None]:
    return {f"recall@{k}": recall_at_k(retrieved_ids, expected_ids, k) for k in ks}
```

| 决定 | 理由 |
|---|---|
| **`expected_ids` 为空返回 `None`（不是 0）** | "没有期望"和"一条都没命中"是**两件不同的事**。返回 0 会把"这条用例没法评估"算成"效果很差"，拉低整体均值——**这是评估里最常见的失真来源之一**。返回 `None` 让调用方可以选择跳过 |
| **`set(retrieved_ids[:k])`** | 先切片再转集合：`in` 判断是 O(1)。同时**天然去重**（万一检索结果里有重复） |

注意签名里 **`retrieved_ids` 是"有序列表"而不是"集合"**——因为"Top-k"这个概念依赖顺序。**把"顺序有意义"这个约束表达在类型与用法上**，比写注释提醒更可靠。

### 7.2 一条用例的数据组装（把检索结果接到指标上）

评估主程序的每一轮大致是：

```python
# ① 检索（走 KnowledgeBase.load()，即 Milvus）
results = kb.search(question, top_k=top_k)
retrieved_ids = [r["id"] for r in results]          # ← 顺序在这里被保留下来

# ② recall@k（把"顺序"喂给指标）
report = recall_report(retrieved_ids, case["expected_knowledge"], ks=(1, 3, 5, 8))

# ③ 生成（同一批块送进生成器）
answer = generator.generate(question, contexts=results, ...)

# ④ ragas（用 answer 作为 response、case["answer"] 作为 ground_truth、
#          各块的 content 作为 contexts）
```

两个容易忽略的点：

| 点 | 说明 |
|---|---|
| **`retrieved_ids` 必须保持检索返回的顺序** | 一旦中途按别的键排序（或转成集合），`recall@1` 就失去意义 |
| **`top_k` 是评估参数，不是生产参数** | eval 用 `--top-k 5`，而生产是 10。**同一份用例在两种口径下的 @8 含义不同**（5 种子+3 扩展 vs 10 种子+…）——所以对比基线时必须口径一致 |

### 7.3 数据集的自我校验（比指标更重要）

第 1 节讲过：`source` 字段由脚本按 `expected_knowledge` **反推并校验**，引用关系用 `crossref_map()` **校验过**（17 处）。这段校验代码虽然不在评分路径上，但它的价值可能比指标本身更大：

> **一个标注错误的数据集，会让所有指标失去意义——而且这种错误"看起来很正常"。**

具体来说，如果 `expected_knowledge` 写错了（比如把"第四十六条"写成"第四十八条"），你会在 recall 报告里看到一个**偏低但完全合理**的数字，然后花几天去优化检索——**方向完全错了**。所以：

| 校验项 | 手段 |
|---|---|
| `source` 与实际期望是否一致 | 脚本反推 + 断言 |
| 期望的引用关系是否真实存在 | `crossref_map()` 校验（被引条号确实出现在引用方正文里） |
| 期望的知识点 id 是否真的存在 | 与图谱节点比对 |

> 一句话：**评估的第一件事不是"跑指标"，而是"确认标尺是准的"。** 这在任何评估体系里都成立，但在知识图谱这类"没有标准答案"的场景里尤其重要（3.3 第 7 节讲的"评测困难"）。

## 8. 本节小结

- 数据集 **55 条**（单跳 18 / 多跳 25 / 复杂 12；劳动合同法 26 / 劳动法 10 / 民法典 20）；**引用关系型用例的 `expected_knowledge` 同时列出引用方与被引方**，使 recall@k 能直接量化"引用链有没有进上下文"。
- 数据的 `source` 由脚本**反推并校验**，引用关系全部用 `crossref_map()` **校验过**（17 处）——**评估集自身的正确性也要被验证**。
- `recall@1/3/5/8` 是自定义指标；**`@8` 是汇报口径，不是生成器上下文上限**（生产是 10 种子 + ≤5 扩展 + 反思 ≈ 15 块起）。
- ragas 两个坑：**版本组合**（ragas 0.3.0 + langchain-community 0.4.0 + langchain 1.x）与 **embedding 必须用 `DashScopeEmbeddings`**；两者的报错都不指向真正原因。
- 基线：总体 **0.489 / 0.729 / 0.859 / 0.947**；民法典 @8 **0.983**（引用链进了上下文）、劳动法 @8 **0.775**（薄弱项，泛主题稀释）。**按 `source` 分组**才能定位问题。
- 诚实交代不足（eval_025/026/030）与改进方向（查询分解、实体链接+图传播均为**未实现**）。

## 企业常见面试问答

**Q1：recall@k 是怎么算的？为什么要自定义而不是用现成指标？**

> 算法很直接：`|期望知识点 ∩ 检索 Top-k| / |期望知识点|`，k 取 1/3/5/8。之所以自定义，是因为**这个系统的基本单位是"知识点"而不是"文本块"**——通用的检索指标（如 recall@k 在 RAG 语境下）默认"检索单元 = chunk"，而我们的期望是"具体哪几条法条"。用一个按知识点算的指标，才能回答"该带的条文有没有进上下文"这个业务问题。另外要澄清一个容易误解的点：**`@8` 只是沿用历史基线的汇报口径，不是生成器的上下文上限**——生产路径实际给生成器的是 10 个种子 + ≤5 个扩展 + 反思补取，约 15 块起。混淆这两者，会让人去优化一个不存在的问题。

**Q2：为什么不全量跑 ragas？**

> 成本和必要性两方面。**成本**上，ragas 的指标（尤其 `answer_relevancy`、`faithfulness`）每个都要调 LLM 做评判，55 条全跑下来既慢又花钱，还要 embedding。**必要性**上，两个指标回答的是不同问题：`recall@k` 是**检索质量**、可以不调 LLM 快速回归（我们日常改检索参数就靠 `--skip-ragas`），ragas 是**回答质量**、适合在关键节点（版本发布、大改 prompt）全量跑一次。所以日常节奏是"改完跑 recall 确认没回退，里程碑跑一次 ragas"。**把贵的评估放在该放的位置**，比每次都全跑更可持续。

**Q3：指标不好怎么定位是检索还是生成的问题？**

> 分层看，我一般按这个顺序：① **先看 `recall@k`**——如果期望条文根本没进上下文，那是**检索问题**，往下查 `seeds` / `graph_expanded` / `reflect_fetched` 三类来源分别贡献了什么（日志里是分开记的，这正是 6.1 讲的"可观测性"）；② **如果 recall 正常但答案不好**，那是**生成问题**——看 `faithfulness`（是否臆造）与 `answer_relevancy`（是否答偏了）；③ **如果 recall 差但答案还行**，说明生成器在缺失资料时仍能合理作答（我们几个薄弱用例就是这种情况），这时要判断"是继续补检索还是接受现状"。关键前提是**日志把"哪一步带进来的条文"分开记了**——否则你只能看到一个总分的上下文，无从归因。

**Q4：你的项目有什么不足？**

> 有三个我知道并且能说清成因的：① **宽泛问题检索不全**——eval_026/030（拖欠工资维权、维权途径）这类同时涉及多法多条文的问题，检索与扩展的分数被"泛主题"稀释，期望条文未必全部落入 top-8；成因是问题本身的模糊性，不是实现 bug。② **按法律分组看，劳动法组偏弱**——@8 只有 0.775，明显低于民法典的 0.983，因为劳动法用例里有更多跨条文、需要多跳的综合题。③ **反思机制的实际增量很小**——全库只有 68/1465 个知识点有可跟进的引用，实测 35 条用例中只有 2 条真正补到条文；我没有把它包装成"智能体自主检索"，因为数据不支持这个说法。改进方向上，**查询分解**（LLM 拆子问题分别检索再合并）与**实体链接 + 图传播**都是讨论过但**尚未实现**的——我会明确说"未实现"，而不是含糊带过。
