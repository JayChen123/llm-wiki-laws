# 3.2 知识构建（二）—— 概念增强与关联图谱

> 定位：知识点切好了，但它们还是"孤岛"。这一节给它们接上两类桥梁：**口语 → 法条**的概念映射，与**知识点 ↔ 知识点**的四类关联边。

本节目标：

1. 理解"法律措辞 vs 用户口语"的代沟，以及概念映射表怎么弥合它；
2. 掌握关联图谱的**四类带类型边**及其权重/阈值；
3. 吃透两个最易错的设计：sibling 的分组键必须是 **(编, 章)**、crossref 的方向要从正文派生；
4. 认识图谱产物的规模构成，并能解释每类边的贡献。

---

## 1. 先解决一个检索层面的"代沟"

用户不会用法律措辞提问。他会问：

| 用户实际说的 | 法条里写的 |
|---|---|
| 加班费 | 延长工作时间…支付工资报酬 |
| 被开除有赔偿吗 | 违法解除…经济补偿 |
| 冷静期多久 | 离婚登记申请之日起三十日内…撤回 |
| 高空抛物谁负责 | 从建筑物中抛掷物品…侵权责任 |

字面检索在这里**必然失效**：BM25 匹配不到"加班费"这三个字，向量也可能因为语义鸿沟而排不上来。这就是**概念映射表**要解决的问题。

---

## 2. `concept_map.py`：53 个概念映射表

三个组成部分：

```python
# 1) 概念 → [(来源文档名关键字, 条文)]，用于
#    · concept_terms_for() 关键词增强
#    · wiki/index.md 核心概念导航
CONCEPT_MAP = {
    "试用期":  [("劳动合同法", "第十九条"), ...],
    "加班费":  [("劳动法", "第四十四条"), ...],
    "离婚冷静期": [("民法典", "第一千零七十七条"), ...],
    "高空抛物": [("民法典", "第一千二百五十四条"), ...],
    ...
}

# 2) 概念 → 用户常用查询词（**刻意避开**"劳动合同/工资/劳动"等过泛停用词）
CONCEPT_KEYWORDS = {
    "加班费": ["加班", "加班费", "延长工作时间", "加班工资", ...],
    ...
}
```

**规模**：`CONCEPT_MAP` 与 `CONCEPT_KEYWORDS` 各 **53 个概念**——劳动法侧 26 个（劳动合同订立/试用期/竞业限制/解除/经济补偿/集体合同/劳务派遣/非全日制/加班费/劳动监察/法律责任…），民法典侧 27 个（诉讼时效/表见代理/监护/善意取得/居住权/抵押担保/格式条款/情势变更/合同法定解除/违约责任/违约金/借款/房屋租赁/无因管理/不当得利/隐私权/个人信息保护/婚姻无效/夫妻共同财产与共同债务/离婚冷静期/法定继承顺序/遗嘱继承/产品责任/交通事故/医疗损害/高空抛物…）。

### 2.1 文档感知匹配（一个容易被忽略的细节）

概念映射存的是 `(法律关键字, 条文)`，不是知识点 id。解析时**必须同时匹配来源文档**：

```python
def concept_terms_for(point):
    for concept, refs in CONCEPT_MAP.items():
        for law, article in refs:
            if law in point.source and article in point.clause:   # 文档感知
                yield from CONCEPT_KEYWORDS.get(concept, [])
```

为什么必须两个条件都判？因为**多部法律有同号条文**：劳动合同法有"第四十四条"，劳动法也有"第四十四条"，而它们的含义完全不同。只按条号匹配就会把"加班费"的查询词注入到错误的法条上。

### 2.2 关键词注入（`enrich_keywords`）

把概念查询词并进对应知识点的 `keywords` 字段（幂等，重复跑不会重复追加）。这个字段随后**同时进入两处**：

- **BM25 索引**（`keyword_retriever` 的语料 = 标题 + 正文 + 关键词）→ 口语词可以直接命中法条；
- **语义编码文本**（`semantic_text`）→ 语义边与向量召回也能感知到概念。

> 记住这条链：**口语词进关键词 → 关键词进 BM25 语料与语义文本 → 口语提问也能召回法条**。这是"加班费"能答对的关键一环。

## 3. 关联图谱：四类带类型边

知识点切完就有结构，但"结构"不等于"关联"：46 条（经济补偿）和 38 条（劳动者解除权）在文档里隔得很远，却必须一起答。图谱就是把这些关系**显式**建出来。

| 边类型 | 来源 | 权重 / 阈值 | 作用 |
|---|---|---|---|
| `sibling` | 同 **(编, 章)** 内的条文 | 权重 1.0 | 结构关联：同章条文天然相关 |
| `keyword` | 关键词 Jaccard | ≥ **0.3** | 主题相近（词面重合） |
| `semantic` | bge-m3 余弦 | ≥ **0.75** | 语义相近（表述不同也算） |
| `crossref` | 正文里"第X条"引用同法其他条文 | 权重 **1.5** | **法条互相引用——多跳召回的关键** |

一条边可以带**多个类型**（`types: ["semantic","sibling"]`），所以后面统计"关系数"会大于"边数"。

---

## 4. `sibling`：结构边，分组键必须是 (编, 章)

规则很简单：同一章内的条文两两相连。但这里有一个**踩得很深的坑**：

民法典 7 编**各自从"第一章"重新起算**——7 编里都有"第一章"。如果只按 `chapter`（章号）分组，就会把"第一编 总则 第一章"、"第二编 物权 第一章"、"第三编 合同 第一章"…**并成一个大团**，同号章之间全部两两连边。

实测后果：曾产生约 **1.97 万条假 sibling 边**，全库边数从 21252 虚高到 **40992**。

正确的分组键是**二元组**：

```python
key = (point.part, point.chapter)      # (编, 章) —— part 为空的劳动法/劳动合同法退化成只能按章分
```

> 同一个教训在 `wiki_writer` 的目录分组里也要守住：有"编"的法律必须按 **编→章 两级**组织目录，否则民法典的目录也会"同号章合并"。**改任何跟章号分组相关的代码，先问一句：带 `part` 了吗？**

## 5. `keyword` 与 `semantic`：内容相似的两条路

### 5.1 keyword：关键词 Jaccard

```python
jac = |A ∩ B| / |A ∪ B|
if jac >= 0.3: add_edge(u, v, "keyword", jac)
```

词面重合度。它能抓住"同一条法律里用词相近的条文"，但对**换了说法**的语义相似无能为力。

### 5.2 semantic：bge-m3 余弦

```python
# 两两点积（向量已 L2 归一）→ 余弦
cos = float(v1 @ v2)
if cos >= 0.75: add_edge(u, v, "semantic", cos)
```

**阈值 0.75 是调出来的**：实测 0.65 会让图谱**近全连接**（大量弱相关边把扩展结果稀释掉），而 0.85 又会让很多真正相关的条文连不上。这类阈值不要凭直觉定，要看**度数分布与最终 recall**。

### 5.3 编码文本必须与向量库共用

```python
def semantic_text(point):
    return f"{point.title}\n{point.content[:200]}"      # 标题 + 正文前 200 字
```

⚠️ **语义边建图与 Milvus 写入必须共用这一个函数**。如果两处各写一套模板，就会出现"图谱里 A、B 语义相邻，但向量检索认为它们不相似"——排查起来极其困难，因为两边单独看都"正常"。

## 6. `crossref`：法条交叉引用（最关键的一类）

### 6.1 是什么

法条正文里会引用别的条文，例如：

- 劳动合同法 **第四十六条** 引 **第三十八条**（劳动者依 38 条解除的，用人单位应付经济补偿）
- **第六十五条** 引 **第三十九条**
- **第四十二条** 引 **第四十五条**

这类"协同条文"是法律问答的常态：**问一个问题，答案分散在互相引用的几条里**。

### 6.2 怎么建

```python
# 正文里出现"第X条" → 同一部法律内的引用 → 建边，权重 1.5
#   · 正则同样含"千"（民法典跨引用大量指向第 1000 条以上条文）
#   · **跨法不建边**（民法典条文不会引用劳动法条文）
```

三个设计点：

| 设计 | 原因 |
|---|---|
| 权重 **1.5**，高于结构边（1.0） | 在同分竞争里，**被引用条文优先被带进上下文**——它们通常是答案的必需品 |
| **仅同法内**建边 | 跨法引用在文本上不存在；硬连会引入噪音 |
| 解析抽成 `crossref_map()` **共用一份实现** | 建边（这里）与反思候选（4.4）用的是同一份规则，避免"两处规则各自漂移" |

### 6.3 规模与效果

- 全库共 **97 处** crossref 引用，涉及 **68/1465** 个知识点（约 4.6%）——**大部分条文并不引用别条**，这一点对后面理解"反思为什么经常零调用"很重要。
- 效果：多跳用例里"被引条文"基本都能进上下文，民法典 20 条用例的 recall@8 达 **0.983**（用例期望同时含引用方与被引方）。

## 7. 图谱产物与规模构成

```json
{
  "nodes": [{ "id": "KP_046", "title": "第四章·第四十六条", "clause": "第四十六条",
              "keywords": [...], "content": "...", "source": "..." }],
  "edges": [{ "source": "KP_038", "target": "KP_046", "types": ["crossref","sibling"], "weight": 1.5 }]
}
```

| 指标 | 数值 |
|---|---|
| 节点 | **1465** |
| 边（按 `(source,target)` 去重） | **21252** |
| 关系数（Neo4j 里按类型拆开后） | **30569** |
| 分类计数（可重复计入同一对节点） | sibling **15306** / semantic **11720** / keyword **3446** / crossref **97** |

> ⚠️ 两个数不要混：**边数 21252** 是"节点对"的数量；**关系数 30569** 是"把一条多类型边拆成多条关系"后的数量（3.5 细讲）。讲的时候说清楚是哪一个，否则会自相矛盾。

**边数失控怎么自查？** 看 sibling 占比。正常情况 sibling 应该与"同章条文对数"量级一致；如果它突然飙升（如那次 3.7 万对），十有八九是分组键丢了 `part`。

## 8. 本节小结

- 概念映射表解决**口语 → 法条**的代沟：53 个概念，**文档感知匹配**（必须同时判来源法律与条号，否则多法同号会串味），查询词注入 `keywords` 后同时进 BM25 语料与语义文本。
- 关联图谱四类边：`sibling`（同 **(编,章)**，1.0）/ `keyword`（Jaccard ≥0.3）/ `semantic`（余弦 ≥0.75）/ `crossref`（同法内引用，**1.5**）。
- 两个易错设计：**sibling 分组键必须是二元组 `(part, chapter)`**（否则同号章并团，边数虚高到 40992）；**`semantic_text()` 必须与向量库写入共用**（否则图谱语义与检索语义不一致）。
- `crossref` 是多跳召回的关键，但覆盖面天然有限（97 处 / 68 个知识点）——这解释了为什么"反思"经常零调用（4.4）。
- 规模：1465 节点 / **21252 边** / 30569 关系；讲规模时说清是"边数"还是"关系数"。

## 企业常见面试问答

**Q1：图谱的边是怎么定的？阈值凭感觉调的吗？**

> 不是凭感觉，是**按效果调**。三类带阈值的边：`keyword` 用 Jaccard ≥0.3（词面重合），`semantic` 用余弦 ≥0.75。语义阈值我们实测过 0.65 会让图谱**近全连接**——大量弱相关边进入，BFS 扩展时把真正相关的条文挤出去，recall 反而下降；太高又会漏掉真正相关但表述差异大的条文。所以调阈值时看的是**度数分布 + 最终 recall**，而不是"看起来合不合理"。另外 `sibling` 和 `crossref` 不带阈值，它们是**确定性**的结构关系与引用关系。

**Q2：为什么 `crossref` 的权重（1.5）比结构边（1.0）还高？**

> 因为**被引用的条文往往是答案的必需品**。举个例子：问"公司违法解除且不给补偿我能主张什么"，答案需要 46 条（经济补偿）**同时**用到 38 条（劳动者解除权），而这两条在文档里隔得很远、词面也不像。检索只可能命中其中一条，另一条要靠图谱带出来。权重给到 1.5，是为了在"扩展预算有限（`EXPAND_K`）"的前提下，让被引条文**优先**挤进上下文。实测这正是民法典多跳用例 recall@8 能到 0.983 的主要原因。

**Q3：口语词命中法条，除了概念映射还有别的办法吗？**

> 有几条路，各有取舍：① **关键词增强**（本项目做法）——人工维护"概念 → 查询词"映射，确定性、可审计、零运行时成本，代价是覆盖面靠人工扩；② **查询改写**——用 LLM 把口语问题改写成法律措辞再检索，覆盖面广，但每次提问多一次 LLM 调用、且改写本身可能引入偏差；③ **纯语义检索**——靠 bge-m3 的语义能力直接弥合，但它对"加班费 vs 延长工作时间"这类**领域专有对应**并不稳，且不可解释。我们选 ①，因为法律领域的"口语 ↔ 法条"对应关系是**有限且稳定**的，人工维护 53 个概念比引入不确定性更划算——这也是"摄入时编译"这个理念的一贯取舍。

**Q4：图谱写进 `sibling` 时踩过什么坑？**

> 最典型的是**分组键只用了章号**。民法典 7 编各自从"第一章"起算，只按章号分组就把不同编的同号章并成了一个大团，产生约 1.97 万条假边、全库边数从 21252 虚高到 40992。修法是把分组键改成二元组 `(part, chapter)`。这个坑有个特点：**它不报错，只是让图谱"更连通"**——而更连通听起来像好事，实际是把扩展预算浪费在无关条文上。所以凡是"看起来更好"的指标异常，都要回头查是不是把不该连的连上了。同一个教训在 Wiki 目录分组上也要守住。
