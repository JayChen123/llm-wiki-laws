## 1. `extract_knowledge_points`：切分状态机

### 1.1 代码（节选）

```python
def extract_knowledge_points(md_path: Path) -> list[KnowledgePoint]:
    # 按物理行（仅 \n）拆分：splitlines() 会把换页符 \f 也当换行，
    # 使 source 行号比编辑器实际行号大（民法典 130 处 \f，漂移 129 行，溯源对不上）。
    raw_lines = md_path.read_text(encoding="utf-8").split("\n")
    segments: list[tuple[int, str]] = [
        (line_no, seg)
        for line_no, line in enumerate(raw_lines, 1)
        for seg in line.split("\f")        # 同一物理行的 \f 分段，共用行号
    ]

    part = part_title = chapter = chapter_title = section = clause = ""
    buf: list[str] = []
    body = False                            # 是否已进入正文（首个"第X条"之后）

    def flush() -> None:
        nonlocal buf
        # 必须有 clause：章/节标题本身不是知识点（页眉噪音曾让 34 个章标题单独成点）
        if buf and chapter and clause and body:
            content = "\n".join(buf)
            head = f"{part} {part_title}·{chapter}" if part else chapter
            kp = KnowledgePoint(
                id=f"KP_{len(points) + 1:03d}",
                title=f"{head}·{clause}",   # 有"编"时标题带编名
                ..., source=f"{md_path.name} L{start_line}-{line_no}",
            )
            kp.keywords = extract_keywords(kp, content)
            points.append(kp)
        buf = []

    def handle_header(stripped: str, this_line: int) -> bool:
        stripped = stripped.translate(_KANGXI_TABLE)     # ① 先归一化
        pm = _PART_RE.match(stripped)                    # ② 再匹配（^ 锚定行首）
        if pm:
            flush()
            part = f"第{pm.group(1)}编"
            part_title = _normalize(pm.group(2))
            # 编内章号重新起算，章上下文必须一并清空
            chapter = chapter_title = section = clause = ""
            buf = []
            start_line = this_line
```

### 1.2 逐段思路

| 段 | 在做什么 | 为什么 |
|---|---|---|
| `split("\n")` + 行内 `split("\f")` | **按物理行**取行号 | `splitlines()` 会把 `\f` 当换行，行号整体偏大（民法典末尾漂移 129 行），**溯源的 `source` 就是假的** |
| `flush()` 的三重条件 | `buf` 非空 + `chapter` 有 + **`clause` 非空** + 已进正文 | 章/节标题本身不是知识点。第 3 个条件是**兜住噪音的最后一道闸**——页眉噪音会被挂到章下，若不校验 `clause` 就会生成 34 个空条文 |
| `handle_header` 先 `translate` 再 match | 康熙部首归一到匹配之前 | 法律 PDF 里 `第⼀条` 的 `⼀` 是 U+2F00，**长得一样但正则不认** → 不归一化则一条都切不出来 |
| `_PART_RE` 用 `^` 锚定 | 只认行首 | 正文里"依照本法第一编第六章…"这类交叉引用不会被误判成编标题 |
| 遇"编"就清空章/节/条上下文 | 编是新的层级起点 | 民法典 7 编**各自从"第一章"重新起算**；不清空，章标题前的内容会挂到上一编 |

### 1.3 如果换个写法会怎样

| 换个写法 | 后果 |
|---|---|
| 用 `splitlines()` | 行号漂移，`source` 定位不准（溯源失效） |
| 不校验 `clause` 非空 | 噪音生成垃圾知识点（曾 34 个） |
| 用 `match` 但去掉 `^` | 正文交叉引用被当成新条头 → **条文重复编号、数量翻倍** |
| 不归一化康熙部首 | 该文档一条都切不出来（但**不报错**） |

> 这个函数的注释密度很高，而这正是**知识图谱工程该有的样子**：每个看似多余的条件，背后都对应一次真实的踩坑。

## 2. `add_edge`：为什么边要"合并"

### 2.1 代码

```python
edges: dict[tuple[str, str], dict] = {}

def add_edge(u: str, v: str, etype: str, weight: float) -> None:
    key = (min(u, v), max(u, v))                       # ① 无向键：排序后取对
    entry = edges.setdefault(key, {"types": [], "weight": 0.0})
    if etype not in entry["types"]:                    # ② 类型去重
        entry["types"].append(etype)
    entry["weight"] = max(entry["weight"], weight)     # ③ 权重取最大（不累加）
```

### 2.2 三个决定

| 决定 | 理由 |
|---|---|
| **键用 `(min, max)`** | 同一条边可能被两类规则同时发现（如既是 `sibling` 又是 `crossref`）。用排序后的键，`(A,B)` 与 `(B,A)` 落到同一条，避免重复 |
| **`types` 是数组** | 一条边可以带多个类型 → 后续在 Neo4j 里拆成多条关系（2.4）。**保留全部类型**才能让下游"只走引用链"这类查询成立 |
| **权重 `max` 而不是求和** | 求和会让"被多条规则命中的边"权重虚高，破坏"权重代表关系强度"的语义。取最大 = **"它最强的那个理由有多强"** |

### 2.3 四类边的构建（同一函数的下半部分）

```python
# 1) 结构边：分组键必须是 (编, 章)
by_chapter.setdefault((p.part, p.chapter), []).append(p)
for items in by_chapter.values():
    clauses = [p for p in items if p.clause]
    for i in range(len(clauses)):
        for j in range(i + 1, len(clauses)):
            add_edge(clauses[i].id, clauses[j].id, "sibling", 1.0)

# 2) 关键词边
jac = _jaccard(points[i].keywords, points[j].keywords)
if jac >= keyword_threshold: add_edge(..., "keyword", round(jac, 4))

# 3) 语义边
cos = float(np.dot(vectors[i], vectors[j]))
if cos >= semantic_threshold: add_edge(..., "semantic", round(cos, 4))

# 4) 引用边（复用 crossref_map，与反思共用同一份实现）
for source_id, targets in crossref_map(nodes).items():
    for target_id in targets:
        add_edge(source_id, target_id, "crossref", _CROSSREF_WEIGHT)
```

两个值得注意的实现细节：

- `clauses = [p for p in items if p.clause]` —— **过滤掉没有 clause 的节点**再两两连边。多一道保险，避免异常数据进来后产生一堆以空条文为中心的边。
- 引用边的解析**抽成 `crossref_map()` 复用**（建边用一次、反思候选用一次）。**同一份规则被两处使用时，一定要抽成一个函数**——否则两份实现会随时间漂移，而"哪边对"极难判断。

## 3. `MilvusVectorStore.upsert`：全量对齐与 flush 顺序

### 3.1 代码

```python
def upsert(self, nodes: list[dict], vectors) -> int:
    if len(nodes) != len(vectors):
        # zip 会静默按短的一侧截断；那样后续"清理陈旧主键"会误删缺向量的知识点
        raise ValueError(f"节点数({len(nodes)})与向量数({len(vectors)})不一致，拒绝写入")
    rows = [{"kp_id": ..., "title": ..., "source": ..., "vector": [...]}
            for node, vec in zip(nodes, vectors)]
    if not rows:
        return 0

    # 先取"写入前"的主键集合，且顺序不能颠倒：Milvus 的写入**与删除**都要 flush 之后
    # 才能被 query 看到，若在 upsert 之后再查会读成空集，陈旧主键清理会静默失效（已踩过）。
    self._client.flush(self.collection)
    existing = set(self._existing_ids())
    self._client.upsert(collection_name=self.collection, data=rows)
    stale = sorted(existing - {r["kp_id"] for r in rows})
    if stale:
        self._client.delete(collection_name=self.collection, ids=stale)
    self._client.flush(self.collection)     # 让本次写入与清理立即生效、可被检索
    return len(rows)
```

### 3.2 这段代码值得逐行读

| 行 | 思路 |
|---|---|
| **长度校验** | `zip` 会**按短的一侧静默截断**。若不校验：写入的是"前 N 条"，而后面的"清理陈旧主键"会把剩下的全删掉 → **数据静默丢失**。宁可报错 |
| **先 flush 再取快照** | Milvus 的**写入与删除都要 flush 后才可见**。顺序写反（先 upsert 再取旧主键）→ 取到**空集** → 清理无事可做 → **陈旧主键永久残留**，且不报错 |
| **`stale = existing - 新集合`** | "全量对齐"的核心：集合内容**必须等于**当前知识库，多出来的删掉 |
| **最后再 flush 一次** | 让本次写入与清理**立即对检索可见**——否则刚建完库检索却查不到 |

> **这是全项目最"教科书级"的一段代码**：它同时体现了知识图谱工程的三条原则——**幂等**（全量对齐）、**显式失败**（长度校验）、**把不可见的状态变化显式处理**（flush）。

## 4. `Neo4jGraphStore.sync`：图的全量对齐

### 4.1 顺序

```python
# ① 清空所有旧关系
self._run("MATCH (:KnowledgePoint)-[r]->(:KnowledgePoint) DELETE r")

# ② 批量写节点（MERGE → 幂等）
"UNWIND $rows AS row "
"MERGE (n:KnowledgePoint {id: row.id}) "
"SET n.seq = row.seq, n.title = row.title, ... , n.keywords = row.keywords"

# ③ 按类型建关系（CREATE —— 因为 ① 已经清空了）
f"CREATE (a)-[:{rel_type} {{weight: row.weight}}]->(b)"

# ④ 最后删除陈旧节点（DETACH 会一并删掉它的关系）
"MATCH (n:KnowledgePoint) WHERE NOT n.id IN $ids DETACH DELETE n"
```

### 4.2 三个"为什么"

| 问题 | 答案 |
|---|---|
| 为什么先清关系、最后才删节点？ | 反过来的话，删节点会连带删掉刚建好的关系（`DETACH` 的语义） |
| 节点用 `MERGE`、关系用 `CREATE`？ | 节点要幂等；关系在 ① 已清空，此刻 `CREATE` 不会撞重复 |
| 为什么 `sync` 和 `upsert` 的顺序逻辑**长得一样**？ | 因为它们解决**同一个问题**：把"权威源"对齐到"派生副本"。**不同存储、同一套路**——先清/取快照 → 写入 → 清理多余 → 使其生效 |

> 这两个函数的相似性是**刻意的**：全量对齐是一套模式，不该每个存储各写一套。以后新增副本（比如再上一个搜索引擎）时，**照这个顺序抄**即可。

## 5. 本节小结

- 摄入侧四个关键函数的**共同套路**：**幂等**（`MERGE` / 全量对齐）、**显式失败**（长度校验）、**顺序敏感**（先快照/清空 → 再写 → 后清理 → 最后 flush）。
- `extract_knowledge_points` 的每个"多余条件"都对应一次真实踩坑：物理行拆分（`\f` 行号漂移）、`clause` 非空（挡噪音）、先归一化再匹配（康熙部首）、`^` 锚定（排除交叉引用）、遇"编"清空上下文（章号重新起算）。
- `add_edge` 用 `(min,max)` 做键 + `types` 数组 + 权重取 `max`：**一条边保留全部类型、权重表示"最强的那个理由"**。
- `upsert` 是全项目最教科书的代码：**长度校验防静默丢数据**、**先 flush 取快照再写**（否则清理静默失效）、**最后 flush 使其可见**。
- `sync` 与 `upsert` 是**同一套"全量对齐"模式**（清/快照 → 写 → 清多余 → 生效）——不同存储、同一顺序，可以照抄。
- 读这些代码的方法：**注释里写了坑的地方，就是设计意图所在**。

## 企业常见面试问答

**Q1：为什么读代码要先读注释？**

> 因为在这个项目里，**注释记录的是"为什么"，而代码只表达"是什么"**。比如 `flush()` 里那句"必须有 clause：章/节标题本身不是知识点（页眉噪音曾让 34 个章标题单独成点）"——只看 `if buf and chapter and clause and body` 这行，你会觉得"clause 非空"是个莫名其妙的条件；读了注释才知道它是在挡一类具体的脏数据。同类例子还有 `upsert` 里"顺序不能颠倒"的注释——它解释了为什么 `flush` 出现在 `upsert` **之前**，而这个顺序从代码本身完全看不出来（两种顺序都能跑，只是其中一种会静默出错）。所以我读陌生代码的顺序是：**先看注释里带"曾/踩过/否则/注意"的句子，那些地方通常是设计的薄弱点，也是理解门槛所在。**

**Q2：`upsert` 里那个长度校验真的必要吗？看起来只是防御性编程。**

> 它是必要的，而且防的是一个**会静默丢数据**的场景。`zip(nodes, vectors)` 在长度不等时**按短的一侧截断、不报错**。如果节点 1465 个、向量只有 1400 条：写入的只有 1400 条，然后 "清理陈旧主键" 那一步算 `existing - 新集合`，会把"在这 1400 条之外"的主键**全部当成陈旧删掉**——连那些"只是缺向量"的知识点一起删了。结果是集合里少了几十条，**没有任何报错**，只有 recall 悄悄下降。所以这里的判断不是"防御性编程"，而是**"这个错误一旦发生就不可察觉"**——凡是这类的，都应该在入口直接拒绝。相同的判断在别处也出现过：pipeline 里 Milvus 与 Neo4j 的写入失败都改成显式报错，而不是 `try/except` 后警告继续。

**Q3：为什么要 `flush` 两次？一次不够吗？**

> 两次的作用不同。**第一次 flush 在写入之前**——目的是让"之前**已经发生但尚未可见**的变更（上一次构建的写入/删除）先落定，这样随后读到的 `existing` 主键集合才是**真实快照**。如果跳过它，可能读到空的或不完整的集合，于是"清理陈旧主键"就清理错了对象，或者干脆什么都不清（静默失效）。**第二次 flush 在写入之后**——目的是让本次写入与删除**立即对检索可见**，否则刚建完库去检索会查不到数据。所以一次是"让过去可见"、一次是"让现在可见"，缺哪一个都会出问题——而**两者都不报错**，所以这个顺序必须有注释、最好还有测试卡住（我们用带可见性延迟的假 client 做了这件事，见 6.1）。

**Q4：`add_edge` 里权重为什么用 `max` 不用求和？**

> 因为**权重表达的是"这条关系的强度"，不是"被发现了多少次"**。假设 46 条和 38 条之间既被 `crossref` 命中（权重 1.5）又被 `semantic` 命中（余弦 0.83）：如果求和得到 2.33，这个数就没有明确含义了——它既不是"引用强度"也不是"语义相似度"，后续的 `分数 = 种子分 × 边权 × decay^hop` 会因此失真；而且加了第三类边（比如以后加"同节"）权重会继续膨胀，让不同版本之间的权重不可比。取 `max` 的语义很清晰：**"这条边最强的那个理由有多强"**——46 和 38 之间最强的理由是"46 明确引用了 38"（1.5），所以它在扩展时优先被带出。这也和"类型单独保留"是配套的：**类型说明"有哪些理由"，权重说明"最强理由有多强"**，两者都不该被合并掉。
