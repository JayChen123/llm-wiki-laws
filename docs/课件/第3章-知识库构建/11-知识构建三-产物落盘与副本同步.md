# 3.4 知识构建（三）—— 产物落盘与副本同步

> 定位：摄入的"最后一公里"——三份产物各自落到哪里，谁是权威源、谁是派生副本，以及**改了知识源为什么必须重跑**。

本节目标：

1. 讲清"**权威源 vs 派生副本**"这条贯穿全项目的分工线；
2. 看懂 `wiki/` 人读视图的构成（全量索引 + 日志 + 少量示例页）以及它**为什么不参与检索**；
3. 掌握向量写入 Milvus 的**全量对齐 + 清理陈旧主键**，以及那个必须 `flush` 的顺序陷阱；
4. 理解"幂等全量重建"的含义与运维后果。

---

## 1. 三份产物与那条分工线

摄入跑完，落盘的东西有四样，角色完全不同：

| 产物 | 角色 | 谁读它 | 能否重建 |
|---|---|---|---|
| `knowledge_graph.json` | **权威源** | 人（diff/审计）+ 同步源 | 可以从 md 重建 |
| Neo4j | 图的**派生副本** | **查询时读它**（`kb.load()`） | 可以从 json 重建 |
| Milvus（`llm_wiki_laws`） | 向量的**派生副本** | 召回时读它 | 可以从 md 重建（要重编码） |
| `wiki/` | **人读视图** | **谁也不读**（只给人看） | 可以从图谱重建 |

> 一句话记住：**只有一个权威源（json）；能"随时重建"的一律是副本或视图**。副本不一致时以权威源为准、重跑同步，而不是去"猜哪边对"。

这个分工带来一个必须接受的运维后果：**派生副本不会自己发现知识库变了**。改了 PDF/md 就必须重跑 pipeline；改了 json 就必须重跑 `sync_graph`。系统刻意不做"自动发现"（原因见本节最后的历史教训）。

## 2. `wiki/` 人读视图：只落索引与示例页

`wiki/` 的定位在第 1 章就定过——**人读视图，不参与检索**。基于这个定位，v2.0 做了一个取舍：

```python
WIKI_SAMPLE_REFS = [
    ("劳动合同法", "第一条"),          # 无"编"的基础形态
    ("劳动合同法", "第十九条"),        # 试用期（概念导航命中）
    ("劳动合同法", "第三十八条"),      # crossref 被引方
    ("劳动合同法", "第四十六条"),      # crossref 引用方（引第三十八条）
    ("劳动合同法", "第八十五条"),      # 与劳动法同条号的消歧样本
    ("劳动法", "第四十四条"),          # 加班费（跨法概念导航）
    ("民法典", "第一条"),              # 有"编"：title 带"第一编 总则"
    ("民法典", "第五百一十一条"),      # 民法典内部引用链
    ("民法典", "第一千二百五十四条"),  # 千位条号 + 编名（高空抛物）
    ("民法典", "第一千零七十七条"),    # 离婚冷静期（概念导航命中）
]
```

落盘三样：

| 文件 | 内容 | 是否全量 |
|---|---|---|
| `wiki/index.md` | **核心概念导航** + 按源文档分组的**全量**目录（有"编"的法律按 **编→章 两级**；仍用 `[[KP_xxx]]` 双链写法） | **全量**（1465 条都在） |
| `wiki/log.md` | 构建日志（一句话：时间 + 知识点数 + 边数） | — |
| `wiki/concepts/KP_*.md` | **只落盘 `WIKI_SAMPLE_REFS` 的 10 个示例页** | **示例** |

为什么这么设计？因为**知识点页不参与检索**（检索读 Neo4j + Milvus），全量落盘 1465 页只是重复劳动（此前 `wiki/` 体积 5.9MB，清理后 176KB）。保留 10 个示例页，是为了讲课时能演示"**一条法条长什么样、它连了谁、边是什么类型、权重多少**"。

一个实现细节值得学：**示例清单写 `(法律, 条文)` 而不是硬编码 `KP_xxx`**。因为知识点编号会随"知识源增删"重新分配——今天 `KP_1459` 是高空抛物，明天加了新法律就可能不是了。而 `(法律, 条文)` 在建库时用 `_resolve_concept()` 解析，**始终指向正确的那一条**；未命中的条目跳过并打印提示。

`wiki/concepts/KP_1459.md` 长这样（民法典第一千二百五十四条）：

```markdown
---
id: KP_1459
title: 第七编 侵权责任·第十章·第一千二百五十四条
part: 第七编 侵权责任
chapter: 第十章
source: 中华人民共和国民法典.md L9475-9489
keywords: 建筑物和物件损害责任, 侵权责任, 侵权人, ..., 高空抛物, 高空坠物
---

# 第七编 侵权责任·第十章·第一千二百五十四条

禁止从建筑物中抛掷物品。……（正文）

## 关联知识点

- [[KP_1457]] （semantic/sibling，权重 1.0）
- ...
```

> 注意 `title` 自带编名"第七编 侵权责任"——这是多法库的必需品，也是 3.2 里"编必须参与分组"的延伸。

## 3. 向量写入 Milvus：全量对齐与陈旧主键

### 3.1 建集合与索引

```python
store.ensure_collection()
# 不存在则建：kp_id VARCHAR(主键) + title/source(标量) + vector FLOAT_VECTOR(1024)
#              索引 HNSW(M=16, efConstruction=200) + 度量 COSINE
# 已存在则**校验维度**，不一致直接重建
```

维度校验不是多余的：`EMBED_DIM` 改了（比如换模型）而集合还是旧的，写入会报错或静默错位——早失败比晚失败好。

### 3.2 "全量对齐"是什么意思

```python
written = store.upsert(graph["nodes"], vectors)
```

`upsert` 做三件事：

1. 写入当前全部节点及其向量；
2. **删除集合里已不在当前知识库中的陈旧主键**；
3. 校验：**节点数与向量数不一致直接报错**。

第 3 点是防一个隐蔽 bug：如果两者长度不等，`zip(nodes, vectors)` 会**静默截断**，于是写入的是"前 N 条"，而后续"清理陈旧主键"又会把剩下的全删掉——数据静默丢失。所以宁可报错。

### 3.3 那个必须 `flush` 的顺序陷阱

Milvus 的**写入与删除都要 `flush` 之后才能被 `query` 查到**。于是"清理陈旧主键"的语句顺序**不能反**：

```
① flush 并取出"旧主键集合"     ← 必须先取快照
② upsert 写入新向量
③ flush（让写入可见）
④ 按 ① 的快照 delete 陈旧主键
```

如果写成"先 upsert 再取旧主键"，那么取到的是**空集**（写入尚未 flush，查不到），清理就**静默失效**——集合里会长期残留已经不存在的知识点 id。

这件事我们踩过两次：一次在知识向量库，一次在长期记忆库（`UserMemoryStore.clear()` 一开始漏了 `flush()`，真实 Milvus 上"清除我的数据"**看似成功、其实延迟生效**）。

> 工程上带走的经验：**假 client 必须忠实模拟"未 flush 查不到"**，否则这类顺序问题在单测里会蒙混过关。我们的 `test_milvus_store.py` 就是用一个带**可见性延迟**的假 client 把顺序卡住的。

## 4. 幂等重建：从 `.npy` 缓存的历史包袱讲起

### 4.1 为什么废弃了 `.npy` 文件缓存

早期实现把知识点向量存成 `wiki/knowledge_vectors.npy`，命中判断是**"文件是否存在"**。这个判定方式埋了一个大坑：

> 民法典入库后，图谱已经 **1238** 个节点，而缓存文件还是旧的 **205** 行。程序**不报错**——`VectorRetriever` 照常加载，只是永远**只在前 205 个节点里排序**。也就是说：**民法典的语义召回长期静默失效**，直到有人注意到 recall 不对。

修法是换成 Milvus + 全量对齐：集合内容与当前知识库**强制一致**（多余的删掉、缺的写入），不再有"文件存在即命中"这种弱判定。

### 4.2 "幂等全量重建"到底意味着什么

| 阶段 | 策略 |
|---|---|
| PDF → MD | **增量**（raw 里已存在同名 md 就跳过） |
| MD → 知识点 → 图谱 → Wiki | **全量幂等重建**（md 更新即生效） |
| 向量 → Milvus | **全量对齐写入** + 清理陈旧主键 |
| 图谱 → Neo4j | **全量对齐**（先清关系、重建、删多余节点） |

"幂等"的好处是：**跑一次和跑十次结果一样**，所以不用担心"要不要先清库"；知识源变了直接重跑即可。代价是每次都要重新编码 1465 条向量（bge-m3 本地编码，无 API 成本，但有时间成本）。

### 4.3 派生副本的失败策略：显式失败

```python
sync_from_json(GRAPH_PATH)        # Neo4j：失败即抛错
store.upsert(graph["nodes"], vectors)   # Milvus：失败即抛错
```

两者都是派生副本，策略**统一为显式失败**。理由是：json 已经落盘，构建结果不会丢；但如果这里静默跳过，就会出现"json 已更新、副本还是旧图/旧向量"的不一致，而这种不一致**在查询侧看不出来**（`kb.load()` 只读副本）。

> 这条曾经不一致过：Milvus 写入原本 `try/except` 后警告继续，而 Neo4j 同步直接失败。同一个函数里两个派生副本的失败策略不一致，是很容易留下的技术债。

## 5. 代码走读：`write_wiki` 为什么只写索引与示例页

### 5.1 完整实现

```python
WIKI_SAMPLE_REFS: list[tuple[str, str]] = [        # 示例页白名单：(法律关键字, 条文)
    ("劳动合同法", "第一条"), ("劳动合同法", "第十九条"), ("劳动合同法", "第三十八条"),
    ("劳动合同法", "第四十六条"), ("劳动合同法", "第八十五条"), ("劳动法", "第四十四条"),
    ("民法典", "第一条"), ("民法典", "第五百一十一条"),
    ("民法典", "第一千二百五十四条"), ("民法典", "第一千零七十七条"),
]

def write_wiki(points, graph, wiki_dir=None, concepts_dir=None) -> None:
    """生成 index.md、log.md 与示例页 concepts/*.md。

    目录可注入：单测必须能指向 tmp_path，否则跑一次测试就往真实 wiki/ 写。
    """
    wiki_dir = WIKI_DIR if wiki_dir is None else wiki_dir
    concepts_dir = CONCEPTS_DIR if concepts_dir is None else concepts_dir
    wiki_dir.mkdir(parents=True, exist_ok=True)
    concepts_dir.mkdir(parents=True, exist_ok=True)

    (wiki_dir / "index.md").write_text(_index_md(points, graph), encoding="utf-8")
    for law, article in WIKI_SAMPLE_REFS:                 # 只写白名单里的示例页
        hit = _resolve_concept(law, article, points)
        if hit is None:
            print(f"[wiki] 示例条文未命中，已跳过：《{law}》{article}")
            continue
        p = next((x for x in points if x.id == hit[0]), None)
        if p is not None:
            (concepts_dir / f"{p.id}.md").write_text(_concept_md(p, graph), encoding="utf-8")
    (wiki_dir / "log.md").write_text(...)
```

### 5.2 四个设计点

| 设计 | 理由 |
|---|---|
| **示例清单写 `(法律, 条文)`，不硬编码 `KP_xxx`** | 编号会随知识源增删**重新分配**——今天 `KP_1459` 是高空抛物，加了新法律就可能不是了。而 `(法律, 条文)` 在建库时用 `_resolve_concept()` 解析，**始终指向正确的那一条** |
| **未命中就跳过 + 打印提示** | 换了知识源后示例清单可能失效；**打印出来比静默少几页好**。另外有一条测试专门断言"清单对真实图谱必须全部命中"，防止条号写错 |
| **`wiki_dir` / `concepts_dir` 可注入** | 否则跑一次测试就往**真实 `wiki/`** 写（和"测试污染 `logs/qa.log`"是同一类问题，6.1 详述）。可测试性要在设计时留口子 |
| **`index.md` 仍写全量** | 人读视图的价值就在于"能一眼看全"。只省掉逐条落盘 1465 个文件（5.9MB → 176KB），索引本身仍然完整 |

### 5.3 一段"降级但不静默"的示范

注意 `_resolve_concept` 返回 `None` 时的处理：**跳过 + 打印**，而不是"抛异常中断整个构建"，也不是"悄悄跳过"。

这两种极端都不好：

| 写法 | 后果 |
|---|---|
| 抛异常 | 一个示例条文写错（或换了知识源）→ **整个 wiki 落盘失败**，连 index 都没有 |
| 静默跳过 | 讲课时发现少了一页，**不知道为什么** |
| **跳过 + 打印**（本项目） | 构建照常完成，且日志里能立刻看到是哪一条没命中 |

> 这是"降级"的一个正确形态：**允许局部缺失，但必须让缺失可见**。和 4.1 的意图识别（放行但把原因写进 reason）、4.4 的反思（停止但记录 `reasons`）是同一个套路。

## 6. 本节小结

- 产物有四种角色：**json = 权威源**，Neo4j / Milvus = 派生副本，`wiki/` = 人读视图（谁都不读）。副本不一致就以 json 为准重跑同步。
- `wiki/` 只落盘 **全量索引 + 日志 + 10 个示例页**；示例清单用 `(法律, 条文)` 而非硬编码 `KP_xxx`（编号会重分配）。
- Milvus 写入是**全量对齐 + 清理陈旧主键**，且节点数与向量数不一致必须报错（防 `zip` 静默截断）。
- **`flush` 顺序不能反**：先取旧主键快照 → upsert → flush → delete。反了会对空集做清理、**静默失效**。
- `.npy` 缓存的教训：弱命中判定（"文件存在即命中"）会造成**静默错误**——Recall 长期偏低但不报错。换成 Milvus + 全量对齐后，集合与知识库强制一致。
- 派生副本**一律显式失败**，同一函数内策略要一致。

## 企业常见面试问答

**Q1：为什么不用一个库存完，非要"权威源 + 副本"？**

> 因为这几类数据的**访问形态**和**人机可读性**要求不同。权威源（json）要满足"人能读、能 diff、能审计"，所以是文件；Neo4j 要满足"按关系遍历"，Milvus 要满足"按相似度近邻"，所以是专门的库。真正的取舍在于：**你愿不愿意为"可审计"付出"维护同步"的代价**。在法律这种"答案错了要能被追责"的场景，我们认为值得——因为一旦检索结果不可解释，整个系统的可信度就没有立足点了。反过来，如果做的是商品推荐，权威源是文件就没什么必要。

**Q2：副本不一致了会怎样？系统怎么发现？**

> **系统不会自动发现**，这是刻意的。`kb.load()` 只读 Neo4j，不会去比对 json；检索侧也不会去校验 Milvus 里的 id 是否都在当前图谱里（`VectorRetriever` 顶多"跳过映射不到的 id"）。所以不一致的表现是**结果变差但不报错**——这很危险，因此我们用两条约定兜住：① 流程上规定"改了谁就重跑谁"（改 md → 跑 pipeline；改 json → 跑 sync_graph）；② 提供 `sync_graph --check-only` 做**两侧计数比对**，可以塞进 CI 或发布前检查。历史上 `.npy` 缓存就是因为没有这种"强制一致"机制，静默失效了很久。

**Q3：知识库更新的标准流程是什么？**

> 四步：① 把 PDF 放进 `data/src/`（或 md 放进 `data/raw/`）；② 跑 `uv run python -m app.ingest.pipeline`——它会增量转 MD、全量重建知识点与图谱、全量重写 Milvus 向量、重建 Wiki 索引、同步 Neo4j；③ 核对输出（知识点数 / 边数 / Milvus 条数）；④ 跑 `pytest` 与 `eval --skip-ragas`，确认新知识没有把老基线打坏（注意：**新增文档追加在末尾编号**，所以历史 KP 编号不变、基线仍可比）。如果需要新概念出现在"核心概念导航"里，先编辑 `ingest/concept_map.py` 再重跑——概念映射是**摄入期**产物，不能事后补。

**Q4：为什么每次都要全量重建，不做增量更新？**

> 因为**全量重建换来的是"确定性"**。增量更新要面对一堆边界问题：某条法条被删了、条号顺序变了、编号要不要重排、图谱里引用它的边怎么办……这些问题在"全量重建 + 幂等"下**全部消失**——每次都是从源文件推出一份完整一致的结果，跑一次和跑十次一样。代价是每次重新编码 1465 条向量（本地 bge-m3，无 API 成本）。在"知识源变化不频繁（法律不是每天改）+ 规模不大（1465 条）"的前提下，全量是明显更划算的选择；如果知识源是百万级、每天变更，那才需要考虑增量与版本化。
