# 3.3 知识图谱构建的常见问题

> 定位：把前两章（本体论 + 建库实现）里零散出现的坑，**按类型系统化归纳一遍**。这一节的目标不是记住每个坑，而是拿到一套"构建知识图谱时该警惕什么"的问题地图。

本节目标：

1. 建立一张**问题地图**：知识图谱构建的坑分五类，各有不同的症状与查法；
2. 掌握每类问题的**典型症状**（尤其是那些"不报错"的）；
3. 学会几个通用的自查手段（收数验证、分类统计、对比实验）；
4. 理解为什么"评测困难"本身就是知识图谱工程的一大问题。

---

## 1. 问题地图：五类坑

```
① 本体设计     结构层级、类型混淆、标识唯一性        → 图"建错了"
② 数据质量     噪音、漏切、错位、字符集              → 图"少东西"或"位置错了"
③ 关系抽取     阈值、覆盖率、边界、方向              → 边"多错了"或"少算了"
④ 参数与阈值   连通度、评估口径、成本                → 效果"悄悄变差"
⑤ 工程与规模   遍历爆炸、一致性、幂等、静默失败       → 系统"慢慢坏掉"
```

**五类的共同特征**：绝大多数**不会抛异常**。知识图谱工程的困难不在"调通"，而在"确认它是对的"。

---

## 2. 第一类：本体设计错误

### 2.1 层级漏层（最严重）

| | |
|---|---|
| **症状** | 边数异常膨胀；"看起来更连通" |
| **本项目案例** | 民法典 7 编各自从"第一章"起算，只按章号分组 → **1.97 万条假 sibling 边**，全库边数 21252 → **40992** |
| **根因** | 本体少了一层（"编"），于是两个不同的"第一章"被当成同一个 |
| **查法** | 看**分类统计**：sibling 占比是否与"同章条文对数"量级一致 |
| **预防** | 2.3 的 6 问清单第 2 条：**领域自带的层级有几层，一层都不能少** |

### 2.2 类型混淆（is-a 与 part-of 混用）

| | |
|---|---|
| **症状** | 逻辑上"推出"不该有的结论；或约束批量套用错对象 |
| **例子** | 把"第一条 part-of 第一章"写成 is-a → 推出"第一条有章号" |
| **根因** | 2.2 讲的两种层级语义不同（is-a 继承属性，part-of 不继承） |
| **预防** | 定义层级时明确问："这是'是一种'还是'是一部分'" |

### 2.3 标识不唯一

| | |
|---|---|
| **症状** | 张冠李戴——引用/展示时指向了另一部法律的同名对象 |
| **本项目案例** | 三部法律**都有第 85 条、98 条、46 条**；若引用只写"第四章·第八十五条"，LLM 无法分辨是哪部法 |
| **根因** | 把"局部唯一"的标识当成了"全局唯一" |
| **预防** | 标识要么全局唯一（`KP_046`），要么**带限定**（"中华人民共和国劳动合同法·第四章·第八十五条"） |

### 2.4 新类型硬塞进旧公理

| | |
|---|---|
| **症状** | 公理开始出现"除非是 X 节点"的例外 |
| **例子** | 若把"概念"做成节点：`sibling`（同编章）与 `crossref`（正文引用）对它都无意义 |
| **判断** | **当一条公理需要不断加例外时，通常说明这个东西不该放进这套公理体系**（2.3 的讨论） |

## 3. 第二类：数据质量

### 3.1 噪音混入

| | |
|---|---|
| **症状** | 出现"不该有"的节点或正文被污染 |
| **本项目案例** | 页眉噪音（`www.npc.gov.cn`、`8/23/2020`）挂在章标题下 → **34 个 clause 为空的垃圾知识点**；"分编"标题被并进上一条正文 → **污染 6 条条文** |
| **兜底** | `flush()` 要求 `clause` 非空（挡住空条文）；分编只作结构边界 |
| **查法** | 抽样看节点标题与正文；统计"clause 为空的节点数"（应为 0） |

### 3.2 漏切（最隐蔽）

| | |
|---|---|
| **症状** | **数量不对**，其余一切正常 |
| **本项目案例** | `CN_NUM_CHARS` 缺"千" → 民法典从第 1000 条起整段漏切，只抽到 **999/1260**，丢掉 261 条 |
| **根因** | 中文数字字符集不全；而条号跨过了 1000 |
| **查法** | **收数验证**：1465 = 1260 + 107 + 98，对不上立刻发现 |
| **预防** | 断言"每个区间都在"（不只是总数） |

### 3.3 字符变体

| | |
|---|---|
| **症状** | 正则一条都匹配不上；或部分条文莫名丢失 |
| **本项目案例** | 法律 PDF 的"第⼀条"用的是**康熙部首变体** `⼀`（U+2F00），眼睛看不出来，正则不认 |
| **处置** | 匹配前做 NFKC 归一 + 手工映射（⺠→民、⻅→见、⻓→长、⻔→门） |

### 3.4 位置信息错位

| | |
|---|---|
| **症状** | 溯源对不上——按记录的行号去原文找不到 |
| **本项目案例** | 源文件含换页符 `\f`，`splitlines()` 把它当换行 → 行号比编辑器实际**大 129 行**（民法典末尾） |
| **处置** | 按物理行（`\n`）拆行、行内再按 `\f` 分段并**共用同一行号** |
| **为什么重要** | 行号是"引用可核验"的落点（4.5）——行号错了，溯源就是假的 |

## 4. 第三类：关系抽取

### 4.1 统计关系的"阈值困境"

这是知识图谱里最经典的矛盾：**阈值低了噪音淹没有用信息，高了又漏掉真关系。**

| 阈值 | 后果 |
|---|---|
| 余弦 0.65（本项目实测） | 图谱**近全连接**——大量弱相关边把扩展结果稀释掉，recall 反降 |
| 余弦 0.85 | 许多真正相关的条文（表述差异大）连不上 |

**处置原则**：

1. 阈值要**按效果调**（看 recall），不按"看起来合不合理"调；
2. 调之前先看**度数分布**（每个节点平均连多少边）——分布失控说明阈值不对；
3. **确定关系不要设阈值**（结构、引用是"是/否"，不该有模糊地带）。

### 4.2 确定关系的覆盖率可能很低

| | |
|---|---|
| **事实** | 全库只有 **97 处** crossref 引用，涉及 **68/1465** 个知识点（约 4.6%） |
| **含义** | "靠引用关系做多跳"只能覆盖很小一部分问题——**别把某个机制的覆盖率想高** |
| **本项目的验证** | 反思机制实测只有 2/35 条用例真正补到条文（4.4）——与这个覆盖率吻合 |

> 这是知识图谱工程里常见的**期望偏差**：设计了一个机制，就默认它到处都在起作用。**先量出覆盖率，再判断这个机制值不值得留。**

### 4.3 关系方向：文本里没有的，不要硬造

| | |
|---|---|
| **症状** | 有向关系退化成无向，或方向全是反的 |
| **本项目案例** | JSON 边的 `source/target` 是 **id 字典序**（97 条 crossref 边全部 `source < target`），**根本没有方向信息** |
| **处置** | 在派生副本（Neo4j）同步时，用**与建边同一份实现**从正文解析真实方向（2.4/3.5） |
| **原则** | 方向是"让副本更好用"的信息 → **在派生时算出来，不要塞回权威源** |

### 4.4 跨边界关系：宁缺勿滥

| | |
|---|---|
| **本项目决定** | **跨法不建 crossref 边**——民法典条文不会引用劳动法条文 |
| **理由** | 文本上不存在这种关系；硬连是"从语义相似倒推出来的假关系" |
| **通用原则** | **图谱的价值全在"关系是真的"**。少连几条只是覆盖率低，错连几条会污染整个下游 |

## 5. 第四类：参数与阈值

### 5.1 参数没接线（静默变差）

| | |
|---|---|
| **症状** | 完全不报错，只是效果比"设计值"差一点 |
| **本项目案例** | `kb.py` 构造检索器时**漏传** `EXPAND_K/EXPAND_HOPS/EXPAND_DECAY` → 长期沿用默认 `expand_k=3`（文档写着 5） |
| **怎么发现** | 日志里 `graph_expanded` **恒为 3**（而不是 5） |
| **预防** | 写"断言配置真的传到了使用者"的回归测试 |

### 5.2 评估口径盲区（改了参数指标不动）

| | |
|---|---|
| **本项目案例** | `EXPAND_K` 从 3 改到 5 → `recall@1/3/5/8` **逐位完全相同** |
| **原因** | eval 用 `--top-k 5`，`@8` 只看前 8 位（5 种子 + 前 3 扩展），多出来的扩展落在第 8 位之后 |
| **真实影响** | **生成上下文 13 → 15 块** |
| **教训** | **指标只覆盖它定义的那部分**。一个参数"改了指标不变"不等于它没用；想评估它，得调**评估口径**（比如 `--top-k`） |

### 5.3 成本账没算清

| | |
|---|---|
| **例子** | 反思机制听起来很贵，实际**95% 的提问零 LLM 调用**（无引用关系 → 直接停）；但它真正的增量也很小 |
| **教训** | 一个机制的"成本"和"收益"都要**量出来**，凭印象判断两头都会错 |

---

## 6. 第五类：工程与规模

### 6.1 遍历爆炸

| | |
|---|---|
| **风险** | 从种子出发，一跳几十个邻居、三跳就是几万条路径 |
| **处置** | **每跳剪枝**（只留 Top-K 继续往下）+ **分数逐跳衰减**（`decay^hop`）+ **跳数上限** |
| **通用原则** | 图遍历一定要有**预算**（跳数、条数、超时），不能让它自然穷尽 |

### 6.2 全量 vs 增量

| | |
|---|---|
| **本项目的选择** | **全量幂等重建**（每次从源文件推出一份完整结果） |
| **为什么** | 增量要处理"条文被删/顺序变了/编号要不要重排/引用它的边怎么办"——这些边界问题在全量重建下**全部消失** |
| **何时该用增量** | 知识源是百万级、每天变更时（本项目 1465 条、法律不常改，全量更划算） |

### 6.3 幂等与一致性

| | |
|---|---|
| **原则** | **权威源唯一，副本可重建**；改谁就重跑谁 |
| **本项目案例** | 改了 json 必须跑 `sync_graph`（`kb.load()` 只读 Neo4j，**不会**去比对 json） |
| **反面教材** | `.npy` 文件缓存按"文件是否存在"判定命中 → 民法典入库后缓存仍是旧的 205 行 → **语义召回长期静默失效** |

### 6.4 静默失败（最需要警惕的一类）

| 症状 | 处置 |
|---|---|
| 写入/删除后查不到（Milvus 要 `flush` 才可见） | 固定顺序：先取旧主键快照 → upsert → flush → delete |
| 测试污染生产日志（跑了 297 条假事件） | 注入 `NullLogger` + 回归测试；**任何写磁盘的函数都要能指定输出位置** |
| `MERGE` 退化成全表扫 | 建库时就建**唯一约束** |
| 假 client 比真实现"更好用" | **假实现必须忠实模拟真实约束**（如可见性延迟），否则顺序类 bug 在单测里蒙混过关 |

## 7. 为什么"评测困难"本身是个大问题

知识图谱构建有一个其他工程问题少有的特点：**很难自动判断"这张图建得对不对"**。

| 困难 | 说明 |
|---|---|
| **没有标准答案** | 边该不该连、连多少条算合理，没有唯一正确的对照 |
| **覆盖率不可验证** | "漏掉了多少本该有的关系"是无法直接测量的——你只知道已经建了多少 |
| **指标是间接的** | 我们只能看 recall@k 这类**下游指标**反推图的质量；图坏了但下游还能勉强工作，就很难察觉 |
| **人工检查成本高** | 21252 条边不可能逐条看 |

**本项目的应对（可以照搬）**：

| 手段 | 作用 |
|---|---|
| **收数验证** | 数量对不上立刻发现（1465 / 21252 / 30569） |
| **分类统计** | 四类边各多少条——占比突变说明有问题（假 sibling 边就是这样暴露出 1.97 万的） |
| **真实数据抽查** | 抽几个知识点，人工核对"它连了谁、对不对"（比如 `KP_046 ↔ KP_038` 的引用对） |
| **下游指标回归** | 任何改动都跑 `eval --skip-ragas` 对比历史基线 |
| **A/B 对比** | 有对照链路可切（`RETRIEVAL_MODE=reflect|bfs`）——改动前后各跑一遍 |

## 8. 六条通用方法论

从上面五类坑里提炼，可以带走的六条：

1. **本体先行**：动手写建图代码前，先回答 2.3 的 6 问（最小实体/层级有哪几层/哪层可能缺/有哪几类相关性/标识是否唯一/哪些假设只在单文档成立）。
2. **确定关系与统计关系必须分开**：前者是"事实"（可用作遍历依据），后者是"线索"（必须靠阈值与权重控制）。
3. **宁缺勿滥**：错连一条边的代价，大于少连十条。
4. **一切关键数字要能一眼看到**：收数、分类统计、覆盖率——**不报错的 bug 只能靠数字发现**。
5. **遍历必须有预算**（跳数/条数/超时），并使用显式路径而非"推理黑盒"，让每条结果可解释。
6. **量出覆盖率与增量再决定去留**：一个机制的"设计意图"和"实际贡献"经常差很远（反思 2/35 条就是例子）。

## 9. 本节小结

- 知识图谱构建的坑分五类：**本体设计 / 数据质量 / 关系抽取 / 参数阈值 / 工程规模**；它们的共同特征是**绝大多数不抛异常**。
- 本体设计错误最严重也最容易低估：**层级漏一层**（"编"）就产生 1.97 万条假边；**类型混淆**（is-a vs part-of）会推出错误结论；**标识不唯一**（多法同条号）导致张冠李戴；**新类型硬塞进旧公理**会让公理充满例外。
- 数据质量的隐蔽问题是**漏切与字符变体**（缺"千"丢 261 条、康熙部首导致一条都切不出），以及**位置信息错位**（`\f` 让行号漂移 129 行）。
- 关系抽取的核心矛盾是**阈值困境**：低了噪音淹没（0.65 近全连接），高了漏真关系。**确定关系不设阈值**；**跨边界关系宁缺勿滥**（跨法不建引用边）。
- 参数类问题的特点是**静默**：没接线（`EXPAND_K` 用了默认值）、**指标盲区**（改了参数 recall 逐位不变，真实影响在生成上下文规模）、成本收益都要量。
- 工程类问题：**遍历必须有预算**；**全量幂等重建**换取确定性；**权威源唯一、副本可重建**；**静默失败**最需要警惕（Milvus flush、测试污染日志、MERGE 全表扫）。
- **评测困难本身就是一大问题**——应对手段是收数验证、分类统计、真实数据抽查、下游指标回归、A/B 对比。
- 六条方法论：本体先行 / 确定与统计分开 / 宁缺勿滥 / 关键数字一眼可见 / 遍历有预算且路径可解释 / 量出覆盖率再决定去留。

## 企业常见面试问答

**Q1：构建知识图谱最难的地方是什么？**

> **确认它是对的。** 难点不在于"建起来"——把文档切分、抽关系、写进图库，工程上是很直接的；难的是**判断建出来的图对不对**，因为这类错误绝大多数**不抛异常**。举两个本项目的真实例子：`CN_NUM_CHARS` 缺了一个"千"字，民法典从第 1000 条起整段漏切、丢掉 261 条——程序完全正常运行，只是数据少了一半多的婚姻家庭编、继承编、侵权责任编；本体少了一层"编"，产生了 1.97 万条假边，图谱反而"看起来更连通"了。这两类问题的共同点是**只能用数字发现**——所以我们的做法是把关键数字全部量化并暴露出来：收数验证（1465 = 1260 + 107 + 98）、分类统计（四类边各多少条）、覆盖率（97 处引用 / 68 个知识点）、下游指标（recall@k 回归）。**知识图谱工程的功夫，一半花在"可验证性"上。**

**Q2：关系抽取的阈值怎么定？**

> 三条原则。① **确定关系不设阈值**：结构边（同章）和引用边（正文里的"第X条"）是"是/否"的判断，它们该是确定性的，不该有模糊地带。② **统计关系（关键词/语义）的阈值按效果调，不按直觉调**：我们在语义边上实测过——余弦 0.65 会让图谱**近全连接**，大量弱相关边在扩展时把真正相关的条文挤出去，recall 反而下降；调高到 0.75 才合适。所以调阈值的依据是**度数分布 + 最终 recall**，不是"看起来连得多不多"。③ **宁缺勿滥**：错连一条边会污染整个下游（扩展、反思、生成上下文），而少连一条边只是覆盖率低一点。特别地，**跨边界的假关系坚决不建**——比如跨法律的引用边，文本上根本不存在这种关系，硬连就是从"语义相似"倒推出来的假知识。

**Q3：为什么你们的图谱没有推理能力？**

> 这是一个**取舍**，不是缺陷。完整的知识图谱通常包含本体 + 推理（比如"本体声明 A 是 B 的子类，那么查 B 自动包含 A"）。本项目**有本体**（编→章→节→条的层级、四类关系的定义与权重、53 个概念映射、若干约束），但**没有推理机**——我们把需要"推导"的部分换成了**显式遍历**（BFS 多跳扩展）。三个理由：① **可解释性**——法律场景要求每条进上下文的条文都能说清"怎么来的"；BFS 的路径（从哪个种子、走哪条边、第几跳、得分多少）可以完整打进日志，而推理机给出的结论对用户是黑盒。② **确定性**——OWL 表达力越强计算复杂度越高（部分子集不可判定），而我们的扩展需要可控预算（每跳剪枝、跳数上限、超时即停），这些在图遍历里就是几个参数。③ **成本收益**——我们真正需要的"推理"其实就是多跳可达，30 行 BFS 就做完了。所以准确说法是：**这是一张有明确本体定义、但推理靠显式遍历的工程化知识图谱。**

**Q4：如果让你重做一遍，会有什么不同？**

> 两件事会提前做。① **本体设计单独评审一次**——本项目那个 1.97 万条假边的坑，根因是 v1.0 的"章号在本法内唯一"假设在民法典上失效了（7 编各自从第一章起算）。如果当时拿 2.3 那张 6 问清单过一遍（"领域自带的层级有哪几层？"），"编"这一层在动手写代码前就会被发现，而不是等边数虚高到 40992 才回头查。② **一开始就把"关键数字"做成可观测的**——收数、分类统计、覆盖率、日志里的三类来源（种子/图谱扩展/反思补取）。我们这个系统里有两个 bug（`EXPAND_K` 没传下去、以及边数异常）都是**靠日志和统计数字发现的**，而不是靠报错。如果一开始就把这些数字暴露出来，排查会快得多。反过来说，**我觉得做得对的两个决定**是：坚持"权威源唯一 + 全量幂等重建"（避免了增量更新的边界问题），以及所有会静默失败的地方都**显式报错、不做降级**。
