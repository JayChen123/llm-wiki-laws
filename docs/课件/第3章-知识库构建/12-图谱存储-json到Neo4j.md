# 3.5 图谱存储 —— knowledge_graph.json → Neo4j

> 定位：把"可 git diff 的 JSON 图谱"变成"可遍历的图数据库"。这一节是 v2.0 的核心增量，也集中了最多实现细节。

本节目标：

1. 说清"JSON 权威源 + 图数据库副本"这个组合为什么成立，而不是二选一；
2. 掌握建模：节点与**四类关系**（`:SIBLING`/`:KEYWORD`/`:SEMANTIC`/`:CROSSREF`），以及"一条多类型边拆成多条关系"；
3. 吃透 `:CROSSREF` 的**方向在同步时从正文派生**这一设计；
4. 避开 Neo4j 的两个必踩坑：**空列表不能作属性值**、**字典序 ≠ 数值序**。

---

## 1. 为什么要有图数据库

3.2 建好的图谱是一个 21252 条边的 JSON。它有两个优点（可 diff、可审计）和一个明显的短板：**不好遍历**。

```
要回答"沿交叉引用链走 3 跳以内能到哪些条文"，JSON 方案得：
  ① 把整个图谱读进内存   ② 自己建邻接表   ③ 手写 BFS   ④ 每跳自己去重与剪枝
Neo4j 方案：
  MATCH (a {id: $id})-[:CROSSREF*1..3]->(b) RETURN b
```

所以答案不是"用图库取代 JSON"，而是**各司其职**：

| | `knowledge_graph.json` | Neo4j |
|---|---|---|
| 角色 | **权威源** | **查询副本（派生）** |
| 面向 | 人（diff / 审计 / code review） | 程序（遍历 / 扩展 / 引用链） |
| 变更 | 由 pipeline 全量重写 | 由 `sync_graph` 从 json 全量对齐 |
| 挂了会怎样 | 构建中断（它是产物） | 查询报错（无降级，见下） |

> 关键约定：**查询链路只读 Neo4j**（`kb.load()`），所以**改了 json 必须重跑同步**，否则会出现"json 已更新、Neo4j 还是旧图"的**静默不一致**。系统不会自动发现——这是刻意的。

---

## 2. 建模：节点与四类关系

### 2.1 节点

标签 `KnowledgePoint`，属性与 JSON 字段**一一对应**：

```python
# sync() 里的节点写入（批量 UNWIND）
"UNWIND $rows AS row "
"MERGE (n:KnowledgePoint {id: row.id}) "
"SET n.seq = row.seq, n.title = row.title, n.part = row.part, ... n.content = row.content"
```

注意 **`content`（正文）也要存进图库**，不是只存标题。原因：4.4 的"反思候选"要**解析正文里的引用**（"第四十六条…依照第三十八条"），候选就是从这里来的。

### 2.2 一条边 → 多条关系

JSON 里一条边可以带多个类型：

```json
{ "source": "KP_038", "target": "KP_046", "types": ["crossref", "sibling"], "weight": 1.5 }
```

同步时按类型**拆成多条关系**：

```python
_JSON_TYPE_TO_REL = {
    "sibling": "SIBLING", "keyword": "KEYWORD",
    "semantic": "SEMANTIC", "crossref": "CROSSREF",
}
```

于是：**关系数 30569 > 边数 21252**。这不是数据冗余，而是"图原生"的必然——拆开之后才能按类型遍历（比如"只走引用链"）。

### 2.3 为什么要拆类型

因为**不同边的语义与权重不同，遍历时经常要区分**：

| 关系 | 语义 | 典型用法 |
|---|---|---|
| `:SIBLING` | 同 (编, 章) 的结构关系 | 补全同章上下文 |
| `:KEYWORD` | 词面相近 | 主题召回 |
| `:SEMANTIC` | 语义相近 | 换说法也能召回 |
| `:CROSSREF` | **有向**的法条引用 | 引用链遍历（本节的亮点） |

其中只有 `:CROSSREF` 有方向，其余三类语义上无向。

## 3. `:CROSSREF` 的方向在同步时派生

这是本节最值得学的一个设计。

### 3.1 问题：JSON 里的方向是假的

JSON 边上虽然写了 `source` / `target`，但那是 **id 的字典序**，不是引用方向——97 条 crossref 边**全部满足 `source < target`**。也就是说 JSON 里根本没有"谁引用谁"的信息。

### 3.2 解法：同步时从正文解析方向

```python
# CROSSREF 的方向从正文解析（json 侧的 source/target 是 id 字典序，方向无意义）
from app.ingest.graph_build import CROSSREF_WEIGHT, crossref_map
...
"weight": crossref_pairs.get((min(src, tgt), max(src, tgt)), CROSSREF_WEIGHT)
```

`crossref_map()` 是**建边时用的同一份实现**（3.2 节讲过：它解析正文里的"第X条"）。同步时复用它，把关系的两端重新判定为：

```
引用方 -[:CROSSREF]-> 被引方
```

### 3.3 这个设计赢在哪

| 收益 | 说明 |
|---|---|
| 可以做**有向**遍历 | `MATCH (a)-[:CROSSREF*1..3]->(b)` 直接拿到"顺着引用链能到的条文" |
| **不用改 JSON 格式** | 权威源保持原样，方向是"副本侧派生"的——派生信息不进权威源，符合 3.4 的分工 |
| 仍然**忠实** | 只对"json 里确实存在的那对 crossref 节点"建方向关系，不凭空造边 |

> 一个可复用的判断：**当某条信息"不改变权威源的内容、只是让副本更好用"时，就应该在派生时算出来，而不是塞回权威源。** 方向就属于这类信息。

## 4. 读回：节点对归一化与 `seq` 排序

`kb.load()` 从 Neo4j 读回图谱，要**与 JSON 1:1 还原**才能保证 recall 可比。这里有两个细节：

### 4.1 节点对归一化（因为有向关系可能成对出现）

`:CROSSREF` 有向，同一对节点可能**双向各有一条关系**（A 引 B、B 也引 A）。而 JSON 里一条边只对应 `(min, max)` 这一个键。

所以 `load()` 与 `counts()` 都按 `(min, max)` **归一化后聚合**（`types` 取并集、`weight` 取 max）：

```
Neo4j:  A -[:CROSSREF]-> B   +   A -[:SIBLING]- B      （两条关系）
JSON :  {source: A, target: B, types: ["crossref","sibling"]}   （一条边）
```

结果：**边数与 JSON 恒等（21252）**，recall 不受影响。

### 4.2 `seq` 排序（字典序 ≠ 数值序）

`id` 形如 `KP_999` 与 `KP_1000`：

```
字典序："KP_1000" < "KP_999"     ← 因为第 4 个字符 '1' < '9'
数值序：999 < 1000               ← 我们要的顺序
```

**顺序会影响检索并列时的打破规则**，进而影响 recall 是否可比。所以节点上额外存一个数字序号：

```python
def _seq_of(kp_id: str) -> int:
    return int(kp_id.split("_")[1])       # KP_1000 → 1000
...
"SET n.seq = row.seq, ..."                # 读回时按 seq 排序，还原 json 顺序
```

> 这类"字符串 id 的排序陷阱"在任何 KP_xxx / user_10 / file_9 的编号方案里都会出现。教训是：**id 是标识，不是排序键**——要排序就单独存一个数值列。

## 5. Neo4j 的两个坑

### 5.1 空列表不能作属性值

```python
# ❌ 写入直接失败
SET n.keywords = []
# ✅ 为空存 None，读回再还原成 []
keywords = node.get("keywords") or []
```

Neo4j 不接受**空列表**作为属性值（历史上它对"空集合属性语义"的处理就是这样）。关键词为空的知识点不在少数，所以这个坑一定会踩到。

### 5.2 写入是"全量对齐"、且无降级

```python
# ① 先清空旧关系；② 按新图重建关系；③ 最后删掉不在新图中的节点
"MATCH (n:KnowledgePoint) WHERE NOT n.id IN $ids DETACH DELETE n"
```

- `DETACH DELETE` 会一并删掉节点的关系，所以顺序上要先把新关系建好再删多余节点。
- **无降级**：Neo4j 不可用即报错（`kb.load()` 若读到空图会明确提示"先跑同步"），不静默退回读本地文件。理由同 3.4：静默降级会带来"以为在用图库、实际在读旧文件"的不可控状态。
- 批量提交：写入用 `UNWIND $rows` 分批（有批量大小常量），避免单事务过大。

## 6. 同步命令与自检

```bash
uv run python -m app.ingest.sync_graph              # json → Neo4j
uv run python -m app.ingest.sync_graph --check-only # 只比对两侧计数，不写入
```

`--check-only` 是**运维自检**：比对"json 边数 / 关系数"与"Neo4j 侧计数"，快速发现不同步。建议的检查点：

| 时机 | 动作 |
|---|---|
| 改了 `knowledge_graph.json` | 跑一次同步 |
| 改了 PDF/md | 跑 pipeline（内部会自动同步） |
| 怀疑不一致 | `--check-only` |
| 发布前 | `--check-only` + `pytest` |

## 7. 本节小结

- 组合策略：**JSON 是权威源（可 diff、可审计），Neo4j 是查询副本（可遍历）**；查询只读 Neo4j，所以改 json 必须重跑同步。
- 建模：节点 `KnowledgePoint`（**含正文 `content`**，反思候选要解析它）+ 四类关系；一条多类型边**拆成多条关系**，所以 **关系数 30569 > 边数 21252**。
- `:CROSSREF` 的**方向在同步时从正文派生**（复用建边同一份 `crossref_map()`），从而支持有向引用链遍历，**且不用改 JSON 格式**。
- 读回要保证与 JSON 1:1：**节点对按 `(min,max)` 归一化**（有向关系可能成对）、**用 `seq` 排序**（`KP_1000` 的字典序小于 `KP_999`）。
- 两个必踩坑：**空列表不能作属性值**（空关键词存 `None`，读回还原 `[]`）；写入是**全量对齐**且**无降级**。

## 企业常见面试问答

**Q1：为什么既留 JSON 又上图库，不嫌重复吗？**

> 因为它们的用户不同、优化目标也不同。JSON 的用户是**人**（要能 diff、能 review、能审计），图库的用户是**程序**（要能高效遍历关系）。重复的是数据，但换来的是"权威源永远可读可审计"+"查询侧永远高效"。更关键的是**方向**：不是"图库 + JSON 冗余备份"，而是"**JSON 权威 → 图库派生**"——json 变了，删掉图库重建一份即可，永远不会出现"两份都不知道谁对"的困境。所以这个组合不是冗余，是明确的**主从关系**。

**Q2：图库挂了系统还能用吗？**

> 不能，会直接报错。这是**刻意的**——`kb.load()` 只从 Neo4j 读图，读到空图会明确提示"先跑同步"，而不是退回读本地 json 装作没事。理由和我们不用 SQLite 降级记忆是同一个：**静默降级会产生"看起来在跑、实际用的是另一套数据"的状态**，这种 bug 最难查，也最伤可信度。所以在这一层我们选择"响亮地失败"。

**Q3：有向边怎么存？为什么不直接在 json 里写方向？**

> 三条理由：① **json 里本来就没有方向信息**——`source`/`target` 是 id 字典序（97 条 crossref 边全部 `source < target`），所以"写方向"等于要在摄入期**重新解析一遍正文引用**；② 那个解析逻辑已经存在（`crossref_map()`，建边时用的），同步时**复用同一份实现**可以避免"两处规则各自漂移"；③ 方向是"**让副本更好用**"的信息，不改变权威源内容——按 3.4 的分工，这类信息**就该在派生时算出来**，不该塞回权威源。所以最终是：json 保持原样，Neo4j 侧按 `引用方 -[:CROSSREF]-> 被引方` 建有向关系，并且只对 json 里确实存在的 crossref 节点对建，保证仍是**忠实副本**。

**Q4：`KP_1000` 和 `KP_999` 的排序问题，你是怎么发现的？**

> 是在做"读回结果与 json 逐条比对"时发现的：边数一致，但**节点顺序对不上**。根因是 `id` 是字符串，字典序下 `"KP_1000" < "KP_999"`（第 4 个字符 `1` < `9`）。而顺序会影响检索并列时的打破规则，进而让 recall 变得不可比——这是个"不影响正确性、只影响可比性"的隐蔽问题。修法是节点上存一个数值 `seq` 属性，读回时按它排序还原 json 顺序。**一般性教训：不要把 id 当排序键**，任何 `xxx_数字` 形式的标识都要单独存一个数值列，这在分页、增量同步、结果比对里都会遇到。
