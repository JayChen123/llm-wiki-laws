# 5.1 双层记忆 —— MySQL 短期 + 画像 + 长期向量

> 定位：让系统"记得住人"。这一节的重点不是把记忆做复杂，而是**守住两条红线**——记忆跨用户不泄漏、记忆不当法律依据。

本节目标：

1. 说清"短期 / 长期"各自解决什么问题，以及**为什么记忆绝不能并入检索词**；
2. 掌握短期记忆的表结构与"按需注入"策略（`MEMORY_INJECT_MODE=auto`）；
3. 掌握长期记忆的两条红线与实现手段（强制 `user_id` 过滤、只注入生成段落）；
4. 理解"不做降级"这个反直觉决定背后的教训。

---

## 1. 为什么需要记忆，以及记忆**不是**法律知识

### 1.1 两层记忆各解决什么

| | 短期记忆 | 长期记忆 |
|---|---|---|
| 存什么 | 当前会话的消息 | 用户画像 + 历史问答语义索引 |
| 存哪里 | MySQL `messages` | MySQL `user_profile` + Milvus `llm_wiki_user_memory` |
| 解决什么 | 多轮对话的**指代延续**（"那 / 具体 / 继续"）与连贯 | **跨会话**记住用户处境（"我在北京，试用期被辞退"） |
| 生命周期 | 会话内（删会话即清） | 跨会话（删会话时连带清空） |

### 1.2 红线一：记忆是"用户背景"，不是法律知识

这条要放在最前面说，因为它决定了整个记忆层的架构：

> **记忆只注入生成的"用户背景"段落，并标注"不得作为法律依据"；绝不并入检索词。**

两个理由：

- **并入检索会重演"串题污染"**：上一问是"劳务派遣"，这一问是"试用期最长多久"，把两者拼起来检索，会命中一堆劳务派遣条文（实测踩过，见第 3 节）。
- **可能让 LLM 把用户历史当法条依据**：用户上次说"我听说试用期最多 3 个月"，如果这句进了参考资料，模型可能把它当成法律事实来引用。

**记忆记住的是人，不是法。**

## 2. 短期记忆：MySQL `messages`

### 2.1 表结构

```sql
users         -- 账号
sessions      -- 会话
messages      -- (session_id, user_id, role, content, citations)   ← citations 是 JSON
user_profile  -- (user_id, fact)  UNIQUE(user_id, fact)             ← 画像，去重
```

字符集 `utf8mb4`（中文 + 表情都能存）。

### 2.2 接口

```python
add / recent / recent_user_queries / turn_count / clear / clear_user
add_fact / facts / ensure_user / ensure_session
```

分工很清楚：`recent` 给"生成时的对话历史"，`recent_user_queries` 给"检索词注入"，`add_fact`/`facts` 管画像。**所有接收 `user_id` 的方法都必须真的用它做过滤**——这是红线二的技术落点。

## 3. 检索词注入：只在"像追问"时才并入上一问

### 3.1 踩过的坑：无条件并入 → 串题污染

最早的实现很"简单直接"：

```python
search_query = " ".join(past_queries + [query])     # ❌ 总是并入上一问
```

它的用意是好的——处理"那 / 具体 / 继续"这类指代。但用户**换话题**时就出事了。实测场景：

| 轮次 | 问题 | 结果 |
|---|---|---|
| Q1 | "劳务派遣的用工单位有什么义务？" | 正常 |
| Q2 | "试用期最长多久？" | ❌ 命中混入 **KP_065 / KP_058 / KP_059**（全是劳务派遣条文） |

更糟的是**反思会顺着错话题继续补取**——错误被放大了一轮。

### 3.2 现状：三档策略 `MEMORY_INJECT_MODE`

```python
def build_search_query(query, past_queries, mode="auto") -> str:
    if mode == "off" or not past_queries:  return query
    if mode == "always":                   return " ".join(past_queries + [query])
    # auto：仅当"像追问"时并入
    return " ".join(past_queries + [query]) if _looks_like_followup(query) else query
```

| 模式 | 行为 | 用途 |
|---|---|---|
| `always` | 总是并入上一问 | 旧行为，保留作对照 |
| `off` | 从不并入 | 对照 |
| **`auto`**（默认） | **仅当"像追问"时并入** | 生产 |

`_looks_like_followup()` 的判据有两条：

1. **含指代词**（"那 / 具体 / 继续 / 它 / 这个"等标记词）；
2. **很短且不含法律实体词**——比如"那怎么办"、"具体呢"，这类省略式追问大概率指向前文。

### 3.3 修复效果

同一场景重测：

> Q2 的 **13 块**上下文**全是试用期条文**，无劳务派遣残留。

> 这条经验有普适性：**"看起来更聪明的兜底"（总是带上历史，显得更懂上下文）往往正是问题的来源**。处理指代要靠**判据**，不能靠"总是并上"这种偷懒的默认值。

## 4. 长期记忆：画像 + 历史语义索引

### 4.1 两个组成部分

| 组成 | 存哪 | 形态 |
|---|---|---|
| **画像**（结构化事实） | MySQL `user_profile` | `("user1", "在北京工作")`，`UNIQUE(user_id, fact)` 去重 |
| **历史问答**（语义索引） | Milvus `llm_wiki_user_memory` | "问题 + 答案"的向量，可按相似度召回 |

⚠️ 注意集合是**独立的**：`llm_wiki_user_memory`（用户记忆）与 `llm_wiki_laws`（法律知识）**分离**。这个分离是红线一的物理保证——不会出现"用户记忆混进法律知识库"的路径。

### 4.2 写入成本刻意压到零 API 开销

```python
# 向量用本地 bge-m3 编码（零 API 成本）
# 历史摘要直接取"问题 + 答案"，**不额外调 LLM**
```

这一点值得强调：很多系统做"记忆摘要"时会再调一次 LLM 把对话压缩成要点——那会让**每一轮问答都多一次 API 调用**。这里选择直接用问答原文（`MEMORY_SUMMARY_CHARS` 限制单条字数），成本为零。

### 4.3 召回

```python
MEMORY_RECALL_K = 3      # 注入生成的记忆条数
# 提问时按 user_id 过滤召回（画像 + 相似历史）→ 作为「用户背景」注入生成
# 并显式标注：**不得作为法律依据**
```

注入段落里的标注不是"免责话术"，它同时是：
- **给模型的指令**（别把它当法条引用）；
- **给用户的告知**（这段是背景，不是依据）；
- **给测试的断言点**（`test_long_term.py` 专测这一点）。

### 4.4 代码走读：`LongTermMemory.search` 的隔离与幂等

这一节的"红线"落到代码上只有几十行，但有两处设计值得单独看。

**① `filter` 是强制的、写在函数签名里。**

```python
def search(self, user_id: str, query: str, top_k: int = MEMORY_RECALL_K) -> list[dict]:
    """按 user_id 过滤 + 语义召回该用户的相关记忆。"""
    if not user_id or not query or self.embedder is None:
        return []
    ...
    hits = self._client.search(
        ...,
        filter=f'user_id == "{user_id}"',      # 红线：必须按用户隔离
    )
```

注意这个函数**只接受 `user_id`，不提供"不按用户查"的入口**——这不是"记得加过滤"，而是**设计上不给"忘了加过滤"的机会**。4.1 讲过的泄漏事故（SQLite 降级后端在 `facts()` 里漏了 `user_id`）正是"靠自觉"的后果。

**② 主键 `mem_id` 由 `user_id + 文本` 派生（幂等）。**

```python
def _next_id(user_id: str, text: str) -> str:
    digest = hashlib.sha1(f"{user_id}|{text}".encode("utf-8")).hexdigest()[:24]
    return f"{user_id[:24]}_{digest}"
```

| 性质 | 好处 |
|---|---|
| **确定性** | 同一用户写同一条记忆 → **同一个主键** → 天然幂等（重复写入不会产生重复记录），不需要额外去重逻辑 |
| **按用户隔离** | 主键里带 `user_id` 前缀，不同用户的相同文本**不会撞主键** |
| **不泄露原文** | 用哈希而不是原文，主键本身不含敏感内容（便于打印/排查） |

> 这是一个**很值得偷学的小设计**：用"业务字段的确定性哈希"做主键，一次性解决**幂等、隔离、不泄露原文**三个问题。相比之下，"自增 ID + 查重逻辑"要写更多代码、还多一次查询。
>
> 面试里如果被问"记忆的主键为什么不用自增 ID"，这三点就是完整的答案。

## 5. 两条红线

| 红线 | 后果 | 实现手段 | 对应测试 |
|---|---|---|---|
| **检索必须带 `filter=user_id == "..."`** | 跨用户泄漏——A 用户看到 B 用户的记忆 | Milvus 检索强制过滤；MySQL 所有查询带 `user_id` | `test_long_term.py`（用户隔离）、`test_mysql_store.py`（断言 SQL 与绑定参数） |
| **记忆只注入生成的"用户背景"段落** | 重演串题污染；LLM 把用户历史当法条依据 | 只在生成阶段拼入；绝不进 `build_search_query` | `test_long_term.py`（注入段落标注）、`test_api_chat.py`（串题注入策略） |

还有一条配套操作：**删除会话时连带清空该用户的长期记忆**——否则"已删内容仍会被召回"，用户的删除意愿被违背。

## 6. 画像低频抽取

```python
PROFILE_EXTRACT_EVERY = 5        # 每 5 轮抽一次（0 = 关闭）
PROFILE_MODEL = "qwen-turbo"     # 轻量模型
```

```python
# profile_extractor.ProfileExtractor
# 只抽"用户自身相关、且跨会话仍有用"的事实，**排除敏感信息**；失败返回空列表
```

设计要点：

| 点 | 理由 |
|---|---|
| **低频**（每 5 轮） | 画像变化慢，每轮都抽是浪费；且这是唯一会额外调用 LLM 的记忆环节 |
| 用 **qwen-turbo** | 抽取是轻任务，不需要 qwen-max |
| **只抽跨会话有用的事实** | "我今年 30 岁"没用，"我在北京工作"有用（影响管辖、地方标准） |
| **排除敏感信息** | 账号、身份证、健康等不进画像 |
| **失败返回空列表** | 画像抽取失败不该影响主问答流程 |

## 7. 为什么不做降级（一个有代价的决定）

### 7.1 曾经的 SQLite 降级路径

早期为了让"没装 MySQL 也能跑"，实现了 SQLite 降级后端。结果它埋了一个**安全 bug**：

> 降级实现在 `facts()` 里**漏了 `user_id` 过滤**，导致**画像跨用户泄漏**。

抓到它的是单元测试（`test_alice / test_bob` 隔离测试）。这说明两件事：① 降级路径同样要守隔离红线；② **多一条代码路径 = 多一处可能漏掉安全约束的地方**。

### 7.2 现状：MySQL 是唯一后端

```python
# 不做 SQLite 降级、不做连接失败回退：连不上直接报错
```

理由：

| 理由 | 说明 |
|---|---|
| 数据不分叉 | 避免"一部分用户在 MySQL、一部分在本地文件" |
| 不做"假装在写" | 避免"以为在写 MySQL，实际写本地文件"的不可控状态 |
| 少一条要守红线的路径 | 多用户场景下，MySQL 一挂就会踩到降级路径的隔离问题 |

### 7.3 另一个 flush 坑

`UserMemoryStore.clear()` 最初**漏了 `flush()`**——在真实 Milvus 上表现为：

> "清除我的数据"**看似成功、其实延迟生效**（当时 `count()` 仍读到旧值）。

这和第 3.4 讲的向量库是**同一个坑**：**Milvus 的写入与删除都要 flush 之后才能被查到**。教训是同一个：假 client 必须忠实模拟"未 flush 查不到"，否则这类顺序问题在单测里会蒙混过关。

## 8. 本节小结

- **两层记忆**：短期（MySQL `messages`，解决多轮指代与连贯）+ 长期（画像存 MySQL、历史问答语义索引存**独立** Milvus 集合，解决跨会话）。
- **红线一**：记忆是"用户背景"，**绝不并入检索词**，只注入生成段落并标注"不得作为法律依据"。
- **检索词注入用 `auto`**：只在"像追问"（含指代词，或很短且无法律实体词）时并入上一问。无条件并入会导致**换话题时串题污染**（实测混入劳务派遣条文）。
- **红线二**：Milvus 检索与所有 MySQL 查询**必须带 `user_id` 过滤**，否则跨用户泄漏。
- 写入成本刻意压到零（本地 bge-m3 编码、不额外调 LLM 做摘要）；画像用 qwen-turbo **低频**抽取（每 5 轮），排除敏感信息，失败不影响主流程。
- **不做降级**：MySQL 是唯一后端，连不上直接报错——SQLite 降级路径曾因漏 `user_id` 过滤导致**画像跨用户泄漏**。
- **Milvus 写入与删除都要 `flush`**，否则"清除我的数据"只是延迟生效（这个坑在向量库与记忆库上各踩了一次）。

## 企业常见面试问答

**Q1：记忆会不会跨用户泄漏？**

> 我们把它当成**红线**来守，手段是"强制过滤 + 测试锁死"两层：① 所有 Milvus 检索**必须带 `filter=user_id == "..."`**，所有 MySQL 查询都带 `user_id` 条件——不是"默认带"，而是设计上就不提供"不带过滤"的调用方式；② 有专门的隔离测试（`test_alice / test_bob` 两个用户交叉验证）与"断言生成的 SQL 与绑定参数"的测试，保证过滤条件真的进了查询。历史上正是这套测试抓到了一个真实泄漏：SQLite 降级后端在 `facts()` 里漏了 `user_id` 过滤。所以后来我们**彻底删掉了降级路径**——因为多一条代码路径就多一处可能漏掉安全约束的地方。

**Q2：为什么不把记忆并进检索词？用户上次说的背景明明有用。**

> 因为**记忆和法条是两类东西**。并进检索词有三个坏处：① **串题污染**——上一问"劳务派遣"、这一问"试用期"，拼起来检索会命中一堆劳务派遣条文（实测过）；② **污染会被放大**——反思环节会顺着错话题继续补取条文，错得更远；③ **可能让模型把用户的历史陈述当成法律依据**——用户上次说"我听说试用期最多 3 个月"，这句要是进了参考资料，模型可能真的引用它。所以我们的分工很明确：**记忆只进生成的"用户背景"段落，并显式标注"不得作为法律依据"**。背景帮助理解用户处境（比如"我在北京"影响管辖判断），但结论必须落在检索出来的法条上。

**Q3：为什么要两层记忆，一个不够吗？**

> 它们回答的是不同时间尺度的问题。**短期**要解决的是"这一轮对话里用户在指代什么"——这需要**最近几条消息**，且必须是精确的（顺序、角色都不能乱），用关系库最合适。**长期**要解决的是"这个用户是谁、问过什么"——这需要**按语义相似度**从历史里挑相关的，用向量检索最合适。硬用一层会有问题：只存 MySQL 就没法按语义召回历史（只能按时间），只存向量就没法可靠地做"最近 N 条"和会话管理（顺序、事务、唯一约束都不擅长）。所以是**按访问形态分工**，不是重复存储。

**Q4：你为什么特意强调"不做降级"？这不是降低了可用性吗？**

> 是，这是**有意的取舍**。降级提高的是"能跑起来"的概率，牺牲的是"数据一致性与安全"。在我们的场景里这笔账不划算：① 记忆是**按用户隔离**的，降级路径必须重新实现一遍隔离约束，而我们已经在这上面出过一次真实泄漏；② 多用户 Web 场景下，MySQL 一挂就会踩到降级路径，等于把安全隐患放到最常走的路上；③ "以为在写 MySQL、实际写本地文件"这种状态**极难排查**，出问题时用户会发现"昨天的对话不见了"。所以我们选择**响亮地失败**。同样的判断在 Neo4j 上也是——`kb.load()` 读不到图就直接提示"先跑同步"，不静默退回读本地文件。一句话：**可用性问题可以商量，一致性与隔离问题不让步。**
