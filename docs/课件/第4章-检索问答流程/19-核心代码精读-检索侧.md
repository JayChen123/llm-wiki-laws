## 1. `HybridRetriever.search`：融合与轨迹

### 1.1 代码

```python
def search(self, query: str, top_k: int = 5, expand: bool = True) -> list[dict]:
    kw = self.keyword_retriever.search(query, top_k=top_k * 3)
    vec = (self.vector_retriever.search(query, top_k=top_k * 3)
           if self.vector_retriever is not None else [])

    rrf: dict[str, float] = {}
    for rank, (node, _) in enumerate(kw):
        rrf[node["id"]] = rrf.get(node["id"], 0.0) + 1.0 / (RRF_K + rank + 1)
    for rank, (node, _) in enumerate(vec):
        rrf[node["id"]] = rrf.get(node["id"], 0.0) + 1.0 / (RRF_K + rank + 1)

    ranked_ids = sorted(rrf, key=lambda k: -rrf[k])[:top_k]
    base = {nid: rrf[nid] for nid in ranked_ids}

    if expand:
        expanded_scores, expanded_hops = self._bfs_expand(
            ranked_ids, base, self.expand_hops, self.expand_k, self.expand_decay)
        extra_ids = sorted(expanded_scores, key=lambda k: -expanded_scores[k])[: self.expand_k]
    else:
        expanded_scores, expanded_hops, extra_ids = {}, {}, []

    self.last_trace = {
        "mode": "bfs" if expand else "seeds_only",
        "seeds": [self._brief(nid, base.get(nid, 0.0)) for nid in ranked_ids],
        "expanded": [self._brief(nid, expanded_scores.get(nid, 0.0), expanded_hops.get(nid))
                     for nid in extra_ids],
        ...
    }
```

### 1.2 三个实现要点

**① 每路取 `top_k * 3` 个候选，而不是 `top_k`。**

```
top_k = 10  →  每路先各取 30 个  →  RRF 融合  →  取前 10
```

为什么？因为 RRF **只看名次**。如果每路只取 10 个，那么"在关键词路排第 15、但在向量路排第 3"的条文**根本进不了融合池**——它会在第一步就被丢掉。取 3 倍是一个经验性的**候选池放大系数**：让两路的中间名次也有机会贡献分数，融合才真正起到"取两路共识"的作用。

> 这是一个典型的**"参数藏在代码里、设计文档不写"**的细节。它的取值（3）影响 recall，但不会在任何配置项里出现。

**② `expand=False` 是一个真实的调用约定。**

```python
# expand=False 只返回 RRF 融合后的种子（供反思式多跳接管后续检索）
```

反思链路（本节第 4 部分）需要在"只有种子"的基础上自己控制怎么扩展，所以它调 `expand=False` 拿基础种子。**同一个检索器要能服务两条链路**，靠的就是这个开关。

**③ `last_trace` 在函数内部记录。**

```python
self.last_trace = {"mode": ..., "seeds": [...], "expanded": [...]}
```

注意：**轨迹不是返回值，而是状态**。这样调用方不必层层透传一个"检索轨迹"参数，日志模块直接从 `retriever.last_trace` 读即可。代价是**它不是线程安全的**（并发检索会互相覆盖）——在当前单请求串行的场景下可以接受，但值得知道这个边界。

## 2. `_bfs_expand`：四个实现要点

### 2.1 代码

```python
def _bfs_expand(self, seeds, seed_scores, hops, per_hop_k, decay):
    adj = self._adjacency_map()
    visited = set(seeds)                                   # ① 种子不参与扩展
    frontier = [(nid, seed_scores[nid]) for nid in seeds]
    expanded, hops_of = {}, {}
    for hop in range(1, hops + 1):
        candidates = {}
        for nid, score in frontier:
            for nb, w in adj[nid]:                         # ② 只扫当前前沿的邻居
                if nb in visited:
                    continue
                s = score * w * (decay ** hop)             # ③ 分数随跳数衰减
                if nb not in candidates or s > candidates[nb]:
                    candidates[nb] = s                     # ④ 同一节点取最高分
        top = sorted(candidates.items(), key=lambda kv: -kv[1])[:per_hop_k]
        if not top:
            break                                          # ⑤ 无新候选 → 提前退出
        frontier = []                                      # ⑥ 下一跳只从幸存者出发
        for nb, s in top:
            expanded[nb], hops_of[nb] = s, hop
            visited.add(nb)
            frontier.append((nb, s))
    return expanded, hops_of
```

### 2.2 逐点说明

| 要点 | 为什么 |
|---|---|
| **① `visited` 用种子初始化** | 种子已在结果里，扩展时不该再被"发现"一次；同时防止沿环走回种子 |
| **② 只扫前沿邻居** | 不是"每跳扫全图"，而是"从上一跳的幸存者往外看一层"——这是 BFS 分层扩展的本义 |
| **③ `decay ** hop` 用跳数而不是累乘** | 从种子直接跳 2 跳的值 = `seed × w × decay²`，与"经由哪个中间节点"无关。**累乘会随路径不同而不同**，导致同一节点因为路径差异得到不同分数（不好解释也不好复现） |
| **④ 候选去重取 `max`** | 同一节点可能被多个前沿邻居指向，取最高分（与 `add_edge` 的权重取 max 同源思路） |
| **⑤ `if not top: break`** | 该跳没有新候选（邻域已探尽）就提前结束，不做无意义的空转 |
| **⑥ `frontier = top`（替换而非追加）** | **这是剪枝的关键**：下一跳**只从本跳的 Top-K 幸存者**出发，而不是"所有已扩展节点"。否则跳数一多就会指数膨胀 |

### 2.3 返回跳数的用途

```python
return expanded, hops_of        # hops_of: {kp_id: 第几跳}
```

跳数不是给打分用的，而是**给日志用的**——`graph_expanded` 里会带 `hop` 字段：

```
"graph_expanded": [{"id": "KP_038", "title": "...", "score": 0.0031, "hop": 1}, ...]
```

排查"某条法条为什么没进上下文"时，`hop` 能立刻告诉你：**它是没被扩展出来（不在列表里），还是扩展到了但分数太低被剪掉**。这是"可观测性设计"的一个小例子：**多返回一个字段，就少一次猜测。**

## 3. `MilvusVectorStore.search`：返回结构的处理

```python
def search(self, query_vector, top_k: int = 5) -> list[tuple[str, float]]:
    hits = self._client.search(
        collection_name=self.collection,
        data=[[float(x) for x in query_vector]],       # ① 批量接口，单条也要包一层
        limit=top_k,
        output_fields=["kp_id"],
        search_params={"metric_type": MILVUS_METRIC, "params": {"ef": 64}},
    )
    if not hits:
        return []
    out = []
    for hit in hits[0]:                                # ② 结果按"查询"分组：hits[0] 是第一个 query 的
        entity = hit.get("entity") or {}
        kp_id = entity.get("kp_id") or hit.get("id")   # ③ 两种取法兜底
        if kp_id is not None:
            out.append((str(kp_id), float(hit.get("distance", 0.0))))
    return out
```

三个细节：

| 细节 | 说明 |
|---|---|
| ① `data=[[...]]` | Milvus 的 `search` 是**批量**接口（支持一次传多个 query），所以单条也要包成二维 |
| ② `hits[0]` | 返回是"每个 query 一组结果"的嵌套结构，取第 0 组 |
| ③ `entity.kp_id or hit["id"]` | 不同版本的客户端/不同配置下，主键字段可能在 `entity` 里也可能在顶层。**两种都试**，比"赌一种"稳 |

> 这里体现的是**接口适配的常见形态**：外部 SDK 的返回结构会随版本变化，**在边界处做一次归一化，别让这种不确定性扩散到业务代码**。注意函数签名只承诺 `[(kp_id, score)]`——上层完全不知道 Milvus 的返回长什么样。

另外 `search_params={"ef": 64}` 是 HNSW 的**查询时**参数（`efConstruction` 是建索引时的参数，两者不同）：`ef` 越大越准但越慢。它和 `MILVUS_METRIC` 一样属于"知道有这回事、需要时再调"的参数。

## 4. `ReflectiveRetriever.search`：循环骨架与超集保证

### 4.1 代码（骨架）

```python
def search(self, query: str, top_k: int = TOP_K) -> list[dict]:
    # 基础上下文 = 与 bfs 模式完全相同的"种子 + 图谱扩展"（含 crossref 边），
    # 保证 reflect 的上下文是 bfs 的超集，不会因换链路丢掉 sibling/semantic 补充
    collected: list[dict] = self.hybrid.search(query, top_k=top_k, expand=True)
    seen = {r["id"] for r in collected}
    scores = {r["id"]: r.get("score", 0.0) for r in collected}
    rounds = 0

    while rounds < self.max_rounds:
        candidate_ids = self._candidate_ids(collected, seen)
        if not candidate_ids:
            reasons.append("无可跟进的引用关系，停止")       # 不调 LLM，直接停
            break
        result = self.reflector.reflect(query, collected, [self.id2node[i] for i in candidate_ids])
        reasons.append(f"[第{rounds + 1}轮] {result.reason}")
        if result.sufficient or not result.fetch_ids:
            break
        fetched = [i for i in result.fetch_ids if i not in seen]
        if not fetched:
            reasons.append("反思要取的条文均已在上下文中，停止")
            break
        for cid in fetched:
            parent = next((x for x in collected if cid in self.crossrefs.get(x["id"], [])), None)
            score = (scores.get(parent["id"], 0.0) if parent else 0.0) \
                    * CROSSREF_WEIGHT * (EXPAND_DECAY ** (rounds + 1))
            collected.append(_as_result(self.id2node[cid], score))
            seen.add(cid); scores[cid] = score
        rounds += 1

    self.last_trace = {"mode": "reflect", "seeds": base_trace.get("seeds", []),
                       "expanded": base_trace.get("expanded", []),
                       "fetched": fetched_brief, "rounds": rounds, "reasons": reasons[:4]}
    return collected
```

### 4.2 四个设计要点

**① 第一行就决定了"超集"性质。**

```python
collected = self.hybrid.search(query, top_k=top_k, expand=True)   # 与 bfs 完全相同的基础
```

反思**不从零开始**，而是先把 bfs 的完整结果作为基础上下文，再往上补。这一行就是 4.4 讲的"**拒绝纯反思**"教训的代码化——**换个链路不该丢掉 sibling/semantic 补充**。

**② `seen` 同时服务两个目的。**

- 作为 `_candidate_ids` 的入参 → **候选里排除已在上下文中的条文**（不做无用功）；
- 作为取回时的过滤 → 防止"模型反复要同一条"导致原地打转。

**③ 补取条文的分数是"名义分数"。**

```python
# 名义分数：沿用原 BFS 的公式（父分数 × 引用权重 × 衰减^轮次），
# 仅供展示与排序参考，不是 RRF 分数
```

这句注释很诚实：这些条文不是通过 RRF 融合来的，硬套 BFS 公式只是为了"有个可比较、可排序的数"。**知道一个数字是"名义上的"而不假装它是精确的**，比糊一个看似合理的分数要好——尤其在日志与前端都会展示 `score` 的场景下。

**④ `reasons[:4]` 截断、`rounds` 只增不减。**

- 日志里只留前 4 条停止理由，避免日志膨胀；
- `rounds` 与 `max_rounds` 构成硬上限（4.4 的第 4 个停止条件）。

## 5. 本节小结

- `HybridRetriever.search` 的三个要点：**每路取 `top_k * 3` 的候选池**（RRF 只看名次，池子小了中间名次根本没机会）、**`expand=False` 开关**（供反思链路接管）、**`last_trace` 作为状态而非返回值**（换来无需层层透传，代价是非线程安全）。
- `_bfs_expand` 六个实现要点：`visited` 用种子初始化、只扫前沿、`decay ** hop` 用跳数（而非累乘路径）、候选去重取 max、无候选提前退出、**`frontier = top` 替换而非追加**（剪枝的关键）。
- **返回 `hops_of` 是为日志服务的**——多一个字段，排查时少一次猜测。
- `MilvusVectorStore.search` 在边界处把外部 SDK 的返回结构**归一化成 `[(kp_id, score)]`**，不让版本差异扩散到业务代码；注意 `search_params` 里的 `ef` 是**查询时**参数，与建索引的 `efConstruction` 不同。
- `ReflectiveRetriever.search` 的第一行（拿 bfs 完整结果作基础）就实现了"**reflect 是 bfs 超集**"这条设计约束；`seen` 一物两用；补取分数是**名义分数**（诚实标注）；`reasons` 截断防日志膨胀。
- 一句话方法：**设计文档讲"为什么这么设计"，代码精读要看"为了这个设计，代码里不得不这么写的地方"**——候选池系数、`frontier` 替换、`hits[0]` 分组、名义分数，都属于后者。

## 企业常见面试问答

**Q1：`top_k * 3` 这个系数是怎么来的？为什么不写进配置？**

> 它是个**经验性的候选池放大系数**，作用是让两路的中间名次也能进入融合。因为 RRF 只看名次：如果每路只取 `top_k` 个，那么"关键词路第 15 名、向量路第 3 名"的条文会在第一步就被丢掉，而它恰恰是"两路共识"的典型候选——本来该被 RRF 抬上去的。取 3 倍是让池子足够容纳这种交叉命中。**"为什么不写进配置"这个问题问得好**：它确实影响 recall，严格说应该可调；目前的判断是"它不是需要按场景 A/B 的参数，而是一个固定的工程余量"，所以留在代码里。但这也是个**可改进点**——如果以后检索质量出现问题，这是一个该被拿出来测的旋钮。我一贯的看法是：**藏在代码里的魔数要么能说清理由（像这个 3），要么就该变成配置**。

**Q2：`_bfs_expand` 里最容易被写错的地方是哪一处？**

> **`frontier = top` 那一行——它是"替换"而不是"追加"**。写错的常见形态是 `frontier.extend(top)` 或者干脆不换、下一跳继续从所有已访问节点出发。后果是**指数膨胀**：一跳几十个邻居、三跳就是几万条路径，性能直接崩。这一行的含义是"**下一跳只从本跳的 Top-K 幸存者出发**"——即每跳都做一次硬剪枝，把"探索"限制在高分路径上。它和 `visited` 配合，才能保证遍历是"有预算的"（我把它算作知识图谱工程的六条方法论之一：**遍历必须有预算**）。另一个容易写错的是 `decay ** hop` 用跳数而不是沿路径累乘——累乘会让同一节点因为路径不同得到不同分数，不可复现也不好解释。

**Q3：为什么轨迹（`last_trace`）要用"状态"而不是"返回值"？**

> 主要是为了**避免层层透传**。检索链路是 `kb.search → HybridRetriever.search → _bfs_expand`，如果轨迹作为返回值往上带，那么每一层都要多返回一个值、每个调用方都要多接一个变量，而它**大多数调用方根本不关心**（只有日志模块关心）。用状态就干净得多：谁要看谁去读 `retriever.last_trace`。代价也很明确——**它不是线程安全的**：并发请求会互相覆盖这个字段。在当前"单请求串行"的场景下可以接受，但如果以后改成异步并发（README 的后续优化里就提到了"改为异步过程、增加并发能力"），这里必须改——要么加锁、要么把 trace 作为返回值或用 contextvar 传递。**所以这是一个"当前合理、但已经知道未来要改"的设计**，我倾向于在文档里把这类边界写清楚，而不是等它出问题。

**Q4：`ReflectiveRetriever` 第一行为什么是"复用"而不是"自己检索"？**

> 因为那正是 4.4 那次失败换来的教训。我们曾经把反思实现成**替代方案**——反思完全替代图谱扩展、候选只有引用关系——结果 **recall@8 从 0.9262 掉到 0.8548**，掉的全是 sibling / semantic 邻居带来的补充，因为它们不属于"引用关系"，在纯反思方案里进不了候选集。修法就是这一行：**先把 `hybrid.search(..., expand=True)` 的完整结果（与 bfs 模式一模一样）作为基础上下文**，反思只在其上做增量补取。这样**结构上保证了 reflect 是 bfs 的超集**——不会因为换链路而丢东西。这个设计还有一个好处：两条链路的 recall 完全一致（实测确实如此），所以**换链路不需要重新建立评估基线**。一句话：**"增强"应该建立在"已有能力"之上，而不是替换它。**
