## 1. `parse_intent`：三段式容错

模型被要求"只输出 JSON"，但**实际输出经常不干净**——可能包在 ```json 围栏里、可能前面加一句"好的，分类结果如下"、也可能干脆只回了一个枚举值。

```python
def parse_intent(text: str) -> IntentResult:
    """容错解析分类器输出：容忍 markdown 围栏与前后多余文字，解析不出则保守放行。"""
    # ① 先尝试从输出里"抠"出 JSON
    match = _JSON_RE.search(text or "")
    if match:
        try:
            data = json.loads(match.group(0))
        except json.JSONDecodeError:
            data = None
        if isinstance(data, dict):
            raw = str(data.get("intent", "")).strip().lower()
            for intent in Intent:
                if raw == intent.value:
                    return IntentResult(intent, str(data.get("reason", ""))[:200])

    # ② 退化：输出里直接出现枚举值（如模型只回了 legal_uncovered）
    lowered = (text or "").lower()
    for intent in Intent:
        if intent.value in lowered:
            return IntentResult(intent, "")

    # ③ 实在解析不出 → 保守放行
    return _UNPARSABLE
```

三段式的思路值得学：

| 段 | 策略 | 理由 |
|---|---|---|
| ① **用正则搜而不是 `json.loads(text)`** | 不假设输出"就是纯 JSON" | 模型加围栏/加前缀是常态，直接 `loads` 会失败 |
| ① **校验取值** | 不直接信任 `data["intent"]`，而是**逐个跟枚举比对** | 模型可能回 `"ANSWERABLE"`（大小写）、`"answerable "`（空格）——先 `strip().lower()` 再与枚举值精确匹配，比"自己写一堆 if"更稳 |
| ② **退化到子串匹配** | 输出里只要**出现过**枚举值就认 | 覆盖"模型只回了 `legal_uncovered` 一个词"这种情况 |
| ③ **兜底返回保守放行** | 解析不出 → 当"可答" | 4.1 的取舍：误拒的代价远大于误放。reason 里写清原因便于排查 |

> **这段代码的哲学**：**对模型的输出，"尽量理解"+"失败时按安全方向默认"**。两件事都要做——只做前者会在解析失败时崩，只做后者会浪费掉模型其实给对了的信息。

## 2. `IntentClassifier`：懒加载与"无 Key 即放行"

### 2.1 代码

```python
class IntentClassifier:
    """基于轻量 LLM 的意图分类器：任何异常都保守放行（ANSWERABLE）。"""

    def __init__(self, api_key=None, base_url=None, model=None, timeout=None):
        self.api_key = api_key or DASHSCOPE_API_KEY
        self.base_url = base_url or DASHSCOPE_BASE_URL
        self.model = model or INTENT_MODEL
        self.timeout = timeout or INTENT_TIMEOUT_S
        self._client = None                     # ← 注意：不在这里建 client

    def _get_client(self):                      # ← 懒加载
        if self._client is None:
            from openai import OpenAI
            self._client = OpenAI(api_key=self.api_key, base_url=self.base_url,
                                  timeout=self.timeout)
        return self._client

    def classify(self, query: str) -> IntentResult:
        """分类单条问题；失败一律放行，异常信息写进 reason 便于排查。"""
        if not self.api_key:
            return _UNAVAILABLE                 # ← 无 Key：直接放行，不发请求
        try:
            resp = self._get_client().chat.completions.create(
                model=self.model, temperature=0, messages=[...])
            ...
```

### 2.2 三个值得注意的决定

| 决定 | 理由 |
|---|---|
| **client 懒加载** | 构造函数里建 client 会让"没有 Key 的环境"连对象都造不出来；懒加载让**构造永远是安全的**，只有真正要发请求时才需要 client。这在测试里也方便（注入假的 classifier 时不需要 OpenAI 环境） |
| **无 Key 直接返回 `_UNAVAILABLE`** | 连"尝试发请求再失败"都不做——**失败路径要短**。而且 reason 是"分类器不可用，按可答放行"，日志里一眼能看出是"没配 Key"而不是"模型答错了" |
| **`timeout` 设在 client 上** | 3 秒超时是 4.1 的设计要点（分类要快）。设在 client 层面而不是每次请求传，保证**所有调用都受这个约束**，不会漏 |

### 2.3 异常处理的形状

```python
try:
    ...  # 发请求 + 解析
except Exception as exc:
    return IntentResult(Intent.ANSWERABLE, f"分类异常，按可答放行：{exc}")
```

三点：**捕获 `Exception` 而不是具体类型**（超时、网络、解析各种异常都要兜住）；**返回正常值而不是抛出**（调用方不必处理异常）；**把异常信息写进 reason**（否则"放行"这个决定事后无从解释）。

> 这是一个**很小的函数，但它的异常处理形状值得背下来**：`try → 成功返回 → except 返回安全默认 + 带上原因`。全项目的降级点（反思、画像抽取、生成失败）用的都是这个形状。

## 3. `_format_memory` 与 `generate_stream`：prompt 拼装

### 3.1 代码

```python
@staticmethod
def _format_memory(memories: list[dict] | None) -> str:
    """渲染长期记忆段落；空则返回空串（不产生多余标题）。"""
    if not memories:
        return ""                                       # ← 空就不输出标题
    lines = ["【用户背景（仅供个性化参考，**不得作为法律依据**，也不得列入引用）】"]
    ...

def generate_stream(self, query, contexts, history=None, memory=None):
    reference = self._format_contexts(contexts)
    memory_block = self._format_memory(memory)
    user_prompt = f"{memory_block}【参考资料】\n{reference}\n\n【问题】\n{query}\n\n请回答："
    messages = [{"role": "system", "content": SYSTEM_PROMPT}]
    messages.extend(history or [])                      # 对话历史
    messages.append({"role": "user", "content": user_prompt})
    stream = self.client.chat.completions.create(
        model=self.model, messages=messages, temperature=0.3, stream=True)
    for chunk in stream:
        if chunk.choices and chunk.choices[0].delta.content:
            yield chunk.choices[0].delta.content
```

### 3.2 逐点说明

| 点 | 说明 |
|---|---|
| **空记忆返回空串** | 不输出一个空的【用户背景】标题。看似小事，但**一个空的段落标题会让模型"试图填补它"**——这是 prompt 拼装的常见陷阱 |
| **标注"不得作为法律依据，也不得列入引用"** | 4.1 的红线在 prompt 层的落点。**同时约束了"怎么用"和"怎么引用"两件事** |
| **段落顺序：记忆 → 参考资料 → 问题** | 记忆在最前（背景），参考资料其次（依据），问题最后（紧邻"请回答"）。**把最需要模型关注的"依据"放在靠近指令的位置**，是 prompt 排布的常用技巧 |
| **`temperature=0.3`** | 生成需要一点表达多样性（比分类的 `temperature=0` 高），但不能太高——法律回答不该"发挥" |
| **`history` 直接 extend 成 messages** | 对话历史直接作为消息序列，而不是塞进 user prompt 的文本里——这样模型能正确区分"谁说了什么" |
| **`if chunk.choices and chunk.choices[0].delta.content`** | 流式的 chunk 里**可能没有 `choices`**（有些实现会发心跳/空块），必须判空再取，否则 `IndexError` |

> 最后一行是流式接口的经典坑：**不是每个 chunk 都带内容**。这类"接口约定之外的边界"必须在代码里显式处理，否则线上偶发崩溃且难以复现。

## 4. 本节小结

### 4.1 本节代码要点

- `parse_intent` 是**三段式容错**：正则抠 JSON → 退化到枚举值子串匹配 → 解析不出则保守放行。**对模型输出要"尽量理解 + 失败按安全方向默认"，两件事都要做。**
- `IntentClassifier` 的三个决定：**client 懒加载**（构造永远安全）、**无 Key 直接放行**（失败路径要短）、**timeout 设在 client 上**（所有调用都受约束）；异常处理形状统一为 `try → 成功返回 → except 返回安全默认 + 带上原因`。
- `_format_memory` **空则不输出标题**（避免模型"试图填补空段落"）；记忆段落显式标注"**不得作为法律依据，也不得列入引用**"；prompt 顺序为**记忆 → 参考资料 → 问题**，把依据放在靠近指令处；`temperature=0.3`（生成要一点多样性，但不能"发挥"）。
- 流式 chunk **可能没有 `choices`**，必须判空——接口约定之外的边界要在代码里显式处理。

### 4.2 这些代码的共同形状

回看本节精读的函数，它们的形状高度一致：

| 套路 | 出现位置 |
|---|---|
| **边界处归一化** | 康熙部首归一（3.1）、Milvus 返回结构归一（4.6）、`parse_intent` 容错（4.7） |
| **显式失败 vs 安全默认，按"失败伤到谁"决定** | 摄入侧写入**报错**；意图识别**放行**；反思**停止**；查询期 Milvus **降级** |
| **幂等** | `MERGE` 写节点（3.6）、全量对齐 |
| **顺序敏感的地方写注释** | `upsert` 的 flush、`sync` 的清理顺序、`frontier = top` |
| **多返回一个字段给日志** | `hops_of`（第几跳）、`reasons`（为什么停）、`last_trace`（三类来源） |
| **对模型输出"尽量理解 + 失败按安全方向默认"** | `parse_intent`、`parse_reflection`、`list` 型输出的解析 |
| **不让外部 SDK 的结构扩散** | `MilvusVectorStore.search` 只承诺 `[(kp_id, score)]` |

**如果只能带走一句话**：

> **这个项目的代码质量，主要体现在"对失败的处理"上——不是处理异常，而是处理"不报错的失败"**：静默失效的 flush 顺序、静默截断的 `zip`、静默变慢的 `MERGE`、静默漏切的字符集、静默失效的缓存命中。这些是全课程反复出现的同一类问题。

## 企业常见面试问答

**Q1：为什么要为模型的输出写这么多容错代码？直接把 prompt 写好不行吗？**

> 不行，因为**prompt 是"请求"不是"保证"**。你可以要求模型"只输出 JSON"，它绝大多数时候会照做，但总会遇到例外：加了 ```json 围栏、前面补一句"好的"、大小写不对、或者在你没预料到的输入上回了另一种格式。这类失败**概率低但一定发生**，而且发生时如果解析崩了，用户看到的是"系统坏了"，而不是"这次分类没成功"。所以我们的做法是**三段式**：尽量理解（正则抠 JSON → 退化到子串匹配）→ 实在不行按安全方向默认（保守放行）。**核心认知是：和 LLM 交互的边界，必须按"不可靠的外部服务"来对待**——和调第三方 API 一样，要容错、要有超时、要有降级。反过来，如果只靠"把 prompt 写好"，那你就是在赌模型每次都守规矩。

**Q2：为什么 client 要懒加载？直接构造函数里建不更简单？**

> 因为在**没有 Key 的环境**里，构造函数会直接失败——而那个环境**恰恰是最需要能构造出对象的**（比如测试、比如本地只想跑检索链路）。懒加载把"需要 client"这件事推迟到"真的要发请求"时，于是：① 没有 Key 也能构造出 classifier，`classify()` 会走 `_UNAVAILABLE` 分支正常返回；② 测试里注入假 classifier 时不需要动 OpenAI 的环境；③ `import` 阶段不会因为缺少配置而炸。**这是一个通用模式**：**把"必然失败的初始化"改造成"按需初始化 + 明确的降级路径"**。同类做法还有 `KB.load()` 里 Milvus 连不上就退化、`IntentClassifier` 无 Key 即放行——都是"让对象能安全地存在，把失败推迟到真正需要它的那一刻，并且那时有明确的降级行为"。

**Q3：你说的"不报错的失败"具体指什么？**

> 指**程序正常运行、结果却悄悄错了**的情况。这类问题在知识图谱系统里特别多，举几个本课程出现过的：`zip(nodes, vectors)` 在长度不等时**静默截断**（写少了数据）；Milvus 的 flush 顺序写反，陈旧主键清理**静默失效**（集合里留垃圾）；`MERGE` 没走索引**只是变慢**（不报错）；`.npy` 缓存按"文件存在"判定命中，导致语义召回**长期静默失效**；中文数字字符集缺"千"，民法典**静默漏切** 261 条；`EXPAND_K` 没传进构造函数，扩展规模**静默变小**。它们的共同点是**没有异常、没有日志、指标也不会立刻崩**，只是效果比设计差一点。所以我们的对策不是"更仔细地写代码"，而是**结构性的**：入口校验（长度不等就报错）、唯一约束（必须建）、关键数字可视化（收数、分类统计、覆盖率）、以及"断言配置真的传下去"的回归测试。**一句话：能报错的地方就报错，不能报错的地方就用数字把它显出来。**
