# 4.3 多跳检索（一）—— 图谱 BFS 扩展与 crossref

> 定位：种子召回了"最像的那几条"，但法律问题常常要靠**协同条文**才答得完整。这一节讲怎么顺着图谱把该带的条文带进上下文。

本节目标：

1. 说清"只召回种子"为什么不够，多跳到底补的是什么；
2. 掌握 `_bfs_expand` 的算法骨架（分层 + 每跳剪枝 + 分数衰减）；
3. 理解 **crossref 权重 1.5** 为何是让"被引条文"稳定进上下文的关键；
4. 正视已知局限：宽泛的"措施/责任"类问题会被泛主题稀释。

---

## 1. 为什么只召回种子不够？

举个具体的例子。用户问：

> "公司违法解除劳动合同，又不给经济补偿，我能主张什么？"

期望进上下文的核心条文至少两条：

| 条文 | 内容要点 | 检索能命中吗 |
|---|---|---|
| 劳动合同法 **第四十六条** | 用人单位应当向劳动者支付经济补偿的情形 | ✅ 大概率命中（"经济补偿"字面重合） |
| 劳动合同法 **第三十八条** | 劳动者可以解除劳动合同的情形 | ❓ 未必——用户没提"解除权"，且 38 条正文里也没有"补偿" |

问题就出在第二条：**它和这个问题高度相关，但内容相似度不高**。它在文档里离 46 条很远、用词也不同——**检索抓不到它，但图谱里有边**（46 条正文引用了 38 条）。

> 所以多跳补的不是"更相似的条文"，而是"**结构上、引用上相关但内容不像的条文**"。这个区别是理解多跳的钥匙：它靠的不是相似度，而是**关系**。

## 2. `_bfs_expand`：算法骨架

### 2.1 代码

```python
def _bfs_expand(self, seeds, seed_scores, hops, per_hop_k, decay):
    """从种子节点沿关联边 BFS 扩展多跳候选。
    节点分数 = 上层种子分数 × 边权重 × decay^hop；每跳只保留 Top per_hop_k 个候选。
    返回 (分数, 跳数)：跳数用于日志里说明"这条扩展是从第几跳带进来的"。"""
    adj = self._adjacency_map()
    visited = set(seeds)                          # 种子不参与扩展（避免自己扩自己）
    frontier = [(nid, seed_scores[nid]) for nid in seeds]
    expanded, hops_of = {}, {}
    for hop in range(1, hops + 1):                # ① 分层推进
        candidates = {}
        for nid, score in frontier:
            for nb, w in adj[nid]:                # ② 只看当前前沿的邻居
                if nb in visited:
                    continue
                s = score * w * (decay ** hop)    # ③ 分数 = 上层分 × 边权 × decay^hop
                if nb not in candidates or s > candidates[nb]:
                    candidates[nb] = s            # 去重取最大
        top = sorted(candidates.items(), key=lambda kv: -kv[1])[:per_hop_k]   # ④ 每跳剪枝
        if not top:
            break
        frontier = []
        for nb, s in top:
            expanded[nb], hops_of[nb] = s, hop
            visited.add(nb)
            frontier.append((nb, s))              # ⑤ 下一跳只从"本跳幸存者"出发
    return expanded, hops_of
```

### 2.2 图上看一次扩展

```
种子（Top-K=10，带 RRF 分）
   │
   │ hop=1：邻居候选 → 按分排序 → 取前 per_hop_k 个 ──┐
   ▼                                                  │ ← frontier 只留幸存者
第 1 跳扩展（≤5 个）                                   │
   │                                                  │
   │ hop=2：同上，但分数再乘一次 decay                 │
   ▼                                                  │
第 2 跳扩展（≤5 个）                                   │
   │                                                  │
   ▼ hop=3：同上 ────────────────────────────────────┘
第 3 跳扩展（≤5 个）
```

### 2.3 三个设计点

| 设计 | 为什么 |
|---|---|
| **每跳都剪枝**（只留 `per_hop_k` 个） | 不剪枝会"遍历爆炸"——一跳的邻居可能有几十个，三跳就是几万条路径 |
| **下一跳只从幸存者出发**（`frontier = top`） | 保证扩展是"沿高分路径"走的，而不是把整个邻域摊平 |
| **分数逐跳衰减**（`decay^hop`） | 让"远亲"分数自然低于"近邻"，避免三跳邻居把一跳邻居挤出去 |

## 3. 参数从哪来，以及一个"没传下去"的坑

所有参数都在 `app/config.py`，**且都可用环境变量覆盖**（便于 A/B）：

```bash
TOP_K=10          # 检索返回的种子数
EXPAND_K=5        # 沿关联边扩展的条数（同时用作每跳预算 per_hop_k）
EXPAND_HOPS=3     # BFS 最大跳数
EXPAND_DECAY=0.5  # 分数逐跳衰减系数
```

### 3.1 踩坑：配置项写了，但没传下去

```python
# kb.py 构造检索器时——**曾经漏传了后三个参数**
HybridRetriever(..., top_k=TOP_K, expand_k=EXPAND_K,
                expand_hops=EXPAND_HOPS, expand_decay=EXPAND_DECAY)
```

漏传的后果：长期沿用构造函数的默认 `expand_k=3`，而 config 与文档都写着 5。**没有任何报错**——系统照常工作，只是"扩展规模比说好的小一截"。

怎么发现的？**是日志里 `graph_expanded` 恒为 3 才暴露的**（3 条而不是 5 条）。

> 这个坑很典型：**"参数没接线"不会报错，只会让效果悄悄变差**。所以现在有一条回归测试专门断言"config 里的参数真的传到了检索器"（`test_expand_params_flow_from_config`）。凡是"配置项 → 构造函数"的传递，都值得这样一条测试。
>
> 顺带说明为什么 `TOP_K` 没出这个问题：它由**调用方**（CLI/Web/eval）显式传给 `search(top_k=...)`，不经过构造函数。

## 4. `crossref` 权重 1.5：让引用链稳定进上下文

### 4.1 原理

扩展时节点的分数是 `上层分 × **边权重** × decay^hop`。回顾四类边的权重（3.2）：

| 边 | 权重 |
|---|---|
| `sibling` | 1.0 |
| `keyword` / `semantic` | Jaccard / 余弦值（≤1） |
| **`crossref`** | **1.5** |

所以一个"被引用条文"通过 crossref 进来时，**分数天然比通过结构边进来高 50%**。在每跳预算有限（`EXPAND_K=5`）的竞争中，它就会优先占位。

### 4.2 真实数据上的效果

| 引用关系 | 场景 |
|---|---|
| 46 → 38 | 经济补偿 ↔ 劳动者解除权（本节开头的例子） |
| 65 → 39 | 劳务派遣解除 ↔ 用人单位单方解除 |
| 42 → 45 | 禁止解除情形 ↔ 逾期解除的后果 |
| 41 → 46 | 竞业限制补偿 ↔ 经济补偿情形 |

> 跨法不建 crossref 边（民法典条文不会引用劳动法条文），所以这个机制只在**同一部法律内部**生效——这是刻意的，硬连跨法引用会引入噪音。

## 5. `EXPAND_K` 到底影响什么（一个容易误读的口径）

我们做过一次 A/B：`EXPAND_K=3` vs `EXPAND_K=5`，跑 `eval --skip-ragas`：

| 指标 | `EXPAND_K=3` | `EXPAND_K=5` |
|---|---|---|
| recall@1 / @3 / @5 / @8 | 0.4894 / 0.7288 / 0.8591 / 0.947 | 0.4894 / 0.7288 / 0.8591 / 0.947 |

**逐位完全相同。** 为什么？因为：

1. eval 用 `--top-k 5`，`recall@8` 只看前 8 位 = **5 个种子 + 前 3 个扩展**；
2. hop=1 的扩展分数最高（`decay^1` 最大），而**前 3 名不随预算变化**；
3. 所以把预算从 3 调到 5，多出来的第 4、5 个扩展**落在了第 8 位之后**，指标看不见。

**它的真实影响在生成上下文规模**：生产路径 13 块 → **15 块**。

> 结论要记牢两点：① **想用 recall 反映扩展规模，得调 `--top-k` 而不是 `EXPAND_K`**；② 反过来，一个参数"改了指标不变"不代表它没用——它可能影响的是**指标没覆盖的那部分**（这里是生成质量）。这类"指标盲区"在任何评估体系里都存在，讲的时候要主动说明。

## 6. 已知局限：宽泛"措施/责任"题会被稀释

三个典型用例（`eval/qa_test_cases.jsonl`）：

| 用例 | 问题 | 现象 |
|---|---|---|
| eval_026 | 拖欠工资怎么维权 | 期望条文未必全部落入 top-8 |
| eval_030 | 维权途径有哪些 | 同上 |
| eval_025 | 孕期被违法解除怎么办 | 同上 |

**成因**：这类问题**同时涉及多部法、多个条文**，而"泛主题"会让很多条文都拿到中等相似度——检索与扩展的分数被摊平，真正该进的那几条反而不突出。

这属于**问题性质决定的困难**：问得越宽，定位越模糊。我们的现状是：

- recall 在这些用例上偏低（劳动法整体 @8 = 0.775，明显低于民法典的 0.983）；
- 但**生成侧仍能给出合法合理的答案**——因为它会基于已召回的相关条文作答，而不是硬编（冒烟测试验证过）。

改进方向见 6.2（补 crossref / 补概念映射 / 查询分解 / 实体链接 + 图传播）。

## 7. 本节小结

- 多跳补的是"**结构/引用相关但内容不像**"的条文——它靠**关系**而不是相似度，这是种子召回补不上的部分。
- `_bfs_expand` 三要素：**分层推进**（≤`EXPAND_HOPS` 跳）、**每跳剪枝**（≤`EXPAND_K`）、**分数衰减**（`分数 × 边权 × decay^hop`）；下一跳只从本跳幸存者出发。
- 参数在 `config.py` 且可环境变量覆盖；**踩过的坑是"参数没传进构造函数"**（`EXPAND_K` 长期用默认 3）——这类 bug 不报错，靠日志与回归测试才抓得住。
- **crossref 权重 1.5** 让被引条文在预算竞争中优先占位，是"46 条能带上 38 条"的关键。
- `EXPAND_K` 从 3 改到 5，**recall 逐位不变**（评估口径看不见），真实影响是**生成上下文规模 13 → 15 块**。
- 已知局限：宽泛的"措施/责任"类问题会被泛主题稀释，是问题性质决定的困难。

## 企业常见面试问答

**Q1：多跳的跳数怎么定？为什么是 3？**

> 3 跳是**效果与成本的平衡点**，不是理论最优。跳数越深，能捞到的条文越多，但噪音也越多——尤其因为分数逐跳衰减（`decay=0.5`），第 3 跳的分数已经只有种子的 1/8 再乘上边权。实践中，法律条文之间的关联大多在 1~2 跳内（同章、直接引用），3 跳基本能覆盖"引用链"场景，再深收益迅速递减。**这个参数是可用环境变量覆盖的**（`EXPAND_HOPS`），如果以后知识源变化（比如加入司法解释，它与法条的关系可能更远），应该重新做 A/B 而不是沿用 3。

**Q2：扩展会不会引入噪音，把无关条文塞进上下文？**

> 会，这是多跳的固有代价，我们用三层机制控制：① **分数衰减**——远跳分数低，不易挤进预算；② **每跳剪枝**——只让每跳的 Top-K 继续往下走，避免"整个邻域摊平"；③ **边权差异**——crossref（1.5）优先于结构边（1.0）与模糊的词面/语义边。但即便如此，扩展结果里仍会有弱相关条目——这也是**为什么最终给生成器的上下文是"种子 + 扩展"两部分而非只给扩展**：种子是"最像的"，扩展是"结构相关的"，生成器拿到的信息里有明显的优先级。另外从实测看，扩展带来的净收益是正的（crossref 让多跳用例 recall@8 达到 0.983）。

**Q3：为什么 crossref 权重比结构边高？为什么不能跨法引用？**

> **权重高**是因为被引条文常常是**答案的必需品**而不是"顺带的上下文"——问"违法解除能不能要补偿"，必须同时知道 46 条（有补偿）和 38 条（解除权从哪来），而后者检索命中不了，只能靠引用关系带。给它 1.5 是为了在预算有限时**优先占位**。
> **不跨法**是因为文本上不存在这种关系：民法典的条文不会写"依照《劳动法》第 X 条"，跨法硬连是从"语义相似"倒推出来的假关系，会把噪音当成结构知识引进图谱。宁可少连也不要错连——**图谱的价值全在"关系是真的"**。

**Q4：一个参数改了指标不变，是不是说明它没用？**

> 不一定，`EXPAND_K` 就是反例。它从 3 改到 5，`recall@1/3/5/8` 逐位完全相同——但真实影响是**生成上下文从 13 块变成 15 块**。原因是评估口径（`--top-k 5` + `@8`）只看前 8 位，而多出来的第 4、5 个扩展落在更后面。这类"指标盲区"提醒两件事：① **指标只覆盖它定义的那部分**，改参数前先想清楚它影响的是不是指标看得见的地方；② 想评估扩展规模，应该调 `--top-k` 而不是只看 recall。反过来说，如果只盯着指标，很容易把"实际有用但指标看不见"的优化砍掉。
