# 4.1 意图识别与兜底 —— 问答前的路由

> 定位：进入检索之前先做一次"分诊"。这一节回答一个体验问题：**不该答的问题，怎么优雅地不答。**

本节目标：

1. 说清为什么要先判意图，而不是"检索不到就兜底"；
2. 掌握三分类（可答 / 法律未覆盖 / 无关）与两套兜底话术；
3. 理解**保守放行**这条反直觉但正确的策略；
4. 学会用 `eval --intent` 量化误判率。

---

## 1. 为什么要先判意图

先想清楚一件事：如果用户问"故意伤害罪判几年"，系统**什么都不做**会发生什么？

检索链路不会报错——它会老老实实返回一堆**低分的劳动法条文**，然后 LLM 拿到这段"参考资料"，被 prompt 要求"依据参考资料作答"，于是**硬凑出一段像模像样的回答**。用户得到的是一段关于"伤害"的、引用着劳动合同法的、完全错误的答案。

这就是幻觉最危险的形态：**不是模型编，而是整条链路在错误的输入上认真工作。**

所以法律问答系统最糟糕的体验不是"我不知道"，而是：

| 反例 | 用户感受 |
|---|---|
| 对刑法问题硬答劳动法 | "这系统在胡说八道" |
| 对"今天天气"强行检索法条 | "它连我在问什么都不知道" |
| 对超出范围的问题给一堆免责声明后才答 | "为什么不早说" |

**先分诊、再作答**——这就是意图识别的定位。

## 2. 三分类

```python
COVERED_LAWS = "《中华人民共和国民法典》《中华人民共和国劳动法》《中华人民共和国劳动合同法》"

class Intent(str, Enum):
    ANSWERABLE = "answerable"            # 可答：本库覆盖的法律问题
    LEGAL_UNCOVERED = "legal_uncovered"  # 法律相关，但本库未覆盖（刑法/行政法/诉讼法/公司法…）
    OFF_TOPIC = "off_topic"              # 与法律无关（天气、编程、闲聊…）
```

判定边界要讲清，尤其是中间那类：

| 分类 | 边界 | 例子 |
|---|---|---|
| `ANSWERABLE` | 面向普通用户的法律咨询，**且**属三部覆盖法律的范围（劳动权益、劳动合同、加班工资、经济补偿、合同、物权、婚姻家庭、继承、侵权责任…） | "试用期最长多久"、"高空抛物谁担责" |
| `LEGAL_UNCOVERED` | **是法律问题，但不在这三部法里** | "故意伤害罪判几年"（刑法）、"公司注册资本要实缴吗"（公司法） |
| `OFF_TOPIC` | 与法律无关 | "帮我写个 Python 快排" |

⚠️ `COVERED_LAWS` 是**提示词与兜底话术共用**的常量。**新增知识源时必须同步这里**——否则新法律的问题会被判成"未覆盖"，系统会理直气壮地拒绝回答一个自己明明能答的问题（这个坑在 3.1 的 Q4 里也提过）。

## 3. 用轻量模型做分类

```python
# 分类用 qwen-turbo，不是 qwen-max —— 分类要快
IntentClassifier(model=INTENT_MODEL, timeout=INTENT_TIMEOUT_S)   # 默认 qwen-turbo / 3 秒
```

三个设计点：

| 设计 | 原因 |
|---|---|
| **`temperature=0`** | 分类是确定性任务，不需要"创造力"；同问题应稳定得同一结果 |
| **只输出 JSON** | 便于程序解析；但**不能要求模型"保证"输出干净**——所以要容错 |
| **`parse_intent()` 容错解析** | 模型常会加 markdown 围栏（\`\`\`json）或前后解释文字；解析器要能剥掉这些噪音 |

```python
def parse_intent(text: str) -> IntentResult:

    ...
```

**为什么不用 qwen-max？** 因为这一步的时延在用户感知的最前面（提问后第一件事），而分类任务的难度远低于生成。用 turbo 把这一跳压到几百毫秒、超时 3 秒，是这个位置该有的工程判断。

## 4. 保守放行：宁可多答一次

这是本节最重要的一个设计取向。

```python
_UNAVAILABLE = IntentResult(Intent.ANSWERABLE, "分类器不可用，按可答放行")
_UNPARSABLE  = IntentResult(Intent.ANSWERABLE, "分类结果无法解析，按可答放行")
```

**所有异常路径都归 `ANSWERABLE`**：超时、网络异常、没有 `API_KEY`、模型输出解析不出来——一律放行。

为什么？因为**两头的错，代价不对称**：

| 错误方向 | 后果 |
|---|---|
| 把可答的判成"未覆盖"（误拒） | **用户的问题被系统白白挡掉**——最严重的体验损失，且用户会认为系统"不会" |
| 把不该答的判成"可答"（误放） | 多检索一次、生成一段不太相关的回答——**有损但不致命**，还能靠 prompt 纪律兜一部分 |

所以宁可多答一次，也不要把正常法律问题挡掉。而且注意：**分类器只做路由，不参与知识定位**——它判完之后，定位仍然完全由检索链路负责。这条边界要守住，否则"分类模型"会悄悄变成一个不可靠的检索器。

> 另一个方向的一致性检查：**反思式多跳是 fail-closed（异常即停）**，而意图识别是 fail-open（异常放行）。这不是自相矛盾，而是因为两者失败时的风险方向不同：前者失败会**引入噪音**（多取无关条文），后者失败会**误伤用户**。判断该 fail-open 还是 fail-closed，看的永远是"失败方向的代价"。

## 5. 兜底怎么"答"

兜底不是简单说"我不知道"，而是**借这次拒答告诉用户你能问什么**：

```python
def fallback_answer(intent: Intent) -> str:
    if intent is Intent.LEGAL_UNCOVERED:
        return f"抱歉，本知识库目前只覆盖 {COVERED_LAWS}，…（建议改写）"
    # OFF_TOPIC：礼貌拒绝 + 可问示例
    return f"当前知识库覆盖 {COVERED_LAWS}，例如你可以问我：\n· 试用期最长可以约定多久？\n…"
```

两套话术的分工：

| 分类 | 话术策略 |
|---|---|
| `LEGAL_UNCOVERED` | **说明覆盖范围 + 建议改写**（用户问的是法律，要告诉他去哪问得着） |
| `OFF_TOPIC` | **礼貌拒绝 + 给可问示例**（顺势把用户引导到能用的问题上） |

### 5.1 接入点：跳过检索，但**不跳过记忆与日志**

```python
# cli.py（Web 端同理）
result = classifier.classify(question)
if result.intent is not Intent.ANSWERABLE:
    answer = fallback_answer(result.intent)
    print(answer)
    memory.add(...)          # ✅ 照常写记忆
    log_qa_event(..., intent=result.intent, intent_reason=result.reason)   # ✅ 照常写日志
    continue                 # 跳过检索与生成
```

这里有一个容易做错的地方：既然不检索不生成，"写记忆"看起来可以省掉。**不能省**——否则多轮对话的上下文会断。用户说"故意伤害罪判几年"（被兜底）接着说"那劳动法里呢"，第二句依赖前一句的语境；如果第一轮没写进会话历史，第二轮的上下文就是残缺的。

日志同理：兜底路径也要记 `intent` 与 `intent_reason`，这样才能事后统计分流比例、排查"为什么不检索"。

## 6. 怎么知道分对了：`eval --intent`

分类质量必须量化，否则只能靠感觉。

```bash
uv run python -m eval.evaluate --skip-ragas --intent
```

口径很简单，因为**评估用例全是法律题**：

> 只要被判成非 `answerable`，就是一次**误判**（把能答的挡掉了）。

注意这个口径**只统计误判率，不改变 recall 口径**——意图识别是路由层，不能污染检索指标（否则历史基线就不可比了）。

## 7. 本节小结

- 意图识别的价值在于：**避免链路在错误输入上"认真工作"**——对超纲问题硬答是幻觉最危险的形态。
- 三分类：`ANSWERABLE` / `LEGAL_UNCOVERED` / `OFF_TOPIC`；`COVERED_LAWS` 被提示词与话术共用，**新增知识源要同步**。
- 用 `qwen-turbo` + `temperature=0` + JSON 输出 + 容错解析——**分类要快**。
- **保守放行**（fail-open）：任何故障都归"可答"。因为误拒（挡掉正常问题）的代价远大于误放（多答一次）。
- 分类器**只做路由，不参与知识定位**；接入点是"跳过检索与生成，但照常写记忆与日志"。
- 用 `eval --intent` 量化误判率（用例全是法律题，非 `answerable` 即误判）。

## 企业常见面试问答

**Q1：意图识别为什么不参与检索？**

> 因为它解决的是**路由问题**，不是**排序问题**。让分类器参与知识定位会带来两个麻烦：① 它会变成一个"准确率不高的检索器"——模型对"哪条法条最相关"的判断远不如 BM25 + 向量 + 图谱的组合，而且不可解释；② 它的故障会直接污染检索结果，而我们现在能保证的只有"故障时保守放行"。所以边界划得很清楚：**分类器只回答"该不该答"，不回答"该答哪条"**。答哪条交给检索链路，这也是"摄入时编译"理念的一贯分工。

**Q2：分类错了怎么办？**

> 分两个方向看。**误拒**（把能答的判成未覆盖）会让用户白白吃一次兜底，所以我们把故障路径全部设为放行，并且用 `eval --intent` 持续量化误判率——用例全是法律题，任何非 `answerable` 都是误判，指标掉了就说明提示词或模型需要调。**误放**（不该答的判成可答）的代价是"多检索一次 + 一段不太相关的回答"，而且生成侧还有领域 prompt 的纪律兜底（"仅依据参考资料作答、给不出就如实说明"）。这个不对称是我们选择 fail-open 的全部理由：**两头的错代价不对等，就不要用同一套策略**。

**Q3：能不能不用 LLM 做分类？**

> 可以，但收益有限。规则/关键词方案（比如命中"故意伤害罪/判几年"就拒答）的好处是零成本、零延迟、完全确定；坏处是**法律问题的边界靠关键词切不干净**——"公司不给加班费能告吗"和"公司不给罚款能告吗"看起来一样，一个可答一个涉及行政法。用轻量模型（qwen-turbo，3 秒超时）是在"准确率"与"成本/延迟"之间取的一个平衡点：它比正则准得多，又比 qwen-max 便宜且快。**真正重要的是它的失败模式**——我们不需要它 100% 准，只需要它"不确定时倾向放行"，剩下的交给检索与生成去兜。

**Q4：兜底回答为什么还要写记忆和日志？**

> 这看起来是"多此一举"，实际是两件事。**写记忆**是为了多轮上下文不断：用户被兜底后往往紧接着换一种问法（"那劳动法里呢"），如果第一轮没进会话历史，第二轮的指代就无从解析。**写日志**是为了可观测：`logs/qa.log` 里带 `intent` 与 `intent_reason`，才能事后统计"分流了多少""为什么这一条没检索"。这两条都属于"不做也不会报错、但会让系统变得不可解释"的那类工作——和第 5 章讲测试时反复强调的"静默失败"是同一类问题。
