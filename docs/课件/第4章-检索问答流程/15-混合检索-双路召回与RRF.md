# 4.2 混合检索 —— BM25 + bge-m3 双路召回与 RRF 融合

> 定位：查询链路的"定位"环节。关键词路与向量路各有所长，这一节讲怎么把两路的分数量纲差异抹平、合成一个可信的排序。

本节目标：

1. 看懂 `kb.search` → `HybridRetriever.search` 的完整调用链；
2. 掌握关键词路（jieba + BM25Okapi，索引含**概念增强关键词**）与向量路（bge-m3 → Milvus 余弦检索）；
3. 吃透 RRF：为什么用"排名倒数"而不是"分数归一"；
4. 能解释 Milvus 不可用时系统如何退化。

---

## 1. 查询调用链

```
用户问题
  │
  ├─► ① 意图识别（4.1）—— 非"可答"直接兜底，不进这里
  │
  ├─► ② 短期记忆按需注入检索词（5.1）—— 仅"像追问"时才并入上一问
  │
  ▼
KnowledgeBase.search(query, top_k)          # app/kb.py
  │
  ▼
HybridRetriever.search                      # app/retrieval/hybrid_retriever.py
  ├─► keyword_retriever.search()   ──┐      # BM25
  ├─► vector_retriever.search()    ──┤      # bge-m3 → Milvus
  │                                  ▼
  │                        RRF 融合（Σ 1/(60+rank)）
  │                                  ▼
  │                        取 Top-K 种子（默认 10）
  └─► _bfs_expand()（4.3）→ 反思循环（4.4）
```

`kb.py` 是**统一入口**：CLI 与 Web 都走它，也由它决定"向量路能不能用"（Milvus 不可用时退化为纯关键词）。检索器本身不关心"谁在问"。

## 2. 关键词路：jieba + BM25Okapi

### 2.1 语料为什么是"标题 + 正文 + 关键词"

```python
# keyword_retriever.py
corpus = [
    jieba.lcut(f"{n['title']} {n['content']} {' '.join(n.get('keywords') or [])}")
    for n in nodes
]
self.bm25 = BM25Okapi(corpus)
```

三段拼起来不是随手写的：

| 段 | 作用 |
|---|---|
| `title` | 章条号与编名（"第二编 物权·第二章·第十三条"）——**编名因此也能参与匹配** |
| `content` | 法条正文，主力信号 |
| `keywords` | **概念增强后的关键词**（3.2）——"加班费"这类**用户口语**就是从这里进来的 |

第三条是"口语 → 法条"能生效的关键：法条正文里根本没有"加班费"三个字，但概念映射把它注入了 `keywords`，于是 BM25 能命中。

### 2.2 BM25 打分直觉

BM25 的核心是两个归一化：

```
分数 ∝ 词频 tf 的饱和函数  ×  逆文档频率 IDF  ×  文档长度归一
```

- **tf 饱和**：一个词出现 10 次不会比出现 3 次"重要 3 倍"——出现的边际收益递减；
- **IDF**：越常见的词权重越低（"的""应当"几乎无信息量）；
- **长度归一**：长文档天然更容易撞词，所以要按长度打折，否则长条文永远占优。

对法律库来说，BM25 的强项是**精确匹配条文号与法律术语**（"第四十六条""竞业限制"），弱项是**换说法就召回不到**——这正好是向量路要补的。

## 3. 向量路：bge-m3 → Milvus 余弦检索

### 3.1 为什么 query 现场编码、知识点向量预先建好

知识点只有 **1465** 条，但**不随提问变化**——所以摄入期一次编码、写进 Milvus；提问时只编码 **1 条 query**：

```python
# vector_retriever.py
qv = embedder.encode([query])[0]          # 现场编码 query（单条）
hits = store.search(qv, top_k)            # [(kp_id, score)]
nodes = [id2node[kp_id] for kp_id, _ in hits if kp_id in id2node]
```

注意最后一行的 `if kp_id in id2node`：**集合里可能残留当前图谱已不存在的 id**，映射不到就跳过——这是防御性写法（正常情况下 3.4 的全量对齐会清掉这些陈旧主键）。

### 3.2 向量路的价值：换一种说法也能命中

| 用户说法 | 法条措辞 |
|---|---|
| "被开除能拿多少赔偿" | 解除劳动合同的经济补偿… |
| "老板不给发工资" | 拖欠劳动报酬… |

BM25 在这些场景会漏，向量路能靠语义近邻补上。但反过来，向量路对**精确条文号**不敏感（"第四十六条"的语义近邻可能是一堆别的条文）——所以两路**互补**，缺一不可。

## 4. Milvus 细节：集合、索引与退化

```python
store.ensure_collection()
# kp_id(VARCHAR 主键) + title/source(标量列) + vector FLOAT_VECTOR(1024)
# 索引 HNSW(M=16, efConstruction=200)；度量 COSINE
# 已存在则校验维度，不一致就重建
```

几个值得讲的点：

| 点 | 说明 |
|---|---|
| 为什么度量是 `COSINE` | bge-m3 输出已 **L2 归一化**，此时余弦与点积等价；用 COSINE 语义更明确 |
| 为什么用 HNSW + COSINE | 近似最近邻，检索快；1465 条的规模其实"暴力算也行"，但用索引是为规模与工程一致性 |
| 维度校验 | `EMBED_DIM`（1024）与集合不一致时**重建**——换模型后忘了改维度，是这类系统最常见的静默错误之一 |
| **退化路径** | Milvus 不可用（服务没起/集合不存在）时：`kb.load()` 打印告警并**退化为纯关键词检索**，不抛异常 |

**退化为什么这里可以"软"、而写入必须"硬"？** 因为失败的方向不同：查询期退化仍然能答（只是少了语义一路，recall 会降），可用性优先；而摄入期静默跳过会产生"副本是旧数据"的不一致，**必须响亮地失败**（3.4）。同一套系统里两种策略并不矛盾——**看失败的方向会伤到谁**。

相关配置（都可用环境变量覆盖）：

```bash
MILVUS_HOST=localhost  MILVUS_PORT=19532        # 宿主映射端口（容器内是 19530）
MILVUS_COLLECTION=llm_wiki_laws  MILVUS_METRIC=COSINE  MILVUS_INDEX=HNSW  EMBED_DIM=1024
```

## 5. 融合：RRF（Reciprocal Rank Fusion）

### 5.1 公式与代码

```python
RRF_K = 60  # RRF 常数

# 两路各自按名次贡献分数
rrf[node["id"]] = rrf.get(node["id"], 0.0) + 1.0 / (RRF_K + rank + 1)   # 关键词路
rrf[node["id"]] = rrf.get(node["id"], 0.0) + 1.0 / (RRF_K + rank + 1)   # 向量路
```

写成公式（rank 为 1 起的名次）：

```
RRF(node) = Σ_path  1 / (60 + rank_path(node))
```

只看**名次**，不看分数。`60` 是那个著名的经验常数（来自 RRF 原论文），作用是**压平头部差异**：名次 1 与 2 的贡献是 1/61 vs 1/62，差别很小；真正拉开差距的是"**在几路里都排得靠前**"。

### 5.2 为什么不用"分数归一化"

两路的分数量纲**根本不可比**：

| 路 | 分数形态 |
|---|---|
| BM25 | 无上界，取决于语料与词频 |
| 余弦相似度 | 固定在 [-1, 1] |

想把它们"归一化后加权求和"，就得先假设分数分布（min-max？z-score？），而这些假设在不同 query 上并不成立——**一个 query 下归一化系数是 0.3，另一个 query 下可能完全反过来**。RRF 绕开了这个问题：排名是**序数**，天然跨路可比，鲁棒且无需调参。

### 5.3 手算一个例子（加深直觉）

设关键词路返回 `[A, B, C]`，向量路返回 `[B, D, A]`：

| 节点 | 关键词路 | 向量路 | RRF 合计 |
|---|---|---|---|
| **B** | 第 2 名 → 1/62 | 第 1 名 → 1/61 | **≈ 0.03252** ← 最高 |
| A | 第 1 名 → 1/61 | 第 3 名 → 1/63 | ≈ 0.03227 |
| D | 未出现 | 第 2 名 → 1/62 | ≈ 0.01613 |
| C | 第 3 名 → 1/63 | 未出现 | ≈ 0.01587 |

**B 赢了 A**——尽管 A 在关键词路排第 1。原因就是**两路共识 > 单路第一**：B 在两路都靠前，说明两条独立的信号都认为它相关。这正是 RRF 的核心假设，也是"混合检索"的意义所在。

## 6. 这一步的产出

```python
def search(self, query, top_k=5, expand=True) -> list[dict]:
    # 返回 top_k 个种子（+ 至多 expand_k 个图谱扩展，见 4.3）
```

- **种子数由调用方决定**：`TOP_K=10`（config 默认），CLI/Web/eval 显式传 `search(top_k=...)`。
- 每个种子带 `rrf` 分——它就是 4.3 多跳扩展的**分数种子**（`种子分 × 边权重 × decay^hop`）。

> 一个校准认知：eval 常用 `--top-k 5`，所以 recall@8 的口径是"5 种子 + 前 3 扩展"；而**生产路径的上下文是 10 种子 + ≤5 扩展 + 反思补取 ≈ 15 块起**。两者不是一回事，讲指标时要说清（6.2 详述）。

## 7. 本节小结

- 检索链路：意图路由 → 记忆按需注入 → 双路召回 → RRF → Top-K 种子 → 多跳扩展；`kb.py` 是统一入口。
- 关键词路：jieba + BM25Okapi，语料 = **标题 + 正文 + 概念增强关键词**（口语词能命中法条的关键）；强在精确匹配，弱在换说法。
- 向量路：bge-m3 编码 query → Milvus 余弦检索 → `kp_id` 映射回节点（映射不到就跳过）；强在语义近邻，弱在精确条号。**两路互补**。
- Milvus：`kp_id` 主键 + 1024 维向量 + HNSW/COSINE，已存在则**校验维度**；**不可用时退化为纯关键词**（查询期可用性优先，与摄入期的"显式失败"方向不同）。
- RRF：`Σ 1/(60 + rank)`，**只看名次不看分数**——因为 BM25 无上界、余弦在 [-1,1]，量纲不可比，归一化要引入不成立的分布假设。**两路共识 > 单路第一**。

## 企业常见面试问答

**Q1：为什么要做混合检索，单用向量不行吗？**

> 单用向量在法律场景有两个硬伤：① **对精确标识不敏感**——用户问"劳动合同法第四十六条"，向量检索未必把那条排第一，因为它不擅长"字面命中"；② **不可解释**——为什么这条排第 2？只能给一个相似度数字。而 BM25 恰好强在这两点：条文号、法律术语的精确匹配，以及"命中哪些词"可解释。反过来说 BM25 也漏"换一种说法"的场景，那正是向量的强项。所以两者不是"一个更好"，而是**互补**——这也是为什么最终要做融合，而不是二选一。

**Q2：RRF 里的 60 是什么？为什么用倒数而不是分数？**

> `60` 是 RRF 原论文里的经验常数，作用是**压平头部差异**：第 1 名和第 2 名的贡献分别是 1/61 与 1/62，差距很小，这样"在另一路也靠前"比"在一路里排第一"更重要。至于为什么用倒数：因为**两路的分数不可比**——BM25 分数无上界、余弦固定在 [-1,1]，要加权求和就必须先归一化，而归一化要假设分数分布（min-max / z-score），这个假设在不同 query 上并不成立。用**名次**就绕开了量纲问题：排名是序数，跨路天然可比，而且不用调参。代价是丢掉了"分数差距有多大"的信息——但在这个场景里，排名比分数更稳。

**Q3：Milvus 挂了会怎样？为什么这里允许降级，而摄入时不许？**

> 查询期：`kb.load()` 打印告警、退化为**纯关键词检索**，CLI/Web 仍然可用——语义召回失效、recall 会明显下降，但系统"还能答"，可用性优先。摄入期：Milvus 写入失败**直接抛错**，不静默跳过。两个方向相反，判断依据是**失败会伤到谁**：查询期降级的代价是"这一问答得差一点"，用户可感知也可容忍；摄入期静默跳过的代价是"副本长期是旧数据、而且没人知道"，这属于会破坏系统可信度的**静默不一致**。一句话：**能用性问题上可以软，一致性问题上一律硬**。

**Q4：`top_k` 到底设多少？**

> 它不是"越大越好"，要分清三个数：① `TOP_K`（种子，config 默认 10）——种子是 RRF 排序的前 N 名，再多会引入弱相关噪音；② `EXPAND_K`（扩展，默认 5）——沿图谱补进来的条数，影响的是**上下文规模**；③ eval 的 `--top-k`（常用 5）——这是**评估时的检索口径**，与生产不同。最容易搞混的是最后这个：`recall@8` 是"5 种子 + 前 3 扩展"下的指标，而生产路径实际给生成器的上下文是 10 种子 + ≤5 扩展 + 反思补取 ≈ **15 块起**。所以"@8 不是生成上下文的上限"，只是沿用历史基线的汇报口径。
