# 4.5 生成与引用溯源

> 定位：上下文凑齐了，怎么让模型"照着法条说人话、并且说清依据"。这一节把"检索"与"答案"之间最后一段路走完。

本节目标：

1. 掌握 `AnswerGenerator` 的 prompt 组装（系统提示 + 参考资料 + 用户背景 + 对话历史）；
2. 理解"**上下文标题带法律名**"这个细节为什么是多法库的必需品；
3. 看懂流式生成与 SSE 的配合；
4. 说清引用溯源为什么要**随消息一起落库**。

---

## 1. 从检索块到人话：`answer.py`

```python
def generate_stream(self, query, contexts, history, memory):
    messages = [{"role": "system", "content": SYSTEM_PROMPT}]
    #          + 参考资料（contexts）
    #          + 用户背景（memory）
    #          + 对话历史（history）
    #          + 当前问题
    stream = self.client.chat.completions.create(..., stream=True)
    for chunk in stream:
        yield chunk.choices[0].delta.content or ""
```

四段输入各有分工：

| 输入 | 来自 | 作用 |
|---|---|---|
| **SYSTEM_PROMPT** | 常量 | 领域角色、生成纪律（只依据资料、不臆造、列引用） |
| **参考资料** | 检索链路（4.2~4.4） | 法条正文，**答案的唯一依据** |
| **用户背景** | 长期记忆（5.1） | 用户自身处境，标注**不得作为法律依据** |
| **对话历史** | 短期记忆（5.1） | 多轮连贯（"那 / 具体 / 继续"） |

### 1.1 参考资料怎么拼

```python
def _format_contexts(contexts) -> str:
    for ctx in contexts:
        body = ctx["content"][:600]        # 每条截断 600 字
        ...  # 标题 + 正文
```

**为什么截断 600 字？** 上下文块数在 15 上下（10 种子 + ≤5 扩展 + 反思补取），法条正文有长有短（民法典个别条文很长）。截断是为了**控制总 prompt 长度**，避免个别长条文把预算吃光。这个值是可以调的工程参数，不是精确的科学常数。

## 2. 领域 SYSTEM_PROMPT：给生成立规矩

prompt 是**民事法律域**定制的（从劳动法扩到民法典后做过一次改写），要点：

| 约束 | 原话（大意） |
|---|---|
| 覆盖范围 | "依据《中华人民共和国民法典》《中华人民共和国劳动法》《中华人民共和国劳动合同法》…解答劳动权益、劳动合同…以及合同、物权、侵权责任、婚姻家庭、继承等民事法律问题" |
| **只依据资料** | "仅依据【参考资料】作答" |
| **点明依据** | "涉及具体规定时点明法律依据" |
| **不许臆造** | "不要臆造法条" |
| **列出引用** | "末尾列出全部引用" |

这五条不是装饰——它们是**幻觉的第二道防线**（第一道是检索定位，第三道是引用可核验）。特别是"给不出就如实说明"，它给了模型一条**合法的退路**：与其硬编，不如承认资料不足。**给模型退路，是抑制幻觉最便宜的手段。**

## 3. 上下文标题带法律名（防张冠李戴）

### 3.1 问题

三部法律**同条号极多**：

| 条号 | 劳动合同法 | 劳动法 | 民法典 |
|---|---|---|---|
| 第八十五条 | ✅ | ✅ | — |
| 第九十八条 | ✅ | ✅ | — |
| 第四十六条 | ✅ | ✅ | — |

如果上下文里只写"第四章·第八十五条"，模型**无法分辨**是劳动合同法还是劳动法那一条——它很可能把 A 法的内容安到 B 法的条号上。这是**实测踩过的坑**。

### 3.2 解法：从 `source` 拼法律名

```python
# _format_contexts：从 source 的文件名前缀取法律名
中华人民共和国劳动合同法.md L...  ──►  "中华人民共和国劳动合同法"
```

拼出来的标题形如：

```
中华人民共和国劳动合同法·第四章·第三十九条
中华人民共和国民法典·第七编 侵权责任·第十章·第一千二百五十四条
```

注意第二行**自带编名**（"第七编 侵权责任"）——这是 3.2"编必须参与分组"的延伸：民法典 7 编里同号章、同号条都可能撞，带上编名才能唯一定位。

> ⚠️ **做任何跨法 / 多文档相关的改动，都必须保持这一点。** 它是"引用可核验"的基础：用户看到的标题能唯一对应到一条法条。

## 4. 流式生成

```python
def generate_stream(...):   # 逐块 yield（stream=True）
def generate(...):          # 聚合 generate_stream 的完整结果
    return "".join(self.generate_stream(query, contexts, history, memory)).strip()
```

**为什么要流式？** 生成一段法律回答通常要几秒到十几秒。流式的价值是把"首字延迟"从"整段生成完"降到"第一个 token"——用户立刻看到字在出，体感差别巨大。

两个实现细节：

| 细节 | 说明 |
|---|---|
| CLI 与 Web **共用同一个生成器** | 只有"怎么把 chunk 送到屏幕/浏览器"不同（`print` vs SSE） |
| 流式失败的处理 | 生成失败发 `error` 事件，但**仍返回 citations 并写记忆**——答案没出来，引用与上下文信息不该丢（排查要用） |

## 5. 引用溯源：为什么必须随消息落库

### 5.1 踩过的坑

最初的实现里，引用只存在**前端内存**里，`onDone` 把流式文本转成历史消息时**把 citations 丢掉了**。后果非常讽刺：

> **回答一完成，最该被核对的溯源信息就消失了**；刷新页面或切换会话后，彻底没有。

而"引用可回溯"正是这个系统最核心的卖点之一（1.1 讲的"答案与出处不是两张皮"）。

### 5.2 现状

citations 以 **JSON 存进 `messages.citations`**，`add()` 与 `session_messages()` 都要带上该字段：

```
MySQL messages 表
  session_id | user_id | role | content | citations(JSON)
                                            │
                                            ▼
                          前端渲染"引用来源 · N 条法条"面板（可展开）
```

每条引用带四个字段：

| 字段 | 用途 |
|---|---|
| `id` | 知识点编号（`KP_046`） |
| `title` | 带法律名的条文标题 |
| `score` | 检索/扩展得分（可看出"为什么它排在这"） |
| `source` | **原始文件 + 行号**（`中华人民共和国劳动合同法.md L...`）→ 可回溯到原文 |

> 第 4 个字段是"可核验"的落点：用户能拿着行号去原文核对，而不是只能相信系统。这也是 3.1 里"行号必须按物理行算"那条踩坑的**下游收益**——行号错了，这里的溯源就是假的。

## 7. 代码走读：`_format_contexts` —— 18 行决定多法库的成败

这段代码很短，但它是 4.5 讲的"上下文标题带法律名"的实现，也是**多法知识库的必需品**。

### 7.1 完整实现

```python
@staticmethod
def _format_contexts(contexts: list[dict]) -> str:
    parts = []
    for i, ctx in enumerate(contexts, 1):
        law = ""
        src = ctx.get("source", "")
        if ".md" in src:
            # 同章同条可能跨两部法律，标题带法律名避免张冠李戴
            law = f"{src.split('.md')[0].strip()}·"
        title = f"{law}{ctx['title']}"
        body = ctx["content"][:600]
        parts.append(f"{i}. [{title}]\n{body}")
    return "\n\n".join(parts)
```

产出的格式：

```
1. [中华人民共和国劳动合同法·第四章·第四十六条]
用人单位应当向劳动者支付经济补偿的情形…

2. [中华人民共和国民法典·第七编 侵权责任·第十章·第一千二百五十四条]
禁止从建筑物中抛掷物品。…

3. […]
```

### 7.2 逐行说明

| 行 | 说明 |
|---|---|
| `src.split(".md")[0].strip()` | 法律名**从 `source` 的文件名前缀取**（`中华人民共和国劳动合同法.md L32-35` → `中华人民共和国劳动合同法`）。**不需要额外维护一份"法律名"字段**——来源信息本来就在 |
| `if ".md" in src` | 防御：万一 `source` 格式变了（没有 `.md`），就退化成不带法律名的标题，**而不是崩掉** |
| `enumerate(contexts, 1)` | 编号从 **1** 开始——模型在正文里引用依据时更容易对上"第几条资料" |
| `ctx["content"][:600]` | **每条截断 600 字**。上下文块数在 15 上下，法条有长有短（民法典个别条文很长）；截断是为了控制总 prompt 长度，避免个别长条文把预算吃光 |
| `"\n\n".join(parts)` | 段落之间空行分隔，便于模型区分"这是两条不同的法条" |

### 7.3 为什么这 18 行是多法库的必需品

三部法律**同条号极多**：都有第 85 条、98 条、46 条。如果标题只写"第四章·第八十五条"，模型看到的是：

```
1. [第四章·第八十五条]
用人单位有下列情形之一的，由劳动行政部门责令限期支付…
```

它**无法判断**这是劳动合同法还是劳动法的 85 条。而这两条的内容与适用场景不同——模型很可能把 A 法的内容安到 B 法的条号上，甚至在同一段回答里**同时引用"劳动法第 85 条"和"劳动合同法第 85 条"却混为一谈**。这是本项目**实测踩过的坑**。

加上法律名之后：

```
1. [中华人民共和国劳动合同法·第四章·第八十五条]
```

**唯一可定位。** 再加民法典的编名（"第七编 侵权责任"），连"7 编内部同号章、同号条"的情况也区分开了。

### 7.4 一个可推广的原则

> **给模型的上下文，标识必须"自足可辨"。**

也就是说：**把这一条单独拎出来看，能不能确定它指的是什么？** 判断标准很简单——如果两条不同的资料在上下文里的标题**长得一样**，那么标识就是不合格的。

同类做法在别处也出现过：

| 场景 | 自足可辨的标识 |
|---|---|
| 生成上下文 | `法律名·编·章·条`（本节） |
| 引用溯源面板 | `id`（`KP_046`）+ 法律名 + `source` 行号（4.5） |
| 长期记忆 | 注入段落**显式标注**"用户背景，不得作为法律依据"（5.1） |
| 反思候选 | 给模型的是**编号**，不是条号（4.4）——条号在多法库里有歧义 |

**最后一条最能说明问题**：反思候选不用"第四十六条"这样的条号，而用"1、2、3"这样的**候选编号**——因为在一个多法库里，"第四十六条"本身就不是自足的标识。**同一个坑，在不同的地方要用不同的方式绕开。**

## 8. 本节小结

- prompt 四段：**系统提示（纪律）+ 参考资料（唯一依据）+ 用户背景（不得作为法律依据）+ 对话历史**；参考资料每条**截断 600 字**以控总长。
- SYSTEM_PROMPT 的五条纪律是幻觉的第二道防线；**"给不出就如实说明"给了模型合法退路**，是抑制幻觉最便宜的手段。
- **上下文标题必须带法律名**（从 `source` 文件名前缀取），民法典还自带编名——多部法律同条号极多，不带法律名模型会张冠李戴（实测踩过）。
- 流式生成把首字延迟从"整段生成完"降到"第一个 token"；CLI 与 Web 共用同一生成器；**流式失败仍返回 citations 并写记忆**。
- **引用必须随消息落库**（`messages.citations` JSON）——否则"回答一完成，最该被核对的溯源信息就没了"，刷新后更彻底丢失。引用含 `id/title/score/source`，`source` 的行号让答案**可核验**。

## 企业常见面试问答

**Q1：怎么抑制幻觉？**

> 三层防线，逐层收紧：① **检索侧**先定位到具体法条，用**真实原文**作为唯一依据——模型没机会"自己回忆法条"；② **生成侧**用领域 prompt 立规矩："仅依据参考资料作答""不要臆造法条""**给不出就如实说明**"。最后这条特别重要——**给模型一条合法的退路**，它才不会为了"完成任务"而硬编；③ **输出侧**回答末尾列出全部引用，每条带法律名与原文行号，**可被用户核验**。此外问答前还有意图识别（4.1）挡住"本库不该答的问题"，避免链路在错误输入上认真工作。三层里我认为第 ③ 层最被低估：**当答案可被核验时，幻觉的成本就从"用户被误导"变成了"用户能发现"**。

**Q2：引用是怎么保证真实的？**

> 引用不是"让模型列"，而是**链路里带出来的数据**。具体做法：检索到的每个知识块本身就带 `id/title/score/source`；生成时把这些块作为参考资料喂给模型并要求"末尾列出引用"；最终**返回给前端的 citations 直接取自检索结果**（不是解析模型输出里的文字）。所以引用**不依赖模型是否诚实**——它来自检索本身。模型的任务只是"在正文里用上这些资料并标注对应关系"。另外每条的 `source` 带原始文件名与行号，用户可以回溯到原文核对，这是"可核验"的落点。

**Q3：为什么一定要把法律名拼进标题？**

> 因为三部法律**同条号极多**（都有 85 条、98 条、46 条）。上下文里只写"第四章·第八十五条"，模型无法分辨是劳动合同法还是劳动法——**实测出现过把一部法的内容安到另一部法的条号上**。修法是 `_format_contexts` 从 `source` 的文件名前缀拼入法律名，标题变成"中华人民共和国劳动合同法·第四章·第八十五条"。民法典还额外带编名（"第七编 侵权责任"），因为 7 编内部也有同号章、同号条。这个细节看起来很小，但它是**多法知识库的必需品**——单法库里并不需要，所以很容易在新项目里被漏掉。

**Q4：流式生成失败怎么办？**

> 发 `error` 事件告知前端，但**仍然返回 citations 并照常写记忆**。理由：生成失败时，用户看到的是"没答出来"，但排查的人需要知道"当时检索到了什么"——如果连 citations 都丢了，就只能看到一个孤零零的报错。同理，记忆也要写（记录这一轮发生过），否则多轮上下文会出现"用户以为问过、系统不记得"的断层。这个处理原则可以概括为：**部分成功时，把已经确定的信息全部保留下来**，不要因为最后一步失败就把前面的成果一起丢掉。
