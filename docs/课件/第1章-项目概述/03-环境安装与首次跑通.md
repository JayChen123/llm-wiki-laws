# 1.3 环境安装与首次跑通

> 定位：从"知道有哪些东西"到"亲手把它跑起来"。这一节按**可照做的顺序**走一遍安装，并把最容易卡住的故障做成一张排查表。

本节目标：

1. 按正确顺序完成环境安装（Python/uv → 凭证 → 容器 → 模型 → Key → 建库 → 起服务）；
2. 记住四个"宿主机端口"，不要和容器内端口混淆；
3. 掌握每一阶段**应该看到什么**（有预期输出才知道是否成功）；
4. 遇到问题时能凭"症状 → 原因 → 处置"表自己排查。

---

## 1. 环境总览：需要哪四类东西

```
① 运行时         Python 3.13+ / uv / Node.js（前端）
② 四个容器       Milvus（向量）· MySQL（记忆）· Neo4j（图）· Redis（Milvus 依赖）
③ 一个本地模型     bge-m3（约 2.2GB，本地编码，零 API 成本）
④ 一个外部 Key     DashScope（qwen-max 生成 / qwen-turbo 分类与反思）
```

三样是本地自足的（① ② ③），只有 ④ 是外部依赖——这也是 1.2 说的"内网部署时只有意图识别与生成需要换模型"。

---

## 2. 第 1 步：Python 与 uv

```bash
# 确认版本（需要 3.13+）
python3 --version

# 安装 uv（若未安装）
curl -LsSf https://astral.sh/uv/install.sh | sh

# 装依赖：uv 会按 uv.lock 还原，并自动创建 .venv
uv sync
```

**为什么用 uv**：它把"虚拟环境 + 依赖解析 + 锁文件"合成一条命令，并且 `uv run` 可以**不激活环境**直接跑——本课程所有命令都是 `uv run python -m …` 形式，正是为了免去"忘了 activate"这类问题。

> ⚠️ 装完依赖后建议立刻跑一次 `uv run python -m pytest tests/ -q`。**这一步不需要任何容器、模型和 Key**（测试全部离线，5.1 详述），所以它是**验证"依赖装对了"最快的方式**。如果这里就失败，问题一定在 Python 环境，不必往下查。

---

## 3. 第 2 步：服务凭证 `docker/.env`

```bash
cd docker
cp .env.example .env
# 编辑 .env，填 MySQL / Neo4j / Redis / MinIO 的账号密码 + JWT_SECRET
```

三个要点：

| 要点 | 说明 |
|---|---|
| **一份文件两处用** | docker compose 自动读它，应用（`uv run …`）也读同一份（`python-dotenv`），**改一处即可让两边一致** |
| **不入库** | `.gitignore` 已忽略 `.env`，仓库里只有模板 `.env.example` |
| **密码里避免 `$`** | compose 会把 `$` 当变量语法（需写 `$$` 转义），而 dotenv 按字面读取、不还原——两边行为不一致，最容易出"compose 能连、应用连不上" |

`JWT_SECRET` 请**务必改成 ≥32 位随机串**：默认值等于任何人都能伪造登录令牌（生产环境必须用环境变量覆盖）。

---

## 4. 第 3 步：起四个容器

```bash
cd docker && docker compose up -d
docker ps                    # 确认四个容器都在跑
```

### 4.1 四个宿主机端口（最容易记错的地方）

| 服务 | 容器名 | 宿主机端口 | 容器内端口 |
|---|---|---|---|
| Milvus | `milvus-standalone` | **19532** | 19530 |
| MySQL | `mysql_container` | **3308** | 3306 |
| Neo4j Browser | `neo4j-standalone` | **7474**（网页） | 7474 |
| Neo4j Bolt | 同上 | **7687**（驱动连这个） | 7687 |
| Redis | `milvus-redis` | 6380 | 6379 |

配置里写的都是**宿主机端口**（`MILVUS_PORT=19532`、`MYSQL_PORT=3308`）。搞混的表现是"连不上"，而且报错往往含糊。

### 4.2 预期输出

```bash
$ docker ps --format '{{.Names}}\t{{.Status}}'
milvus-etcd         Up
milvus-minio        Up (healthy)
milvus-standalone   Up
milvus-redis        Up
mysql_container     Up
neo4j-standalone    Up (healthy)
```

几点说明：

- `etcd` / `minio` 是 **Milvus 的依赖**（元数据与对象存储），不是本项目直接用的；
- `minio` 与 `neo4j` 有 **healthcheck**（MinIO 探活、Neo4j 用 `cypher-shell` 执行 `RETURN 1`）——看到 `(healthy)` 才说明真就绪；
- **首次启动 Milvus 会慢一些**（要初始化 etcd/minio）。如果 `pipeline` 立刻失败，先 `docker ps` 看它是不是还在起。

---

## 5. 第 4 步：bge-m3 模型

本项目用**本地** bge-m3 做向量编码（既有语义边，也有查询向量），路径配在：

```python
# app/config.py
BGE_MODEL_PATH = "..."      # ← 机器相关，换环境先改这里
```

| 要点 | 说明 |
|---|---|
| **这是最常需要改的一行配置** | 模型路径因人而异，属于"机器相关"配置，不是通用默认值 |
| 体积约 **2.2GB** | 首次加载慢（几十秒），之后每次进程启动仍要加载一次 |
| 编码次数 | 摄入期一次编码 1465 条；查询期每次只编码 1 条 query |
| 零 API 成本 | 这是选本地模型的核心理由（1.2 选型表） |

> 排障提示：**"模型加载失败"和"路径写错"的表现很像**。若报路径不存在，先确认 `BGE_MODEL_PATH` 指向的目录里确实有模型文件（而不是它的上一级）。

---

## 6. 第 5 步：DashScope API Key

```bash
export API_KEY="你的-dashscope-key"
```

| 谁用它 | 模型 | 不用会怎样 |
|---|---|---|
| 生成回答 | `qwen-max` | CLI 会降级为"只展示检索结果"，不生成自然语言 |
| 意图识别 | `qwen-turbo` | **保守放行**（3.1）：所有问题都当"可答"处理，功能仍可用 |
| 反思 | `qwen-turbo` | **fail-closed**（4.4）：直接停止继续检索，不影响已有上下文 |
| 画像抽取 | `qwen-turbo` | 抽取失败返回空列表，不影响主流程 |

注意**没有 Key 时系统不会崩**——只是降级。这个设计是刻意的：让"检索链路"可以完全独立于外部 LLM 运行与调试。

## 7. 第 6 步：首次建库（这是最耗时的一步）

```bash
uv run python -m app.ingest.pipeline
```

它会依次做（1.2 的摄入流程）：PDF→MD（增量）→ 提取知识点（全局编号）→ 概念关键词增强 → bge-m3 编码 → 建图谱 → 落盘 json → 同步 Neo4j → 写 Milvus → 落 Wiki 视图。

### 7.1 预期输出（用来核对是否成功）

```
[pipeline] 关联边 21252 条，已写入 knowledge_graph.json 与 wiki/（index + log + 10 个示例页）
[pipeline] 向量已写入 Milvus 集合 llm_wiki_laws：1465 条
```

**关键数字**：

| 指标 | 期望值 |
|---|---|
| 知识点 | **1465**（民法典 1260 + 劳动法 107 + 劳动合同法 98） |
| 关联边 | **21252** |
| Milvus 条数 | **1465** |
| Neo4j 关系数 | **30569**（> 边数，因为一条多类型边拆成多条关系，2.4 讲过） |

### 7.2 建完之后自检

```bash
# ① Neo4j 与 json 两侧计数是否一致
uv run python -m app.ingest.sync_graph --check-only

# ② Milvus 集合条数
uv run python -c "from app.retrieval.vector_store import MilvusVectorStore; print(MilvusVectorStore().count())"
```

> ⚠️ **改了知识源（PDF/md）后必须重跑 pipeline**——派生副本（Neo4j / Milvus）**不会自己发现知识库变了**。这是全课程反复强调的一条（3.4 细讲）。

## 10. 故障排查表

按"症状 → 原因 → 处置"组织。**这张表覆盖了本课程里所有踩过的环境类坑。**

### 10.1 依赖与版本

| 症状 | 原因 | 处置 |
|---|---|---|
| `pymilvus` 一 import 就报 `No module named 'pkg_resources'` | 装成了 **2.4.x**——它依赖已被移除的 `pkg_resources`，在 Python 3.13 上直接失败 | 锁到 **`pymilvus>=2.5,<2.6`**（2.5.x 客户端连 Milvus v2.4.4 服务端已实测可用） |
| 裸 `pytest` 报 `ModuleNotFoundError: app` | `app` 包不在 `sys.path` | 用 **`uv run python -m pytest`**（`python -m` 会把项目根加入路径） |
| ragas 报 `vertexai` 模块缺失 / `agenerate_prompt` 不存在 | 版本组合不兼容 | 锁定 **`ragas==0.3.0` + `langchain-community==0.4.0` + langchain 1.x**（唯一已验证组合） |
| ragas 报 `input.contents is neither str nor list of str` | 用了 `langchain_openai.OpenAIEmbeddings` | 评估必须用 **`langchain_community.embeddings.DashScopeEmbeddings`** |

### 10.2 容器与连接

| 症状 | 原因 | 处置 |
|---|---|---|
| 应用报连不上 Milvus | **端口搞混**：宿主机是 **19532**（容器内 19530） | 核对 `MILVUS_PORT=19532` |
| 应用报连不上 MySQL | 宿主机是 **3308**（容器内 3306） | 核对 `MYSQL_PORT=3308` |
| compose 能连、应用连不上 | 密码里含 `$`：compose 按变量语法处理，dotenv 按字面读取 | 密码里**避免 `$`**，或 compose 里写 `$$` |
| `docker compose up` 拉不到镜像 | 部分网络下 ghcr.io / deb.debian.org 不可达 | 换镜像源；**镜像尽量不依赖 ghcr** |
| 首次 pipeline 立刻报 Milvus 错 | Milvus 还在初始化 | 等它 healthy 后重跑（命令是幂等的） |

### 10.3 模型与 Key

| 症状 | 原因 | 处置 |
|---|---|---|
| 报模型路径不存在 | `BGE_MODEL_PATH` 指向的目录不对 | 改 `app/config.py`（这是**机器相关**配置） |
| 每次都等很久才出结果 | bge-m3（2.2GB）在进程启动时加载 | 正常现象；摄入期会一次编码 1465 条 |
| CLI 不生成自然语言答案 | 没设 `API_KEY` | `export API_KEY=…`（不设也能用：降级为只展示检索结果） |
| 所有问题都走了兜底/都当可答 | 意图分类器故障 → **保守放行**（3.1） | 正常降级行为；检查 Key 与网络 |

### 10.4 数据与构建

| 症状 | 原因 | 处置 |
|---|---|---|
| 改了 md 但检索结果没变 | **派生副本不会自己发现知识源变了** | 重跑 `pipeline`（只改 json 则跑 `sync_graph`） |
| 图谱已是新的，但检索仍是旧的 | `kb.load()` **只读 Neo4j**，不会比对 json | 跑了 pipeline 却没同步？查 `sync_graph --check-only` |
| 知识点数不是 1465 | 源文档不完整 / 切分规则未覆盖新文档结构 | 对照 2.3 的"6 问自查清单"检查层级与标识假设 |
| Neo4j 写入报错 | **空列表不能作属性值**（关键词为空要存 `None`） | 已有处理，见 3.5；改这块时别改回去 |
| "清理陈旧向量"看起来没生效 | Milvus **写入与删除都要 `flush` 后才可见**，顺序写反会静默失效 | 顺序必须是"先取旧主键 → upsert → flush → delete"（3.4） |
| 排障时发现 `graph_expanded` 恒为 3 | **配置项没传进构造函数**（`EXPAND_K` 曾漏传） | 确认 `kb.py` 传了全部 `EXPAND_*`；有回归测试卡住（5.1） |
| Web 页面 404 | 没构建前端 | `cd web && npm run build` |
| 跑测试污染了 `logs/qa.log` | 测试没替换 logger | 已有 `NullLogger` 夹具 + 回归测试（5.1）；别绕过它 |

## 11. 本节小结

- 安装顺序：**Python/uv → 装依赖并跑离线测试 → `docker/.env` → 起四个容器 → bge-m3 路径 → `API_KEY` → pipeline 建库 → 起服务**。
- 装完依赖**先跑 `pytest`**：它全部离线（不需要容器/模型/Key），是验证 Python 环境最快的办法。
- **四个宿主机端口必须记准**：Milvus **19532**、MySQL **3308**、Neo4j **7474**（网页）/ **7687**（驱动）、Redis 6380——配置里写的都是宿主机端口。
- 凭证**集中在 `docker/.env`**，compose 与应用读同一份；密码里**避免 `$`**；`JWT_SECRET` 生产必须换。
- 建库后核对四个数字：知识点 **1465**、边 **21252**、Milvus **1465**、Neo4j 关系 **30569**；再跑 `sync_graph --check-only` 确认两侧一致。
- 三类环境坑最容易卡人：**版本组合**（pymilvus / ragas+langchain）、**端口混淆**、**模型路径**——都在第 10 节的排查表里。
- 一个贯穿性的认知：**无 Key 时系统降级而不崩**（检索链路可独立运行），这既是设计取舍，也是调试时的便利。

## 企业常见面试问答

**Q1：你这个项目的环境复杂度怎么样？依赖了哪些外部服务？**

> 分三层看。**本地自足的部分**：Python/uv 跑应用，四个容器（Milvus 向量、MySQL 记忆、Neo4j 图、Redis 是 Milvus 的依赖），加一个本地 bge-m3 模型（2.2GB，零 API 成本）。**唯一的外部依赖是 DashScope**，用于三件事：qwen-max 生成回答、qwen-turbo 做意图识别与反思、以及画像抽取。**关键在于降级行为**：没有 Key 时系统不会崩——CLI 降级为"只展示检索结果"，意图识别**保守放行**（都当可答），反思 **fail-closed**（直接停），画像抽取失败返回空。所以**检索链路可以完全独立于外部 LLM 运行与调试**，这在排障时很有价值。如果要内网部署，只需要把 `DASHSCOPE_BASE_URL` 指向兼容 OpenAI 协议的网关并换模型名。

**Q2：安装过程中最容易踩的坑是什么？**

> 三个，都是"不报错但很费时间"的类型：① **版本组合**——`pymilvus` 必须是 `>=2.5,<2.6`（2.4.x 在 Python 3.13 上 import 就失败，因为它依赖已被移除的 `pkg_resources`）；ragas 必须是 `ragas==0.3.0` + `langchain-community==0.4.0` + langchain 1.x 这个特定组合（0.4.x 会丢掉 `vertexai` 模块）。② **端口混淆**——Milvus 宿主机是 **19532**（容器内 19530）、MySQL 是 **3308**（容器内 3306）；配置里写的是宿主机端口，记反了就是连不上，而报错信息不会告诉你端口记错了。③ **模型路径**——`BGE_MODEL_PATH` 是"机器相关"配置，换环境必须改；而且"路径写错"和"模型加载失败"的表现很像。我的经验是：**先把离线测试跑通（`pytest`，不需要容器/模型/Key），再往上叠服务**——这样每加一层就能确定是哪一层的问题。

**Q3：为什么密码里要避免 `$`？**

> 因为**两个读取方对 `$` 的处理规则不同**。docker compose 会把 `.env` 里的 `$` 当作变量引用语法（要写 `$$` 才是字面量），而应用侧用 `python-dotenv` 读取时我们特意设置了 `interpolate=False`——**按字面读取、不展开**。这个设置本身是对的（避免密码被悄悄改写），但后果是：如果密码里含 `$`，compose 与服务端会拿到**不同的密码**，出现"compose 能连、应用连不上"这种最难查的现象。我们的处置是**直接约定密码里不用 `$`**——比"教每个人正确转义"更可靠。这也是 `.env.example` 模板里专门写了一句提示的原因。

**Q4：怎么确认安装真的成功了？**

> 我会按四步验证，每步都有**可核对的数字**：① `docker ps` 看到四个容器且 Milvus/MySQL/Neo4j 有 healthy（Neo4j 的 healthcheck 是执行 `cypher-shell 'RETURN 1'`，比"进程活着"更可信）；② `uv run python -m pytest tests/ -q` → **217 passed**（全离线，验证 Python 依赖）；③ `uv run python -m app.ingest.pipeline` → 输出 **1465 知识点 / 21252 关联边 / Milvus 1465 条**，再跑 `sync_graph --check-only` 确认 Neo4j 关系数 **30569** 与 json 一致；④ `export API_KEY=… && uv run python -m app.cli` 问一个能验证多跳的问题（比如民法典高空抛物，应命中"第一千二百五十四条"）。**关键是第三步的这些数字**——它们能一次性验证切分、建图、向量、图同步四件事都对了，比"服务起没起来"更能说明问题。
